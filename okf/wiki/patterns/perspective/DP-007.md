# DP-007 검증 기록 없는 지급

- 묶음: **진위 판별** — 대사로 나온 초과가 진짜 초과인지, 기준·단위·표기 문제로 생긴 초과인지 가른다
- 관점: 검증 절차 — 수량 검증을 거치지 않고 지급했는가
- 사고 유형: ⑦ 정책/시스템 통제 미흡 (같은 담당자·거래선에 반복되면 ②)
- 대상 범위: **좁힘** — 직전 결과 안에서 조건을 더해 줄인다
- 설명: 실적 지급은 수량 검증을 거친 뒤 지급되어야 한다. 검증 기록이 없거나, 지급 뒤에 검증되었거나, 검증 인정수량보다 많이 지급된 건을 찾는다. 수량이 맞더라도 검증 없이 지급된 것 자체가 통제 위반이다.
- 답하는 질문: 지급 전에 수량 검증 기록이 있고, 지급수량이 검증 인정수량 이내인가
- 관련 패턴(참고): [P-124 검증 로그 부재](okf/wiki/patterns/anomaly/P-124.md), [P-111 선후 순서 위반](okf/wiki/patterns/anomaly/P-111.md), [P-010 과실 기반 부정](okf/wiki/patterns/fraud/P-010.md)

## 고르는 때

보고서(누적 보고서와 부록 SQL)에서 아래 신호가 보이면 이 패턴을 후보로 둔다.

- 결과의 지급 건 일부에 검증 내역이 연결되지 않는다
- 보고서에 법인이 수량 검증을 하지 않는다(예: GSCM 수량검증 미실시)는 언급이 있다

## 고르지 않는 때

- 검증 내역 테이블에 지급 문서와 연결할 키가 없다 → 확인 필요로 남긴다

## 추출 로직

1. 지급 항목을 셀아웃 검증 정산 내역과 연결한다
2. 유형 ① 검증 없음: 연결되는 검증 내역이 없다
3. 유형 ② 사후 검증: 검증일 > 지급일
4. 유형 ③ 초과 지급: 지급수량 > 검증 인정수량
5. 법인·담당자별로 ①~③ 건수와 금액, 전체 지급 대비 비중을 낸다

## 정상 예외

질문에 「제외해 줘」로 넣는다.

- 검증 대상이 아닌 지급 유형(정액 지원 등)
- 검증 시스템 도입 이전 기간

## 임계 조정

숫자를 새로 정하지 않는다. 기준은 시나리오 생성 에이전트가 데이터 분포를 보고 정한다.

- ① 비중이 법인 전체 지급의 대부분이면 건 단위가 아니라 「검증 미운영 법인」으로 보고 범위를 법인 단위로 정리한다

## 멈춤 기준

- 무검증 지급액이 크면 검증부실 시나리오로 멈출 수 있다
- 특정 담당자·거래선에 몰리면 [DP-018](okf/wiki/patterns/perspective/DP-018.md) 과 함께 다시 본다

## 함께 쓰기

- [DP-006](okf/wiki/patterns/perspective/DP-006.md) — 같은 지급 항목의 수량 신뢰성과 함께
- [DP-018](okf/wiki/patterns/perspective/DP-018.md) — 무검증 지급이 몰린 대상을 함께 볼 때

## 질문 단서

> 직전 결과의 지급 건 가운데 셀아웃 검증 내역이 없거나, 지급 뒤에 검증되었거나, 검증 인정수량보다 많이 지급된 건을 뽑고 법인·담당자별 비중을 함께 보여 줘.

드릴다운 질문의 「이번 관점」 줄로 쓴다(원본 질의와 이전 관점 줄 뒤). 직전 결과에 맞춰 고쳐 쓰고, 함께 고른 패턴이 있으면 한 줄로 합친다. 물리명·패턴 번호는 쓰지 않는다.

## 대입 예시: 셀아웃 인센티브 과다지급

- 기준 시나리오: 셀아웃 인센티브 과다지급(영업 / 판매법인 / 매출차감, '23.上 등록). 거래선/SKU 기준 누적 셀인 < 셀아웃 인센티브 지급수량
- Risk 사례: ■■법인은 GSCM 수량검증을 하지 않고 수작업으로 관리
- 사고사례: ■■법인은 프로모션별 검증만 하고 누적 수 검증 프로세스가 없어 과지급
- 관련 테이블: `TI_GRPB_DE_SELLOUT`(셀아웃 검증 정산 내역), `TI_GRPF060·061`(지급 헤더·항목)

## 확인 필요

- `TI_GRPB_DE_SELLOUT` 의 검증일·인정 수량 컬럼과 지급 문서 연결 키
- 지급일 컬럼
