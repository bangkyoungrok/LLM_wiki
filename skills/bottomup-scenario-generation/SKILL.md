# bottomup-scenario-generation

데이터에서 이상치를 먼저 찾고, 그 이상치를 바탕으로 감사 시나리오를 만든다. 문서는 요청을 이해하고 테이블을 찾는 데 쓰고, 시나리오의 근거는 실제 데이터다. 결과는 `skills/audit-report/SKILL.md` 형식의 감사 보고서다.

```
1 요청 이해·테이블 찾기 (main-agent)
→ 2 이상치 탐색 (bottomup-anomaly-explorer)
→ 3 시나리오 탐색 (main-agent)
→ 4 보고서 (audit-report)
```

탐색 결과가 마음에 들지 않으면 스스로 판단해 앞 단계로 돌아가 다시 한다. 같은 테이블을 다른 기준으로 보려면 2단계로, 다른 테이블을 보려면 1단계 「테이블」로 돌아간다(기간은 다시 정하지 않는다). 2단계는 모두 합쳐 최대 2번까지 맡긴다.

## 1. 요청 이해와 테이블 찾기

1. **분석 기간**: 날짜를 말했으면 그 기간, 길이만 말했으면 직전 달 말일까지 그 길이, 말하지 않았으면 직전 달 말일까지 12개월이다(예: 2026-11-17 이면 2025-11-01 ~ 2026-10-31). 이 기간은 끝까지 바꾸지 않는다.
2. **도메인 정보**(필요할 때만): 요청의 용어나 업무 배경을 OKF 문서만으로 알 수 없으면 AGENTS.md 「도메인 정보 참고」대로 읽는다.
3. **도메인**: `okf/wiki/index.md` 로 요청에 맞는 도메인을 정하고 도메인 page 를 읽는다. 요청에 범위가 없으면 거래 테이블이 많은 도메인 2개다. `okf/wiki/patterns/anomaly/index.md` 는 어떤 이상치를 볼 만한지 감을 잡는 참고로만 본다.
4. **테이블**: 요청에 테이블이 있으면 그것을, 없으면 도메인 page 「테이블 목록」에서 요청과 관련 있고 거래가 한 건씩 쌓이는(날짜·금액이 있는) 테이블을 고른다. 몇 개를 고를지는 요청에 맞춰 판단한다. 업무 표현이 많거나 도메인 page 로 테이블을 찾지 못하면 `schema-linker` 에 맡긴다.
5. **시나리오 JSON**: 입력에 `scenario_name`·`scenario_sql` 이 있으면 그 SQL 이 읽는 테이블을 먼저 넣고, SQL 의 조건은 2단계에 참고로 넘긴다.

## 2. 이상치 탐색 — `bottomup-anomaly-explorer`

고른 테이블에 이상치가 있는지 `bottomup-anomaly-explorer` 에 맡겨 찾는다. 이 단계는 시나리오를 만드는 것이 아니라 이상한 데이터가 있는지 보는 것이다. 요청, 분석 기간, 테이블, 도메인 page, 참고(볼 만한 이상징후 패턴, 시나리오 JSON)를 넘긴다(형식은 `sub-agents/bottomup-anomaly-explorer/SKILL.md` 의 「입력」).

- 이상치가 돌아오면 3단계로 간다.
- 이상치가 없으면, 요청과 관련 있는 다른 테이블이나 도메인이 있을 때 1단계 「테이블」로 돌아가 새로 고르고 한 번 더 맡긴다. 그래도 없으면 「유효한 시나리오 없음(이상치 없음)」으로 4단계에 간다.

## 3. 시나리오 탐색

찾은 이상치로 시나리오 SQL 을 만들어 실행하고, 쓸 만한 시나리오가 나올 때까지 고친다. main-agent 가 직접 한다.

1. **읽기**(한 응답에서 함께): `skills/sql-query/SKILL.md`, 이상치가 나온 테이블의 문서, `okf/wiki/normal-patterns.md`.
2. **이상치 고르기**: 요청과 관계가 크고, 금액·건수가 크고, 같은 대상에서 여러 이상치가 겹치는 것부터 쓴다. 연결된 두 테이블을 이어야 보이는 이상치(연결된 기록 없음, 금액 불일치)는 감사 가치가 높다. 이상치에 맞는 이상징후 패턴이 있으면 조건을 쓸 때 참고한다.
3. **컬럼·코드값 확인**: 조건에 쓸 컬럼·코드값 뜻을 확인할 것이 여럿이면(테이블 3개 이상, 또는 확인할 코드값 2개 이상) `term-grounding` 에 맡긴다.
4. **시나리오 SQL 쓰고 확인**: `skills/sql-query/SKILL.md` 에 적힌 시나리오 SQL 쓰는 법대로 쓰고, 건수를 확인하고, 걸린 건을 살펴본다. 조건의 숫자는 이상치 결과의 값(평소 범위의 경계 등)을 쓰고 새로 지어내지 않는다.
5. **다시 하기**: 확정하지 못하면 조건을 고치거나 다른 이상치로 2부터 다시 한다. 데이터 적재·표기 문제로 보이면 부수 발견에 적고 다른 이상치로 간다. 이상치를 다 써도 안 되면, 같은 테이블을 다른 비교 단위나 지표로 볼 여지가 있을 때는 2단계로, 다른 테이블을 봐야 할 때는 1단계 「테이블」로 돌아가 한 번 더 한다.

`execute_sql` 상한(AGENTS.md)에 닿을 때까지 확정하지 못하면 「유효한 시나리오 없음」으로 4단계에 간다.

**시나리오 이름**: 데이터에서 보인 현상으로 40자 이하로 짓는다.

- 예: 「종료일보다 먼저 지급된 기록이 특정 거래선에 몰림」, 「짝이 되는 출고 기록이 없는 청구 행」
- 부당, 허위, 특혜, 몰아주기, 들러리, 조작, 횡령, 유용, 담합처럼 의도를 단정하는 말은 쓰지 않는다. 기간, 테이블·컬럼 이름, 패턴 ID 도 넣지 않는다.
- 시나리오 JSON 의 조건을 그대로 썼으면 그 `scenario_name` 을 쓴다.

## 4. 보고서 — `audit-report`
