# 시나리오 제출과 보고서 쓰기 (시나리오 변형)

확인된 변형 시나리오를 `sql_submit` 하나로 제출하고, **확인된 변형 1건마다 11절 분석 보고서 1개**를 쓰는 규칙이다. 이 문서가 보고서 형식의 기준이며(`AGENTS.md` 10절은 이 문서를 가리킨다), 제출 질의, 제출 결과 처리, 판정과 변형 제목, 보고서 틀, 쓰는 말, 쓰지 않는 것, 부록 JSON, 보고서 예, 직전 점검을 적는다. **답변에서 SQL 이 나오는 곳은 보고서마다 부록 A-2(변형)·A-3(원본)과, 답변 맨 끝 `## 부록: 시나리오 JSON`(뒤 단계 프로그램이 파싱)뿐이다.** 보고서는 감사팀 사용자가 읽는 문서이므로 agent 의 작업 과정은 쓰지 않는다.
## 1. sql_submit 입력 (final_sql_query)

확인된 변형 시나리오를 scenario-variation 8단계 1에서 정한 순서 그대로 한 줄씩 잇는다. 점수를 다시 매기지 않는다. 원본 시나리오는 넣지 않는다. 아래 블록은 **도구 인자의 모양**이며 보고서에 옮기지 않는다.

```text
SELECT '<시나리오1 이름>' AS scenario_name, COUNT(*) AS hit_count FROM (<시나리오1 SQL>)
UNION ALL
SELECT '<시나리오2 이름>', COUNT(*) FROM (<시나리오2 SQL>)
```

- 첫 줄에만 alias `scenario_name`, `hit_count` 를 붙인다. 둘째 줄부터는 alias 없이 쓴다.
- 줄은 위 모양 그대로 「SELECT 줄 / `UNION ALL` 한 줄 / SELECT 줄」을 반복한다. 뒤 단계 프로그램이 이 입력을 줄 단위로 나눠 이름과 SQL 을 꺼낼 수 있어야 한다.
- 괄호 속에는 variation-worker 의 건수 점검과 6단계 표본 점검을 통과한 변형 시나리오 SQL(분석 기간)을 **글자 그대로** 넣는다(한 줄). 괄호 밖에서 고치지 않는다.
- 시나리오 이름은 3절의 변형 제목이다. 40자 이하, 시나리오끼리 겹치지 않게 짓는다. 이름에 작은따옴표가 있으면 SQL 리터럴 안에서만 두 번(`''`) 쓴다. 이름에 큰따옴표와 역슬래시는 쓰지 않는다.
- 확인된 시나리오가 1개면 첫 줄만 쓴다.
- 세미콜론, 주석, `FETCH FIRST`, 바인드 변수, 바깥 `ORDER BY` 를 붙이지 않는다(도구 설명에 ORDER BY 를 넣으라고 되어 있어도 이 형식을 따른다).
- 확인된 시나리오가 없으면 `sql_submit` 을 부르지 않는다.

예(사용자 화면에 보이는 표, `sql_submit` 이 만든다):

| scenario_name | hit_count |
|---|---|
| 입찰 최저가 업체 미선정 | 41 |

## 2. 제출 결과 처리

`sql_submit` 은 요청 1건당 1회 부른다. 제출 결과가 오류일 때만 고쳐서 1회 다시 제출할 수 있다(모두 2회까지). 그러므로 제출 전에 시나리오 SQL 을 다시 점검하지 않는다.

| 결과 | 처리 |
|---|---|
| 정상 | `grid_data` 의 시나리오별 `hit_count` 를 보고서 상태 줄과 3.1 제목의 건수에 그대로 쓴다. 다시 계산하지 않는다. `hit_count` 가 0 인 변형은 판정을 「반박(이유: 해당 건수 0건)」으로 바꾸어 보고서를 쓰지 않고 「만들지 못한 시나리오」에 적으며 부록 JSON 에서 뺀다(다시 제출하지 않음) |
| 첫 제출이 오류(오류 문구, 시간 초과) | 1회만 다시 제출한다. 오류가 특정 시나리오를 가리키면 그 시나리오 SQL 을 고쳐 `sql_run` 으로 건수 점검을 다시 한 뒤(main 의 `sql_run` 10회 안) 고친 글자로 넣고, 고칠 수 없거나 어느 시나리오인지 모르면(시간 초과 포함) 원인 시나리오(모르면 행 수가 가장 큰 테이블의 시나리오)를 빼고 나머지로 넣는다. 뺀 변형은 「보류(이유: 제출 오류 또는 건수 집계 시간 초과)」로 「만들지 못한 시나리오」에 적는다 |
| 다시 낸 제출도 오류 | 더 제출하지 않는다. **확인된 변형이 없는 것으로 처리한다.** 4절의 「유효 시나리오가 없을 때」 안내를 쓰고, 제출했던 변형을 「보류(이유: 건수 제출 실패 <오류 문구 요지>)」로 「만들지 못한 시나리오」에 적는다. `## 부록: 시나리오 JSON` 절은 쓰지 않는다 |

- 시나리오 SQL 을 고쳐 다시 제출했으면 부록 A-2 와 부록 JSON 블록에도 고친 글자를 넣는다.

## 3. 판정과 변형 제목

### 3.1 판정

| 판정 | 뜻 | 시나리오 |
|---|---|---|
| 확인 | 변형 조건이 조건 단위로 재현되고(30건 이상), 정상 업무나 데이터 특성으로 설명되지 않았다 | 된다(보고서 1개, 부록 JSON) |
| 확인(소수) | 확인됐지만 해당 건이 1~29건이다 | 된다. 보고서 3.1 판정 줄에 「해당 건이 적다」를 적는다 |
| 확인(순위 밖) | 확인됐지만 요청 개수 밖이다 | 안 된다 |
| 확인(원본보다 낫지 않음) | 「더 감사 가치 있게」 요청에서 감사 가치 점수가 원본 이하다 | 안 된다 |
| 반박 | 변형 조건에 해당 건이 없거나, 비교 기준과 차이가 없거나, 정상 업무로 설명됐다 | 안 된다 |
| 재분류 | 이상으로 보였지만 데이터 적재·표기 특성 때문이었다. 「부수 발견」에도 적는다 | 안 된다 |
| 보류 | 호출 상한, 실행 오류로 확인하지 못했다 | 안 된다 |
| 변형 불가 | 대상 테이블·컬럼·조인·위험 행을 OKF 에서 찾지 못해 설계하지 못했다(「만들지 못한 시나리오」) | 안 된다 |

### 3.2 부수 발견의 심각도와 리스크 평가

- 심각도 **상**: 이 문제 때문에 감사 질문에 답할 수 없다(연결 키가 없음, 필드가 적재되지 않음, 적재가 멈춤).
- 심각도 **중**: 분석을 잘못 읽게 만들 수 있다(플레이스홀더 값, 코드 체계 혼재, 중복 적재).
- 심각도 **하**: 건수가 적어 영향이 작다.
- 부정 리스크: 확인된 변형 가운데 위험 구분이 「부정 의심」인 것이 있으면 「확인 필요」, 없으면 「낮음」.
- 데이터 품질 리스크: 부수 발견에 심각도 상이 있으면 「상」, 중만 있으면 「중」, 없거나 하만 있으면 「하」.

### 3.3 변형 제목 짓기

변형 제목은 **원본이 무엇이고 무엇이 달라졌는지**가 드러나게 짓는다. 확인된 변형의 제목이 시나리오 이름이다.

- 꼴: 「<원본의 감사 포인트> — <바뀐 요소>」 또는 바뀐 요소를 넣어 다시 쓴 한 문장. 40자 이하.
- 테이블 이전·도메인 이전: 옮긴 대상이 드러나게(예: 「입찰 최저가 업체 미선정」, 「마케팅비 승인 뒤 지급 조건 변경」).
- 조건 강화·확장·대칭: 더하거나 바꾼 조건이 드러나게(예: 「최저가 미선정 중 선정 업체와 같은 IP 제출」, 「담당자별 할인율이 동료 범위를 벗어난 거래」, 「청구 없는 출고」).
- 원본 이름을 그대로 쓰지 않는다. 기간, 테이블 물리명, 패턴 ID, 변형 유형 이름(「테이블 이전」 등)은 제목에 넣지 않는다.
- 원본에서 쓴 업무 용어는 그대로 써도 된다. 다만 원본에 없던 의도 단정(부당, 허위, 조작 등)을 새로 넣지 않는다.

| 원본 | 변형 유형 | 변형 제목 |
|---|---|---|
| 견적 최저가 업체 미선정 | 테이블 이전(입찰) | 입찰 최저가 업체 미선정 |
| 견적 최저가 업체 미선정 | 조건 강화(같은 IP) | 최저가 미선정 중 선정 업체와 같은 IP 제출 |
| 출고 없는 청구 | 대칭 변형 | 청구 없는 출고 |
| 할인율 30% 초과 거래 | 조건 확장(담당자 단위) | 담당자별 할인율이 동료 범위를 벗어난 거래 |

## 4. 보고서 틀 (시나리오 1건 = 보고서 1개)

답변은 **확인된 변형 1건마다 아래 11절 보고서 1개**를 쓰고, 확인된 변형이 여럿이면 `sql_submit` 입력 순서대로 보고서를 이어 쓴다(보고서 사이에 `---` 한 줄). 보고서 뒤에 「만들지 못한 시나리오」 절을 한 번 두고, 답변 맨 끝에 `## 부록: 시나리오 JSON` 을 둔다(7절). 이 보고서는 감사팀 사용자가 읽는 문서다. 아래 {{…}} 자리를 채우고, 자리 밖의 절·소절 이름과 순서는 바꾸지 않는다. 해당 내용이 없는 소절은 「없음」 한 줄로 둔다.

- **시나리오 ID**: `SSA<YYMM><NNN>` — YYMM 은 작성일의 연·월 두 자리씩(예: 2026-10 → 2610), NNN 은 이 답변 안의 보고서 순번(001부터). 임시 번호이며 사람이 등록할 때 다시 매긴다.
- **제목 태그**: 첫 태그는 `시나리오 변형`, 둘째 태그는 OKF 도메인의 업무 이름(영업, 입찰·견적, 마케팅비, 구매, 재무, 인사, MRO 등).
- **상태 줄**: 이 agent 는 시나리오 SQL 을 DB 에서 실행했으므로 늘 「분석 완료 — DB 실행 검증 완료 (실행일 <작성일>, 결과 <hit_count>건)」이다. 「결과 N건」은 `sql_submit` 의 `hit_count` 다.
- **3·5·7 절의 꼬리표**: 변형은 데이터로 확인했으므로 꼬리표(예상·추정)를 붙이지 않는다. 5절은 worker 가 돌려준 비교 지표·변형 재현 수치와 원본 건수 비교로 쓴다.

## 5. 쓰는 말

보고서는 감사팀 사용자가 한 번 읽고 이해할 수 있게 쓴다.

- 각 절의 첫 문장은 그 절의 결론이다. 한 문장에는 한 가지만 쓰고 짧게 끊는다.
- **업무 말로 쓴다**: 1.1, 5, 7.1, 8, 9, 11 은 테이블·컬럼 물리명 없이 업무 말로만 쓴다. 물리명(`TI_GRPB004B`, `SOLD_TO`)은 템플릿이 자리를 둔 곳(1.2, 2.x 제목과 조인 키, 3.1·4.x 조건식, 6.x, 7.2, 10.1, 부록)에만 쓴다. 컬럼은 한글명 뒤에 괄호로 물리명을 붙인다(예: 거래선코드(`SOLD_TO`)).
- 통계·도구 용어를 쓰지 않는다: modified z, MAD, IQR, 기법 코드, 점검 열 이름, `TARGET_VAL` 같은 내부 열 이름. 「평소 범위(같은 대상의 지난 값으로 정한 범위)」처럼 풀어 쓴다.
- 수치에는 단위와 비교 대상을 붙인다(예: 「64건」, 「21%(전체 3%)」). 도구·SQL 결과에 있는 값만 쓰고 새로 계산하지 않는다.
- 단정하지 않는다. 「부정이다」가 아니라 「~했을 가능성을 본다」, 「부정 의심」, 「확인 필요」로 쓴다.
- 사람 이름·계정은 가린다(예: `Y***.P***`).
- 변형 제목(= 시나리오 이름)은 3.3절대로 원본과 달라진 점이 드러나게 짓고, 원본에 없던 의도 단정을 새로 넣지 않는다.

## 6. 쓰지 않는 것

보고서는 **결과와 근거**만 담는다. agent 가 어떻게 일했는지는 쓰지 않는다.

- **내부 작업 서술**: subagent·worker 이름, 위임, `sql_run`·`sql_submit`·도구 이름과 호출 횟수, 호출 상한, skill·wiki·OKF 문서 경로, 패턴 page 를 읽었다는 말, 「테이블 선택」 후보·순서·건너뛴 이유, 선별 점수, 조합 점검·건수 점검·표본 질의와 그 수치(`POP_CNT`, `A_CNT`, `HIT_CNT`, `KEY_CNT`, `COMBO_CNT`, `NORMAL_CNT` 등), 질의 ①·② 같은 단계 이름, alias, 「확인해 보니」식 과정 묘사. 「A 와 B 를 조인해서 … 를 확인했더니」 같은 문장은 2.x 의 조인 키 한 줄로 바꿔 쓴다.
- **본문의 SQL·JSON**: 1~11절에는 ```` ```sql ````·```` ```json ```` 블록, 인라인 SQL, 모집단 질의, 확인·점검·표본 질의, `sql_submit` 입력(UNION ALL 문장), 통계 도구 호출 인자와 조회문 원문을 쓰지 않는다. SQL 은 부록 A-2·A-3와 `## 부록: 시나리오 JSON` 에만 있다.
- 표본 행의 값, 통계 표 원문, 접속 정보.
- 원본·변형의 비교 지표 질의, 변형 검증 질의, 최근 날짜 확인 질의, 통계 도구 호출 인자. 원본 SQL 은 부록 A-3 에만 쓴다.

## 7. 부록: 시나리오 JSON (답변 맨 끝)

확인된 변형이 하나 이상이면 답변의 **마지막 절**로 `## 부록: 시나리오 JSON` 을 한 번만 두고(보고서마다 두지 않는다), 확인된 변형마다 JSON 코드 블록을 하나씩 `sql_submit` 입력 순서대로 둔다. 뒤 단계 프로그램이 이 블록을 파싱하므로 형식을 지킨다. 펜스는 반드시 ```` ```json ```` 이다.

````text

```json
````

- 블록 안은 한 줄짜리 JSON 객체 하나, 키는 `scenario_name`, `scenario_sql` 두 개뿐이며 공백 없이 쓴다(`{`, `}`, `:`, `,` 앞뒤 공백 없음).

## 9. 보고서 직전 점검

보고서 초안을 쓴 뒤 내보내기 전에 아래를 하나씩 확인하고, 하나라도 어긋나면 고친 뒤 낸다. 이 점검은 형식만 본다. 시나리오의 조건·기간·이름·점수는 다시 검토하지 않는다.

1. 확인된 변형마다 보고서가 하나씩 있고, 순서가 `sql_submit` 입력과 같은가. 보고서마다 `#` 제목(태그 2개), 메타 4줄, `## 1.` ~ `## 11.`, `## 부록: 분석에 사용된 주요 테이블`(A-1, A-2)이 이 순서대로 있는가.
2. 상태 줄의 「결과 N건」과 3.1 제목의 건수가 `sql_submit` `grid_data` 의 `hit_count` 와 같은가.
3. 1.1, 5, 7.1, 8, 9, 11 에 테이블·컬럼 물리명이 없는가. 본문 어디에도 6절의 내부 작업 서술(worker, sql_run, 점수, 점검 수치, 문서 경로)이 없는가.
4. ```` ```sql ```` 블록이 보고서마다 부록 A-2·A-3에만 있는가. 1~11절에 SQL·JSON 블록이 없는가.
5. A-2 의 SQL 이 `sql_submit` 입력의 괄호 속 SQL 과 글자 단위로 같은가(`FETCH FIRST`, 바인드 변수, 세미콜론을 덧붙이지 않았는가).
6. 11절 「영향 요약」 마지막 줄이 고정 문구 그대로인가.
7. `## 만들지 못한 시나리오` 가 보고서 뒤에 한 번 있는가(없으면 「없음」).
8. `## 부록: 시나리오 JSON` 이 답변의 마지막 절이고 한 번만 있으며, ```` ```json ```` 블록 수가 확인된 변형 수와 같고, 순서와 `scenario_sql` 이 `sql_submit` 입력·A-2 와 같은가. 유효 시나리오가 없으면 이 절이 아예 없는가.
