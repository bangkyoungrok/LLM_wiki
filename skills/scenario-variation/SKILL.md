# scenario-variation

원본 시나리오에서 출발해 변형 시나리오를 만든다. 순서는 **원본 분해 → 변형 설계 → 패턴·위험 붙이기 → 데이터 확인 → 표본 점검 → 제출 → 보고서**다. 기간은 분석 기간 하나만 쓴다. 이 SKILL.md 를 읽은 다음 응답에서 아래 파일을 `agent_studio_project_view` 로 함께 읽는다.

- `skills/scenario-variation/references/variation-types.md` (감사 골격, 변형 유형, 후보 기록 형식)
- `skills/scenario-variation/references/query-writing.md`, `skills/scenario-variation/references/answer-format.md` (질의, 제출, 보고서)
- `wiki/patterns/index.md`, `wiki/risk-interpretation.md`, `wiki/normal-patterns.md`, `wiki/criteria.md`

`stat-views.md`·`result-reading.md` 는 통계 경계가 필요한 변형(조건 확장 등)이 있을 때만 읽는다. 패턴 분류 파일(`wiki/patterns/anomaly/*.md`)은 2·3단계에서 원본·변형에 붙는 패턴의 것만 읽는다.

## 절차

1. 요청 해석: 원본(입력 형태: 기존 시나리오 목록의 이름 / JSON / 자연어), 변형 유형(사용자 지정, 없으면 `variation-types.md` 3절), 변형 개수(기본 1), 대상(지목한 테이블·도메인), 기간(원본 SQL 에 기간 리터럴이 있으면 그 기간, 사용자가 말했으면 그 기간, 둘 다 없으면 최근 데이터 기준 1년)을 정한다. 원본을 하나로 특정할 수 없으면(같은 이름이 여럿, 설명이 모호) 보고서 대신 한 가지만 되묻는다. **여기서 정한 원본·유형·개수·기간 해석은 확정이다.** 이후 단계에서 사용자 요청 문장을 다시 인용하거나 해석하지 않는다.
2. 원본 확보와 분해:
   - `variation-types.md` 1절대로 감사 골격을 만든다. 기존 시나리오 목록의 이름이면 `okf/references/scenarios.md`(있을 때)와 `okf/t2s/examples/` 를, JSON 이면 SQL 을, 자연어면 `sql-query` 「테이블 선택」 절로 테이블을 고른다(`sql-query` 를 아직 읽지 않았으면 이때 `skill_view` 로 읽는다. 표현 3개 이상이거나 테이블을 못 찾으면 후보 확인을 `term-grounding` 에 맡기고 고르기는 main agent 가 한다). 원본 SQL·목록에 적힌 참조 테이블은 다시 고르지 않고 그대로 쓴다. 참조 테이블 문서를 한 응답에서 함께 읽는다.
   - 조각마다 데이터 이상징후 패턴을 붙이고(`wiki/patterns/index.md` 2·3절), 감사 위험을 고른다(`wiki/risk-interpretation.md` 3절).
   - 분석 기간 정하기(원본·사용자가 날짜를 주지 않았을 때): 기준 테이블의 최근 데이터 날짜를 아래 질의로 `sql_run` 1회 확인한다. `FROM_DT`(포함) ~ `TO_DT`(미포함)가 분석 기간이다. 원본과 변형의 테이블이 다르면 두 테이블을 `UNION ALL` 로 함께 보고 `LAST_DT` 가 더 이른 쪽을 끝으로 한다. 날짜는 결과 값을 그대로 쓴다.

     ```sql
     SELECT '<테이블>' AS TBL, m.LAST_DT, TO_CHAR(ADD_MONTHS(TO_DATE(m.LAST_DT, 'YYYYMMDD') + 1, -<개월 수>), 'YYYYMMDD') AS FROM_DT, TO_CHAR(TO_DATE(m.LAST_DT, 'YYYYMMDD') + 1, 'YYYYMMDD') AS TO_DT FROM (SELECT MAX(<기준 날짜>) AS LAST_DT FROM <query_name> WHERE <기준 날짜> <= TO_CHAR(SYSDATE, 'YYYYMMDD') AND <기준 날짜> >= TO_CHAR(ADD_MONTHS(SYSDATE, -24), 'YYYYMMDD') AND REGEXP_LIKE(<기준 날짜>, '^[0-9]{8}$')) m
     ```

     - `<개월 수>` 는 기본 12. `VARCHAR2(14)` 는 `SUBSTR(<기준 날짜>, 1, 8)`, `DATE` 는 `TO_CHAR(<기준 날짜>, 'YYYYMMDD')` 로 바꿔 쓴다. 최근 2년 안에 데이터가 없는 테이블(`LAST_DT` NULL)은 변형 대상으로 쓰지 않는다.
   - 원본 건수: 원본 SQL(복원 포함)의 기간 리터럴을 분석 기간으로 맞춘 뒤 `query-writing.md` 3절 건수 점검 질의를 `sql_run` 1회 실행해 POP_CNT, HIT_CNT, HIT_AMT 를 적어 둔다. 실행되지 않는 원본은 `sql-query` 판정 표로 1회만 고치고, 그래도 안 되면 「원본 실행 불가」로 두고 변형만 진행한다.
3. 변형 설계(문서만, SQL 실행 없음): `variation-types.md` 2절 규칙으로 요청 개수 + 2개까지 후보를 만든다. 테이블 이전·도메인 이전의 대상 테이블은 `sql-query` 「테이블 선택」 절대로 고른다(사용자가 테이블을 지목했으면 그 테이블). 후보마다 4절 형식(대응표, 질의 초안, 바꾼 이유, 비교 지표, 통계 경계 필요 여부, 확인된 사실 — `query_name`·유형과 「테이블 선택」 기록 줄 포함)을 채운다. 대상 테이블 문서·조인 문서를 한 응답에서 함께 읽는다(최대 10개). 대상이나 조각을 OKF 에서 찾지 못한 후보는 「변형하지 못한 후보」로 두고 이유를 적는다.
4. 패턴·위험 붙이기: 후보마다 바뀐 조각에 패턴을 붙이고(`wiki/patterns/index.md`), 감사 위험 행을 정한다(원본과 같은 행이 원칙, `risk-interpretation.md` 3절). 위험 행이 없거나 `normal-patterns.md` 로 이미 설명되는 조각만 남은 후보는 뺀다. 후보에 V1 부터 번호를 붙이고 `answer-format.md` 3절 규칙으로 제목을 짓는다.
5. 데이터 확인: 후보마다 `variation-worker` 1개를 한 응답에서 함께 맡긴다(최대 5개, 아래 「variation-worker 위임」). worker 가 조각을 고쳐 돌려주면(조각 수정) 고친 조각을 그 후보의 변형으로 쓰고 대응표와 제목도 맞춘다.
6. 표본 점검: worker 가 「충분」·「충분(소수)」로 돌려준 후보마다 worker 의 예외 질의로 `query-writing.md` 4절 표본 질의(5행, PII 제외)를 `sql_run` 1회 실행한다. 아래 판정 표로 판정한다.
7. 시나리오 SQL 확정: 「확인」·「확인(소수)」 후보마다 worker 의 예외 질의(분석 기간)를 글자 그대로 시나리오 SQL 로 확정한다(다시 실행하지 않는다). 제목이 시나리오 이름이다.
8. 선별·제출·보고서:
   1. `wiki/criteria.md` 로 원본과 확인된 변형의 점수를 매긴다. 「더 감사 가치 있게」 요청이면 위험 연결·영향 규모·탐지 가능성 합이 원본보다 높은 변형만 남긴다(낮으면 판정을 「확인(원본보다 낫지 않음)」으로 바꾸고 시나리오에서 뺀다). 점수 순으로 요청 개수만 시나리오로 낸다. 나머지 확인된 후보는 「확인(순위 밖)」이다.
   2. 제출(조립만 한다): 1에서 정한 순서 그대로, 시나리오마다 제목과 SQL(7단계에서 확정한 예외 질의)을 글자 그대로 `answer-format.md` 1절 틀에 넣어 `sql_submit` 을 1회 부른다. 시나리오가 없으면 부르지 않는다. 이 단계에서는 기간·조각·대응표·제목·점수를 다시 검토하지 않고, 사용자 요청을 다시 해석하지 않으며, 보고서를 구상하지 않는다. 표본 점검까지 통과한 SQL 은 제출 전에 다시 점검하지 않는다. `sql_submit` 을 부르는 응답에서는 제출 질의만 만들고, 보고서는 결과를 받은 다음 응답에서 쓴다. 오류면 `answer-format.md` 2절대로 1회만 다시 제출하고, 다시 실패하면 확인된 변형이 없는 것으로 처리한다.
   3. 보고서를 쓰기 직전에 `answer-format.md` 를 다시 읽는다(이 단계만 같은 대화에서 이미 읽은 파일을 다시 읽는다). `answer-format.md` 4절 틀로 **확인된 변형 1건마다 11절 분석 보고서 1개**를 `sql_submit` 입력 순서대로 쓴다. 재료는 이미 확정된 것(판정, worker 반환의 수치·설명 재료, 확인된 사실, 테이블 문서, `sql_submit` 결과)을 `answer-format.md` 4절 「재료 대응」 표대로 옮겨 쓰며 다시 정하지 않는다. 보고서 뒤에 `## 만들지 못한 시나리오`(변형 불가·반박·재분류·보류·확인(순위 밖)·확인(원본보다 낫지 않음) 후보, `hit_count` 0)와 `## 부수 발견`, 맨 끝에 `## 부록: 시나리오 JSON` 을 둔다. 문체와 금지는 `answer-format.md` 5·6절을 따른다: 감사팀 사용자가 읽는 문서이므로 업무 말로, 물리명은 템플릿 자리에만, 통계·도구 용어와 agent 의 작업 과정(worker, 도구, 점수, 질의 ①·②, 점검 수치, 문서 경로)은 쓰지 않는다. `answer-format.md` 9절 점검을 마친 뒤 낸다.

변형 시나리오 SQL 은 특정 거래처나 사원을 지목하지 않고 조건으로 쓴다. 지목된 대상은 근거 수치로 적는다.

## sql_run 상한 (main agent)

- main agent 의 `sql_run` 은 요청 1건당 **10회**다. 단계별로 나누어 두지 않고 합쳐서 센다. 쓰는 곳은 2단계 최근 날짜 확인(원본이나 사용자가 날짜로 기간을 줬으면 0회)과 원본 건수 점검(1회, 수정 1회), 6단계 표본 점검(「충분」 후보당 1회), 수정과 제출 오류 뒤 재점검이다.
- 3·4단계는 문서만으로 한다. 변형 후보의 SQL 을 main agent 가 시험 실행하지 않는다(worker 가 한다). 6단계 표본 점검에 쓸 횟수를 남겨 둔다.
- 같은 SQL 은 다시 실행하지 않는다. 수정은 질의 1건당 2회까지이되 10회 안에서만 한다. 고쳐도 안 되면 「보류」로 적고 넘어간다.
- 직접 읽는 테이블 문서는 10개까지, `sql_submit` 은 1회(오류 시 1회 재제출)다. 읽을 문서는 원본 테이블, 변형 대상 테이블, 그 사이 조인 문서로 충분하다. 확인하지 못한 것은 추가 조회로 메우기보다 「데이터 해석 가정」에 적는다.

## variation-worker 위임

subagent 는 이 대화를 보지 못한다. worker 가 값 확인·문서 탐색으로 질의를 낭비하지 않도록 **main agent 가 이미 확인한 사실을 모두 넘긴다.** `variation-types.md` 4절의 후보 기록을 그대로 넣고 아래를 더한다.

1) 목표: 「아래 변형 시나리오가 분석 기간 데이터에서 조건 단위로 재현되는지, 정상 업무나 데이터 특성으로 설명되지 않는지 확인해 variation-worker 반환 형식으로 돌려준다」
2) 원본 골격 요약과 원본 건수(POP_CNT, HIT_CNT, HIT_AMT)
3) 분석 기간: 시작일 포함·종료일 미포함 날짜와 기준 날짜 컬럼 형식에 맞춘 리터럴
4) 대상 테이블 문서 경로, 조각에 붙은 패턴의 분류 파일 경로
5) 상한과 출력: `sql_run` 5회·통계 도구 2회 이하, 반환 형식(2,000 token 이하)

- 돌려받은 결과가 반환 형식이 아니면 같은 prompt 로 1회만 다시 맡기고, 다시 실패하면 그 후보는 「보류」(이유: 데이터 확인 실패)로 적는다.

## 판정

후보마다 아래 표에서 위부터 맞는 첫 행으로 판정한다. 판정 이름의 뜻은 `answer-format.md` 3절이다.

| 상황 | 판정 |
|---|---|
| worker 가 「충분」이고, 표본 5행이 `wiki/normal-patterns.md` 의 정상 조건에 해당하지 않음 | 확인 |
| worker 가 「충분(소수)」이고 표본이 정상 조건에 해당하지 않음 | 확인(소수) — 시나리오로 내되 해당 건이 적다고 적는다 |
| 표본 행이 `normal-patterns.md` 2절(업무 패턴)에 해당함 | 반박 (이유: 표본이 정상 업무 <패턴>) |
| 표본 행이 `normal-patterns.md` 1절(데이터 특성)에 해당함 | 재분류 (이유: 데이터 적재·표기 특성 <패턴>). 「부수 발견」에도 적는다 |
| worker 가 「반박」 또는 「재분류」 | worker 판정 그대로 |
| worker 가 「보류」, 표본 질의 오류가 `sql-query` 의 수정 뒤에도 남음, 호출 상한 | 보류 (이유: 확인하지 못한 까닭) |
| 3·4단계에서 대상·조각·위험을 찾지 못함 | 변형 불가 (보고서 4절, 이유) |
