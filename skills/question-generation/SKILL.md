# question-generation

`top-down`·`bottom-up` 은 시나리오 생성 에이전트에 넣을 **감사 질문 1건**과 그 JSON 을 만든다. 순서는 **요청 해석 → 후보 모으기 → 후보 정리 → 점수로 1건 고르기 → 후보 확인 → 질문 쓰기 → 최종 확인 → JSON 출력** 이다.

`variant` 는 `skills/question-generation/references/variant.md` 를 따른다. 이 파일에서는 「질문 문장 규칙」과 「출력 JSON」의 출력 형식·`scope.period` 규칙·질문 생성 불가 형식만 쓴다.

`drilldown` 은 더 좁힐지 판단하고 **드릴다운 질문 1건**을 만든다. 맨 아래 「drilldown」 절만 따른다. 그 위의 절들은 `drilldown` 에 쓰지 않는다.

## 모드별 근거

| 모드 | 후보 모으기 | 근거 | 질문 모양 |
|---|---|---|---|
| `top-down` | `question-scout` | 부정 패턴(P-0xx), 실제 사고(CS-xxx), 도메인·테이블 문서 | 「부정 위험 시나리오를 만들어줘」 |
| `bottom-up` | `question-table-scout` | 테이블 문서의 컬럼·키·기준 날짜·금액·관련 테이블, 이상징후 패턴(P-1xx), 실제 사고 | 「테이블 구조에서 …가 서로 맞지 않는 거래를 찾아줘」 |
| `drilldown` | 없음(main-agent 가 직접) | 누적 보고서, 사고 유형(7개), 드릴다운 패턴(DP-xxx) | 「<원본 질의> 위 질의에 더해, 아래 관점으로 결과를 더 좁고 깊게 봐 줘. - <관점>: …」 |

- 패턴 번호의 실제 범위는 `skills/question-generation/references/local-values.md` 에 있다.
- 패턴 종류를 섞지 않는다. top-down 은 P-0xx, bottom-up 은 P-1xx, drilldown 은 DP-xxx 만 쓴다.
- bottom-up 은 테이블 1개에서 시작할 수도 있고, 같은 도메인·프로세스의 테이블 2~3개에서 시작할 수도 있다.
- 한 후보에 두 모드 성격이 섞이면 더 강한 근거 쪽 모드로 정한다.

## 읽을 문서

| 때 | 함께 읽는 문서 |
|---|---|
| 시작할 때 | `skills/question-generation/references/local-values.md` |
| top-down 후보를 직접 모을 때 | `okf/wiki/patterns/fraud/index.md`, `okf/real-cases/index.md`, `okf/real-cases/patterns.md`, `okf/domains/index.md` |
| bottom-up 후보를 직접 모을 때 | `skills/question-generation/references/table-exploration.md`, `okf/wiki/patterns/anomaly/index.md`, `okf/domains/index.md`, `okf/schemas/<OWNER>/index.md` |
| 도메인 page 를 볼 때 | `okf/domains/<slug>.md` |
| 테이블을 확인할 때 | `okf/schemas/<OWNER>/index.md`, 해당 테이블 문서 |
| 용어·중복을 확인할 때 | `okf/glossary/index.md`, `okf/wiki/examples/index.md` |
| drilldown 할 때 | 「drilldown」 절의 「읽을 문서」 |

테이블 문서에서 보는 것:

- frontmatter: `table_name`, `query_name`, `owner`, `table_class`(거래 테이블 `transaction` 우선), `table_type`(종합리포트 > 리포트 > 마스터 > 인터페이스 > 기준정보), `row_count`, `size`, `business_area`, `business_detail`, `tags`(`class:transaction`, `has:amount`, `has:soft-delete`, `has:validity-period`, `domain:*`)
- `# Schema`: 컬럼 물리명, 한글명, 타입, 키, 코드·참조
- `# Joins`: 관련 테이블과 연결 키(있으면)
- `# T2S 힌트`: 기준 날짜, 플레이스홀더, 주의할 점. 참고만 하고 질문 문장에는 쓰지 않는다

## 절차

1. **요청 해석**: 모드, 도메인, 기간, 테이블 이름, 위험 주제, 키워드를 정한다.
   - 기간 기본값: 직전 달 말일까지 12개월. 시작일과 종료일을 모두 포함한다. 예: 2026-11-19 실행 → `2025-11-01` ~ `2026-10-31`.
   - 범위 기본값: 전체 도메인. 도메인을 말하면 `okf/wiki/index.md` 에서 맞는 도메인으로 좁힌다. `bottom-up` 이고 도메인이 없으면 거래 테이블이 많은 도메인 2개를 먼저 본다.
   - 테이블 이름이 있으면 `bottom-up` 은 그 테이블을 시작 테이블로 쓰고, `top-down` 은 그 테이블을 쓰는 후보만 모은다.
   - 모드가 없으면 top-down 후보와 bottom-up 후보를 각각 1개 이상 만들고 점수로 고른다. 요청에 「테이블」·「컬럼」·「구조」·「중복」·「누락」·「짝 없음」·「불일치」가 있으면 bottom-up 을 먼저 본다.
   - 여기서 정한 조건은 끝까지 바꾸지 않는다.

2. **후보 모으기**: 모드에 맞는 sub-agent 에 맡긴다. 그 sub-agent 의 「입력」대로 넘긴다. 모드가 없으면 `question-scout` 와 `question-table-scout` 에 모두 맡기고 후보를 합친다. 직접 모을 때는 위 「읽을 문서」를 따른다.

3. **후보 정리**: 모드마다 3~5개. 후보마다 아래를 채운다.
   - 위험 주제 한 문장, 모드, 도메인(slug·이름), 업무 프로세스
   - 패턴 ID·이름 1~3개
   - 실제 사고 1~2건(CS 번호, 있으면)
   - 거래 테이블(`query_name`, `table_type`, `class:transaction`, `has:amount`, `row_count`)
   - 기준 날짜 컬럼·형식, 금액 컬럼, 업무 키
   - bottom-up 이면 시작 테이블, 관련 테이블, 확장 경로, 단일·복수
   - 근거 문서 경로

4. **점수로 1건 고르기**: 아래 「점수 기준」으로 매긴다. 0점 기준이 있는 후보는 뺀다. 가장 높은 1건을 고른다.

5. **후보 확인**: 고른 1건을 `question-grounder` 에 맡긴다. 아래 「질문 문장 규칙」도 함께 넘긴다. 돌려받은 결과로 점수를 다시 매긴다. 「불가」이거나 0점 기준이 생기면 다음 후보로 바꿔 한 번 더 맡긴다.

6. **질문 쓰기**: 아래 「질문 문장 규칙」과 모드별 문형으로 질문 1건을 쓴다.

7. **최종 확인**: 질문이 점수 기준과 문장 규칙을 지키는지 본다. 데이터로 답할 수 없으면 다음 후보로 바꿔 5부터 다시 한다. 후보 바꾸기는 5와 합쳐 1번까지다. 그래도 없으면 「질문 생성 불가」로 출력하고 사유를 적는다.

8. **출력**: 아래 「출력 JSON」 1개.

## 판정

| 상황 | 처리 |
|---|---|
| 범위에 맞는 패턴·도메인·테이블이 없음 | 질문 생성 불가(사유: <무엇> 없음) |
| 패턴이 「도메인 없음」·「불가(그래프)」·「범위 밖」·「쓰지 않음」 | 그 후보를 뺀다 |
| 거래 테이블이 아님 / `row_count = 0` / 기준 날짜 없음 | 그 후보를 뺀다 |
| 금액 컬럼이 없음 | 금액 규모를 말하는 후보는 뺀다. 건수·비율만 보는 후보는 데이터 점수 1점으로 남긴다 |
| bottom-up 테이블 컬럼으로 P-1xx 조건을 만들 수 없음 | 그 후보를 뺀다 |
| bottom-up 테이블 사이의 연결 키를 문서에서 찾지 못함 | 단일 테이블 후보로 줄이거나 뺀다 |
| `okf/wiki/examples/index.md` 의 기존·승인 시나리오와 감사 포인트가 같음 | 그 후보를 뺀다 |
| 특정 업체·사원·문서번호를 넣어야만 성립 | 그 후보를 뺀다 |
| 모든 후보가 빠짐 | 질문 생성 불가 + 빠진 사유 목록 |

## 점수 기준 (10점)

| 기준 | 2점 | 1점 | 0점(후보에서 뺌) |
|---|---|---|---|
| 위험 연결 | 모드에 맞는 패턴 2개 이상과 근거(실제 사고 또는 테이블 구조)가 같은 업무 흐름에 연결됨 | 패턴 1개, 또는 근거만 있음 | 패턴·근거 연결 없음 |
| 데이터 | `class:transaction`, `has:amount`, `row_count > 0`, 기준 날짜·금액 컬럼 확인 | 네 가지 중 일부만 확인 | 거래 테이블·금액·기준 날짜 중 하나라도 없음 |
| 범위 | 도메인 1개, 업무 프로세스, 기간이 모두 있음 | 도메인만 있음 | 범위를 정할 수 없음 |
| 탐지 | 조건 단위(비율·간격·중복·연결된 기록 없음·순서 등)로 쓸 수 있고 특정 대상을 지목하지 않음 | 일부만 조건으로 쓸 수 있음 | 특정 업체·사원·문서번호를 지목해야만 성립 |
| 새로움 | `okf/wiki/examples/index.md` 의 기존·승인 시나리오와 감사 포인트가 다름 | 비슷하지만 조건이 다름 | 감사 포인트가 같음 |

모드별로 보는 근거:

- **top-down**: 위험 연결은 `okf/wiki/patterns/fraud/index.md` 의 패턴 2개 이상과 `okf/real-cases/patterns.md` 의 사례. 데이터는 테이블 문서 frontmatter 와 `# Schema`.
- **bottom-up**: 위험 연결은 `okf/wiki/patterns/anomaly/index.md` 에서 붙인 패턴 2개 이상과 `okf/wiki/risk-interpretation.md` 의 감사 위험. 데이터는 시작 테이블의 frontmatter 와 기준 날짜·금액·업무 키 컬럼, 복수 테이블이면 연결 키. `row_count`·`size` 가 크고 금액 컬럼이 있는 후보를 먼저 본다. 금액이 없으면 데이터 점수는 1점을 넘지 않는다.

점수가 같으면 아래 순서로 고른다.

1. 매출 인식 위험(가공 매출, 기간 말 부풀리기, 실적 조작)이 걸린 후보
2. 근거가 더 구체적인 후보(top-down 은 실제 사고, bottom-up 은 테이블 구조·관련 테이블)
3. 패턴 수가 많은 후보
4. `row_count`·`size` 가 큰 후보

## 질문 문장 규칙

1. 한국어 업무 문장 1~3개. 한 문장으로 끝내는 것을 먼저 한다.
2. 기간을 넣는다. 날짜 또는 「최근 12개월」.
3. 도메인과 업무 프로세스를 업무 용어로 넣는다.
4. 위험 주제 또는 이상 신호를 넣는다.
5. 의도(무엇을 찾고 싶은지)를 넣는다.
6. 물리 테이블명·컬럼명·SQL·코드값을 쓰지 않는다.
7. 특정 업체·거래처·사원·문서번호를 쓰지 않는다.
8. 근거 없는 숫자 기준을 쓰지 않는다. 필요하면 「기준 초과」·「평소보다 큰」처럼 쓴다. 구체 기준은 시나리오 생성 에이전트가 데이터를 보고 정한다.
9. 어느 모드인지 드러나게 쓴다.
10. bottom-up 의 시작·관련 테이블과 확장 경로는 질문에 쓰지 않고 `bottom_up` 에만 둔다.
11. `{정상 업무}` 는 `okf/wiki/normal-patterns.md` 에서 확인한 것만 쓴다. 확인하지 못하면 그 구절을 뺀다.

모드별 문형:

- `top-down`: {기간} {도메인}의 {프로세스} 영역에서 {위험 주제}가 의심되는 거래를 찾을 수 있는 부정 위험 시나리오를 만들어줘. {패턴 단서}를 함께 보고, {정상 업무}는 제외해줘.
- `bottom-up`: {기간} {도메인}의 {프로세스}에서 {시작 테이블의 컬럼·키에서 보이는 이상 신호}가 나타나는 거래를 찾아줘. {관련 테이블과의 관계}를 함께 보고, {정상 업무}는 제외해줘.

나쁜 질문:

- 「<테이블명>에서 <컬럼명>이 이상한 걸 찾아줘」: 물리명이 드러나고 위험 주제가 없음
- 「A업체가 부정했는지 봐줘」: 특정 업체를 지목함
- 「매출 데이터를 분석해줘」: 범위·기간·의도를 알 수 없음
- 「금액이 1억 초과인 건을 찾아줘」: 근거 없는 숫자 기준
- 「어제 데이터에서 이상한 걸 찾아줘」: 기간·도메인·프로세스를 알 수 없음

좋은 질문과 출력 예시는 `skills/question-generation/references/local-values.md` 에 있다.

## 출력 JSON

JSON 코드블록 1개만 둔다. 앞에 사람이 읽는 한 줄 `질문: <question 과 같은 문장>` 을 두어도 된다.

모드별로 들어가는 필드(이 순서대로):

| 모드 | 필드 |
|---|---|
| `top-down` | `schema_version`, `question`, `mode`, `scope`, `risk_theme`, `intent`, `expected_finding`, `grounding`, `data_evidence`, `variant`, `duplicate_check`, `score`, `rationale` |
| `bottom-up` | `schema_version`, `question`, `mode`, `scope`, `risk_theme`, `intent`, `expected_finding`, `grounding`, `bottom_up`, `variant`, `duplicate_check`, `score`, `rationale` |

필드 규칙:

| 필드 | 규칙 |
|---|---|
| `schema_version` | `"1.0"` |
| `question` | 위 「질문 문장 규칙」을 지킨 질문 |
| `mode` | `"top-down"` / `"bottom-up"` |
| `scope.domain_name`, `scope.domain_slug` | `okf/domains/index.md` 의 이름·slug |
| `scope.business_area` | 업무 영역 |
| `scope.business_process` | 도메인 page 의 프로세스 단계 |
| `scope.period` | `start`, `end`(`YYYY-MM-DD`, 둘 다 포함), `basis`(예: 「직전 달 말일까지 12개월」) |
| `risk_theme.summary` | 위험 주제 한 문장 |
| `risk_theme.pattern_ids`, `pattern_names` | top-down 은 P-0xx, bottom-up 은 P-1xx |
| `risk_theme.real_cases` | CS 번호. 없으면 `[]` |
| `intent` | 무엇을 찾는지 한 문장 |
| `expected_finding` | 찾을 것으로 보는 거래 한 문장 |
| `grounding.primary_table` | 테이블 문서의 `query_name`(`OWNER.TABLE`) |
| `grounding.table_type` | 테이블 문서의 `table_type` |
| `grounding.row_basis` | 업무 키 또는 1행 단위. 그레인 문제(중복 등)가 있으면 함께 적는다 |
| `grounding.date_column`, `amount_column` | 물리 컬럼명. 없으면 `null` |
| `grounding.supporting_tables` | 함께 쓰는 테이블 `OWNER.TABLE`. 없으면 `[]` |
| `grounding.key_terms` | `{"term": 업무 용어, "column": "TABLE.COLUMN"}` 목록. 컬럼이 여러 개면 `/` 로 잇는다. 없으면 `[]` |
| `data_evidence` | `null` |
| `bottom_up` | 아래 `bottom_up` 객체 |
| `variant` | `null`. variant 모드의 JSON 은 `skills/question-generation/references/variant.md` 에 있다 |
| `duplicate_check` | `checked_against`(`"okf/wiki/examples/index.md"`), `similar_scenarios`(이름과 다른 점, 없으면 `[]`), `result`(`"신규"` / `"유사"` / `"미확인"`) |
| `score` | `total`(0~10), `criteria`: `risk_link`, `data_feasibility`, `scope_clarity`, `detectability`, `novelty`(각 0~2) |
| `rationale` | 1~3문장. 왜 좋은 질문인지, 쓴 근거 문서, 시나리오 생성 에이전트가 확인할 것 |

`bottom_up` 객체(bottom-up 만):

| 필드 | 규칙 |
|---|---|
| `starting_tables` | 시작 테이블 1~3개, `OWNER.TABLE` |
| `related_tables` | 넓혀서 본 테이블. 없으면 `[]` |
| `expansion_path` | 시작 테이블 컬럼 → 관련 테이블 컬럼. 단일 테이블이면 그 안에서 본 컬럼과 신호 |
| `table_scope` | `"단일"` / `"복수"` |
| `rationale` | 이 테이블 구조에서 어떻게 질문으로 넓혔는지 |

- 확인하지 못한 값은 지어내지 않고 `null` 또는 `[]` 로 둔다.
- bottom-up 인데 `bottom_up` 이 없거나 시작 테이블·컬럼이 문서와 맞지 않으면 그 후보는 쓰지 않는다.

질문을 만들지 못하면 JSON 대신 아래를 출력한다.

```text
질문 생성 불가
- 사유: <한 줄>
- 빠진 후보: <후보 — 사유> (여러 건이면 줄마다)
```

## drilldown

검증을 통과한 시나리오를 더 좁힐지 판단하고, 좁힌다면 드릴다운 패턴(`okf/wiki/patterns/perspective/`)을 골라 **드릴다운 질문 1건**을 만든다. 드릴다운 질문은 원본 질의를 그대로 두고, 이전 드릴다운에서 더한 관점과 이번에 더할 관점을 덧붙인 것이다. 새 시나리오를 만드는 일이 아니다. 드릴다운 결과는 늘 직전 단계 결과의 일부다.

순서: **입력 확인 → 멈춤 확인 → 사고 유형 판단 → 패턴 고르기 → 진행 판단 → 더할 관점 정하기 → 질문 쓰기 → JSON 출력**

드릴다운 패턴은 순서대로 밟는 단계가 아니다. 드릴다운 1회마다 누적 보고서를 보고 지금 가장 적절한 패턴을 1~3개 골라 한 번에 쓴다. 다음 드릴다운을 할지, 어느 패턴으로 할지는 그 결과를 보고 다시 정한다.

### 입력

- `question`: 원본 질의
- `stage`: `{name: 단계명, number: 단계 번호(2~5), max_depth: 최대 드릴다운 횟수}`. `max_depth` 가 없거나 1보다 작으면 4로 본다.
- `base_scenario_md`: 직전 단계까지의 누적 보고서 전문. 1단계 보고서, 그 뒤 드릴다운 절들(「## <관점> 관점으로 더 확인」), 맨 끝 「부록: 시나리오 JSON」 순서다. 부록의 SQL 은 지금까지 걸린 조건을 읽는 데만 쓴다.

### 읽을 문서

| 때 | 문서 |
|---|---|
| 시작할 때 | `okf/wiki/patterns/perspective/index.md` |
| 패턴을 고른 뒤 | 고른 패턴 파일 `okf/wiki/patterns/perspective/DP-xxx.md` (3개까지) |
| 패턴의 「확인 필요」 테이블·컬럼, 정상 업무를 확인할 때 | `okf/schemas/<OWNER>/tables/<TABLE>.md`, `okf/wiki/normal-patterns.md` |

- 고르지 않은 패턴 파일은 읽지 않는다. 후보는 index 의 패턴 목록과 「먼저 보는 패턴」으로 고른다.

### 멈춤 확인

아래 가운데 하나라도 맞으면 판단하지 않고 `proceed=false` 와 `reason` 을 낸다.

| 상황 | `reason` |
|---|---|
| `question` 이 비었음, `stage` 가 객체가 아님, `stage.number` 가 정수가 아니거나 2보다 작음, `base_scenario_md` 가 비었음 | 「입력 오류 — <무엇이 틀렸는지>」 |
| `stage.number` 가 `max_depth + 1` 보다 큼 | 「최대 드릴다운 횟수(<max_depth>회)를 모두 사용함 — <stage.number - 1>단계까지의 결과로 종료」 |
| 보고서의 검증 결과가 PASS 가 아님 | 「검증을 통과하지 않은 시나리오」 |
| 보고서의 직전 드릴다운 단계 상태가 정상이 아님 | 「직전 드릴다운 단계가 정상으로 끝나지 않음」 |
| 현재 누적 0건 | 「현재 누적 0건」 |

### 사고 유형 판단

1. 보고서의 감사 포인트(시나리오 개요·점검 항목)와 사고 수법으로 7개 유형 가운데 하나를 정한다(index 2절).
2. 보고서에 부정 패턴(P-0xx)이 있으면 index 3절 대응표를 출발점으로 쓴다. 감사 포인트와 맞지 않으면 감사 포인트를 따른다.
3. 유형은 드릴다운마다 다시 본다. 직전 드릴다운 결과가 다른 유형을 가리키면(예: 과다지급이 특정 담당자·거래선 조합에 몰림 → ②) 바꾼다.
4. 유형을 정할 수 없으면 `proceed=false`, `reason` 「사고 유형을 정하지 못함」.

### 패턴 고르기

1. 보고서의 이전 드릴다운 절에서 이미 쓴 관점과 그때의 건수 변화를 본다. 이미 쓴 패턴은 다시 고르지 않는다.
2. index 2절에서 정한 유형의 「먼저 보는 패턴」부터 본다. index 4절 목록의 관점·답하는 질문을 보고서 신호와 맞춰 후보 3~5개를 정한다.
3. index 5절 묶기 규칙으로 1~3개를 고른다. 직전 결과가 누적 대사로 나온 초과이고 진위 판별(DP-002 ~ DP-007)을 아직 하지 않았으면 진위 판별을 먼저 고른다.
4. 고른 패턴 파일을 읽는다. 「고르는 때」에 맞는 신호가 보고서에 없거나 「고르지 않는 때」에 해당하면 뺀다.
5. 고른 패턴의 「확인 필요」 테이블·컬럼이 보고서나 OKF 테이블 문서로 확인되는지 본다. 확인되지 않아 데이터로 답할 수 없는 패턴은 뺀다.
6. 남은 패턴이 없으면 `proceed=false`, `reason` 「쓸 수 있는 드릴다운 패턴이 없음 — <뺀 패턴과 사유>」.

### 진행 판단

건수만 보고 정하지 않는다. 「어떤 조건으로 몇 건이 나왔는가」가 감사에서 무엇을 뜻하는지 보고 정한다. 전체 건수가 보고서에 있으면 비율도 본다.

더 좁힌다(`proceed=true`):

- 조건이 넓어서 정상 업무 거래나 표기상 이상(정산 단위, 거래선 기준, 수량 표기)이 많이 섞였을 것 같다.
- 결과 안에 금액대·시기·사람·같은 대상의 반복 같은 쏠림이 보이고, 고른 패턴으로 좁히면 의심 대상이 뚜렷해진다.
- 범위가 넓어서 감사인이 무엇부터 봐야 할지 알기 어렵다.

멈춘다(`proceed=false`):

- 고른 패턴의 「멈춤 기준」에 이미 해당한다.
- 조건 자체가 심각해서 잡힌 건이 모두 감사 대상이다. 예: 이중 지급, 증빙 중복, 승인 전 지급, 요청자와 승인자가 같은 사람.
- 이미 구체적인 대상(지급 문서, 거래선·담당자 조합)으로 모여서 감사인이 한 건씩 바로 볼 수 있다.
- 관점을 더했을 때 이전 결과와 다른 새 정보가 나온다고 구체적으로 말할 수 없다.

멈춤은 실패가 아니다. 지금까지 검증을 통과한 결과가 그대로 포털에 등록된다.

### 더할 관점 정하기

1. 직전 단계 결과를 전제로 한다. 이미 더한 관점과 좁혀진 대상을 버리고 1단계부터 다시 생각하지 않는다.
2. 고른 패턴의 「추출 로직」을 업무 말로 옮겨 이번 관점의 내용으로 삼는다. 여러 패턴을 골랐으면 같은 대상(같은 거래선·제품, 같은 지급 문서)에 함께 거는 한 관점으로 합친다.
3. 넓히지 않는다. 패턴의 대상 범위는 「좁힘」 또는 「대조」뿐이다. 기간 늘리기, 조건 풀기, 직전 결과 밖의 건 보기는 하지 않는다.
4. 임계값은 패턴의 「임계 조정」을 따라 좁히는 쪽으로만 말한다. 숫자를 새로 정하지 않는다.
5. 패턴의 「정상 예외」와 `okf/wiki/normal-patterns.md` 의 정상 업무는 제외할 것으로 넣는다.
6. 특정 업체·국가 값으로 고정하지 않는다. 특정 업체·사원 코드를 나열하지도 않는다. 대상을 드러낸 조건(같은 대상의 반복 횟수, 서로 다른 업체의 같은 값, 비율, 마스터의 같은 속성)으로 말한다.
7. `stage.name` 은 이름표다. 이름에 묶이지 말고 지금 시나리오에 가장 의미 있는 패턴을 고른다. `stage` 에 다른 재료(대상 목록, 후보 테이블 등)가 있으면 먼저 쓴다.

### 드릴다운 질문 규칙

드릴다운 질문은 원본 질의에 관점을 쌓아 가는 글이다. 모양(`{ }` 를 채운다):

~~~text
{원본 질의 그대로}
위 질의에 더해, 아래 관점으로 결과를 더 좁고 깊게 봐 줘.
- {이전 드릴다운 관점 1}: {그때 더한 내용 한 문장}
- {이전 드릴다운 관점 2}: {그때 더한 내용 한 문장}
- {이번 관점(perspective)}: {이번에 남길 건과 함께 볼 것 1~2문장}. {정상 예외}는 제외해 줘.
~~~

1. 원본 질의(입력 `question`)는 고치지 않고 첫 줄에 그대로 둔다.
2. 이전 드릴다운 관점은 보고서의 「## <관점> 관점으로 더 확인」 절에서 순서대로 가져와 한 줄씩 그대로 둔다. 첫 드릴다운이면 이 줄들은 없다.
3. 이번 관점은 맨 끝 한 줄이다. 줄 머리는 `perspective` 와 같게 쓴다. 고른 패턴의 「질문 단서」를 직전 결과에 맞춰 고쳐 쓰고, 패턴을 여러 개 골랐으면 한 줄로 합친다.
4. 이번 관점 줄에는 무엇을 남기는지(좁히는 조건)와 정상 예외를 쓴다.
5. 덧붙이는 줄에는 물리 테이블명·컬럼명·SQL·코드값·패턴 번호를 쓰지 않는다. 원본 질의에 있던 표현은 그대로 둔다.
6. 특정 업체·거래처·사원·문서번호를 쓰지 않는다.
7. 근거 없는 숫자 기준을 쓰지 않는다. 「평소보다 큰」·「분포 상위」처럼 쓴다.

### 출력 JSON

JSON 코드블록 1개만 둔다. 아래 6개 외의 필드는 넣지 않는다.

| 필드 | `proceed=true` | `proceed=false` |
|---|---|---|
| `proceed` | `true` | `false` |
| `accident_type` | 정한 사고 유형. 예: `"④ 검증부실/과다지급"` | 정했으면 그 유형, 못 정했으면 `""` |
| `pattern_ids` | 고른 패턴 1~3개. 예: `["DP-002", "DP-004"]` | `[]` |
| `perspective` | 이번에 더하는 관점. 10~30자 명사구. 「관점」으로 끝내지 않는다. 보고서에 「## <perspective> 관점으로 더 확인」 제목으로 들어간다 | `""` |
| `question` | 위 「드릴다운 질문 규칙」을 지킨 질문 1건. 줄바꿈은 `\n` | `""` |
| `reason` | `""` | 한 문장. 멈추는 이유 |

- `proceed=true` 인데 `perspective` 나 `question` 을 쓸 수 없으면 `proceed=false` 로 내고 `reason` 에 「관점을 정하지 못함」을 쓴다.
- 출력 예시는 `skills/question-generation/references/local-values.md` 에 있다.
