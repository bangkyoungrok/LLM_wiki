# variant

기존 시나리오 1건을 바꿔 variant 감사 질문 1건과 그 JSON 을 만든다. sub-agent 없이 main-agent 가 직접 한다.

순서: **시나리오 고르기 → md 읽기 → 바꾸기 → 질문 쓰기 → JSON 출력**

## 시나리오 고르기

- 입력에 시나리오 ID 가 있으면 `okf/references/scenarios/<ID>.md` 를 읽는다.
- ID 가 없으면 `okf/references/scenarios/summary.md` 의 「시나리오 목록」 표에서 요청의 도메인·테이블·키워드에 가장 맞는 1건을 고른다. 단서가 없으면 아무거나 1건을 고른다.
- `okf/references/scenarios/summary.md` 는 시나리오를 고를 때만 쓴다.

## md 에서 쓰는 것

| md 의 내용 | 쓰는 법 |
|---|---|
| 맨 위 표(감사 포인트, 모집단, 단계, 실행 제약) | 기존 시나리오가 무엇을 찾는지 잡는다 |
| 사용 테이블 | 모두 그대로 쓴다 |
| 조건 인벤토리 | 바꿀 조건을 여기서 고른다. 「변형」 칸의 등급을 지킨다 |
| 조건용 파생 컬럼, 단계별 필터, SQL 구조 스켈레톤 | 조건이 어디에 걸리는지 본다 |
| 공식 단계, 점검 항목에서 나온 변형 축 | 조건의 업무 뜻과 제외 사유를 본다 |
| 「변형」 절의 제약 | 지킨다. 이 변형에 걸리는 것은 `cautions` 에 옮긴다 |
| 「변형」 절의 슬롯, 대표 조합, 추가·교체 후보 | 예시다. 참고만 하고 그대로 옮기지 않는다 |

## 바꾸는 규칙

1. 감사 포인트는 이어받고, 탐지 조건이 달라지게 바꾼다. 문장만 바꾼 것은 변형이 아니다.
2. 바꾸는 방법은 값 변경, 조건 추가, 조건 제거, 조건 교체, 테이블 조인이다. 여러 개를 함께 써도 된다.
3. 사용 테이블은 하나도 빼지 않는다.
4. 「정의」 등급 조건은 빼지 않는다. 「구조」 등급 조건은 값을 바꾸지 않는다.
5. 새 테이블을 조인해도 된다. 연결 키는 `okf/schemas/<OWNER>/tables/<TABLE>.md` 에서 확인한 것만 쓴다. 확인하지 못하면 조인하지 않는다.
6. 코드값은 md 나 테이블 문서에 있는 것만 쓴다. 숫자는 md 에 있는 값을 쓰거나, 새 기준이면 「더 짧게」·「평소보다 큰」처럼 방향만 쓴다.
7. 조건을 빈틈없이 다 정하지 않는다. 무엇을 왜 바꿨는지가 드러나면 된다. 정확한 값과 SQL 은 시나리오 생성 에이전트가 정한다.
8. 특정 업체·사원·문서번호로 조건을 고정하지 않는다.

## 판정

| 상황 | 처리 |
|---|---|
| 입력 ID 의 md 가 없음 | 질문 생성 불가(사유: 기존 시나리오 md 없음) |
| 감사 포인트와 탐지 조건이 기존 시나리오와 같은 변형만 나옴 | 질문 생성 불가(사유: 변형 아님) |

## 질문 쓰기

`skills/question-generation/SKILL.md` 의 「질문 문장 규칙」을 따른다. 기존 시나리오 이름과 바꾼 내용은 업무 말로 쓰고, 조건 ID·물리명은 `variant` 객체에만 둔다.

문형: 기존 「{기존 시나리오 이름}」 시나리오를 변형해서, {기간} {업무}의 {프로세스}에서 {바꾼 뒤 찾으려는 것}을 찾아줘. {바꾼 것}을 적용하고, {유지한 것}은 유지해줘.

## 출력 JSON

출력 형식(JSON 코드블록 1개, 앞의 `질문:` 한 줄)과 질문 생성 불가 형식은 `skills/question-generation/SKILL.md` 「출력 JSON」을 따른다.

필드(이 순서대로): `schema_version`, `question`, `mode`, `scope`, `intent`, `expected_finding`, `variant`, `rationale`

| 필드 | 규칙 |
|---|---|
| `schema_version` | `"1.0"` |
| `question` | 위 문형으로 쓴 질문 |
| `mode` | `"variant"` |
| `scope.domain_name`, `scope.business_process` | md 맨 위 표 「모집단」의 업무와 프로세스 |
| `scope.period` | `skills/question-generation/SKILL.md` 의 `scope.period` 규칙과 같다 |
| `intent` | 바꿔서 무엇을 찾으려는지 한 문장 |
| `expected_finding` | 찾을 것으로 보는 거래 한 문장 |
| `variant` | 아래 `variant` 객체 |
| `rationale` | 1~3문장. 왜 이렇게 바꿨는지, 읽은 문서 경로, 시나리오 생성 에이전트가 확인할 것 |

`variant` 객체:

| 필드 | 규칙 |
|---|---|
| `base_scenario` | `scenario_id`, `scenario_nm`, `audit_point`(md 의 감사 포인트), `tables`(md 사용 테이블 전부, 적힌 이름 그대로) |
| `variant_nm` | 변형 후 시나리오 이름. 아래 「변형 후 이름」대로 쓴다 |
| `summary` | 무엇을 어떻게 바꿨는지 한 문장 |
| `changes` | 바꾼 것마다 `type`, `condition_id`, `from`, `to`, `reason` 을 담은 객체 목록 |
| `kept_conditions` | 그대로 둔 조건. `"<조건 ID> <뜻 한 줄>"` 목록 |
| `joined_tables` | 새로 조인한 테이블마다 `table`(테이블 문서의 `query_name`), `join_key`, `reason`. 없으면 `[]` |
| `cautions` | md 의 실행 제약·제약 가운데 이 변형에 걸리는 것. 없으면 `[]` |

`changes` 의 각 값:

- `type`: `"값 변경"` / `"조건 추가"` / `"조건 제거"` / `"조건 교체"` / `"테이블 조인"`
- `condition_id`: 조건 인벤토리의 ID. 새 조건이면 `null`
- `from`: 바꾸기 전 조건. 새 조건이면 `null`
- `to`: 바꾼 뒤 조건. 제거면 `null`
- `reason`: 왜 바꿨는지 한 문장

## 변형 후 이름

- 무엇을 찾는지 보이게 40자 이하로 쓴다. 예: 「공고 전에 견적서가 발행된 단독 참여 견적」
- 기간, 테이블·컬럼 이름, 조건 ID 는 넣지 않는다.
- 부당, 허위, 특혜, 몰아주기, 조작처럼 의도를 단정하는 말은 쓰지 않는다.
- 질문 단계에서 붙이는 이름이다. 최종 이름은 시나리오 생성 에이전트가 정한다.
