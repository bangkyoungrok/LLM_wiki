# 출력 명세

출력은 **Markdown 1개**다. 맨 끝 `## verdict JSON` 절의 ```json 코드블록 1개를 파싱한 결과가 입출력 명세서의 출력 변수다. 그 앞에는 사람이 읽는 **판정(표)** 과 **검증 요약** 절이 있다.

## 1. 파싱 규칙

- 출력 안의 ```json 코드블록은 **정확히 1개**이며 `## verdict JSON` 절에 둔다. 심판 JSON, 표본 행, 예시, 판정(표), 검증 요약 등은 json 블록으로 쓰지 않는다 (표 또는 일반 텍스트로).
- JSON 은 UTF-8, 키 순서는 아래 2절 순서를 지킨다. 주석·후행 쉼표를 쓰지 않는다.
- 최상위 `verdicts` 배열은 항상 쓴다. 검증 대상이 1건이므로 배열에 객체 1개를 담는다.

## 2. verdict JSON 스키마

최상위는 `verdicts` 배열이고, 각 요소는 검증 대상 시나리오 1건을 담은 객체다. 값이 null 이어도 키는 항상 모두 쓴다.

```json
{"verdicts":[{"scenario_name":"...","verdict":"INVALID","total_score":5.3,"dimensions":{"논리적 타당성":6.0,"데이터 근거성":2.0,"감사 실효성":6.0,"커버리지":8.0,"복잡성":6.7},"row_count":null,"reason":"..."}]}
```

| 키 | 타입 | 규칙 | 후속 사용 |
|---|---|---|---|
| `verdicts` | object[] | 검증 대상 1건이면 객체 1개. 항상 배열로 쓴다 | |
| `verdicts[].scenario_name` | string | 입력 받은 이름 그대로. 입력이 없으면 `""` | |
| `verdicts[].verdict` | string | `PASS` / `INVALID` / `DUPLICATE` / `DB_UNAVAILABLE` (SKILL.md 판정표) | 드릴다운 판단 `base_validation.verdict` |
| `verdicts[].total_score` | number \| null | 0.0~10.0, 소수 첫째 자리(차원 가중합). 채점하지 않았으면 null | 드릴다운 판단 `base_validation.total_score` |
| `verdicts[].dimensions` | object \| null | 키 5개 고정: `논리적 타당성`, `데이터 근거성`, `감사 실효성`, `커버리지`, `복잡성`. 값은 차원 점수(0.0~10.0, 소수 첫째 자리): 나머지 4차원은 O ÷ 5 × 10, 복잡성은 O ÷ 6 × 10. 종합 점수와는 별개(종합은 가중합). 채점하지 않았으면 null | |
| `verdicts[].row_count` | integer \| null | 시나리오 SQL 실행의 실제(도구가 자르기 전) 행 수(6절). 실행하지 않거나 행 수 확인 불가면 null | |
| `verdicts[].reason` | string | 판정 근거 1~2문장. 3절 형식 | 드릴다운 판단 `base_validation.reason` |

> 데이터 사전 대조(`bundle_check`), 실측 증거(`evidence`), 중복 판별 대상(`duplicate_of`)은 JSON 에 담지 않는다. 이 내용은 각각 Markdown 의 「데이터 사전 대조」(2절), 「SQL 실행 결과」(3절), 「중복 판별」(6절) 절에 표·문장으로 둔다.

## 3. reason / evidence 작성 형식

### 컬럼명 표기

- `reason`, `evidence`, 항목별 판정 근거, 검증 요약 등 출력의 모든 문장에서 물리 컬럼명을 쓸 때는 **`물리명(한글명)`** 형식으로 쓴다 (예: `REQ_NO(견적입찰번호)`).
- 한글명은 데이터 사전 문서 `# Schema` 표의 컬럼명·코멘트에서 확인한다. 데이터 사전 문서가 없어 확인하지 못하면 물리명 단독으로 쓴다.
- 한글명 단독으로 쓰지 않는다.

### reason

| verdict | 형식 | 예 |
|---|---|---|
| `PASS` | `<탐지 요지> <N>건, 26개 항목 중 <K>개 충족(종합 <S>). 기존 시나리오와 2축 이상 일치 없음.` | `낙찰 총액이 요청가와 1% 이내 일치 + 경쟁 견적 절반 이상 ±10% 근접 1,061건, 26개 항목 중 23개 충족(종합 9.0). 기존 시나리오와 2축 이상 일치 없음.` |
| `DUPLICATE` | `26개 항목 중 <K>개 충족(종합 <S>). 기존 <ID>(<이름>)와 <축> 일치로 중복.` | `26개 항목 중 20개 충족(종합 6.6). 기존 SSA2405003(들러리 견적 업체 반복 참여)와 위험 상황·대상 일치로 중복.` |
| `INVALID` (점수 미달) | `26개 항목 중 <K>개 충족. 통과 기준인 6.0점 미만으로 중복 검토 미수행.` (가장 큰 감점 원인 1개를 앞에 덧붙일 수 있다) | `26개 항목 중 17개 충족. 통과 기준인 6.0점 미만으로 중복 검토 미수행.` |
| `INVALID` (입력 누락) | `입력 누락: <항목>. 채점 미수행.` | |
| `DB_UNAVAILABLE` | `DB 실행 불가로 채점·중복 검토 미수행.` | |

### evidence

- 실측 수치를 먼저 쓴다: 행 수, 모집단 건수, 분포 등. 실측이 없으면 "미실행(사유)"이라고 쓴다.
- 판정에 영향을 준 데이터 사전·SQL 문제를 덧붙인다 (예: "데이터 사전에 없는 객체 DEMO.DEMO_BID", "정상 업무 제외 조건 없음").
- `DB_UNAVAILABLE` 이면 오류 원문을 그대로 쓴다.
- PII 값은 쓰지 않는다.

## 4. 숫자·문자 형식

- 점수는 number 로 쓴다 (`5.6`, 문자열 `"5.6"` 금지). 정수 점수도 `8.0` 처럼 소수 첫째 자리까지.
- JSON 문자열 안의 큰따옴표·역슬래시는 이스케이프한다.
- 건수는 Markdown 본문에서는 천 단위 쉼표(`1,061건`), JSON 의 정수 필드에서는 쉼표 없이(`1061`).

## 5. Markdown 구성

절 제목과 순서를 고정한다. 해당 사항이 없는 절도 지우지 않고 "없음" 또는 "미수행(사유)"을 쓴다.

```
# 유효성 검증 결과: <scenario_name>

> 판정: <verdict> · 종합 <S> / 10 · 행 수 <N>행 · 중복: <없음 | ID(이름) | 미수행>
> 검증일: <YYYY-MM-DD>

## 1. 입력 확인
- scenario_name: <입력 값>
- 형식 점검: 이상 없음 | <바인드 변수·주석·세미콜론·FETCH FIRST 기록>

## 2. 데이터 사전 대조
| 점검 | 결과 | 근거 |
(SELECT 전용, 객체명, 컬럼, 조인, 코드값, 삭제 플래그, PII 행)

## 3. SQL 실행 결과
- 실행: 성공 | 0행 | 오류 | 미실행(<사유>) | DB 연결 불가
- 행 수: <N>행 | 확인 불가
- 오류: 없음 | <오류 원문>
(표본 최대 5행을 Markdown 표로. PII 마스킹)

## 4. 보조 증거
| 질의 목적 | 결과 요약 |

## 5. 채점
### 5.1 차원 점수
| 차원 | 가중치 | O 개수 | 점수(0~10) | 반영 점수(점수 × 가중치) |
(5행 + 종합 행. 종합 = 반영 점수 합, 0~10)
### 5.2 항목별 판정
| id | 판정 | 근거 |
(L1~L5, D1~D5, E1~E5, C1~C5, X1~X6 의 26행)

## 6. 중복 판별
- 미수행(<사유>) | 후보 목록 표 + 후보별 3축 비교 표 + 판정

## 7. 확인 필요
- 없음 | <정보 부족 후보, 문서로 확정 못 한 컬럼 의미 등>

## 판정
| 키 | 값 |
(verdicts 6개 필드 + 데이터 사전 대조·중복·근거 상세 3행. 아래 「판정(표)」 규칙)

## 검증 요약
(3~6줄의 짧은 문단 또는 불릿. 아래 「검증 요약」 규칙)

## verdict JSON
(```json 코드블록 1개)
```

### 판정(표)

- `## 판정` 절은 verdict JSON (`verdicts` 배열의 1개 객체)을 **표**로 보여준다 (json 블록은 1개만 허용되므로 사람이 읽는 판정 결과는 표로 쓴다).
- 표는 2열(`키` / `값`)이며 키 순서는 verdicts 요소 필드 순서(`scenario_name`, `verdict`, `total_score`, `dimensions`, `row_count`, `reason`)와 같다.
- `값` 열의 규칙:
  - `scenario_name`, `verdict`, `reason` 은 값을 그대로 쓴다.
  - `total_score` 는 number 로 쓴다.
  - `dimensions` 는 5개 차원 점수를 한 줄로 나열한다 (예: `논리적 타당성 6.0 · 데이터 근거성 2.0 · 감사 실효성 6.0 · 커버리지 8.0 · 복잡성 6.0`). null 이면 `미채점`.
  - `row_count` 는 정수로, null 이면 `확인 불가`.
- verdicts 6개 필드 이후에 다음 **상세 3행**을 추가해, JSON 에 담지 않는 결과를 사람도 표에서 바로 본다:
  - `evidence`: 실측 수치와 핵심 발견 1~3문장 (3절 evidence 규칙).
  - `duplicate_of`: `DUPLICATE` 가 아니면 `없음`, 아니면 `<scenario_id>(<scenario_nm>, 일치 축: <matched_axes>)`.
  - `bundle_check`: 5개 키 요약 (예: `객체 위반: DEMO.DEMO_BID / 컬럼 누락 없음 / 조인 위험 없음 / PII 없음 / SELECT 전용 통과`). 대조하지 못했으면 `미대조`.

### 검증 요약

- verdict JSON 보다 앞에 두고, **3~6줄로 간략**하게 쓴다. 길게 쓰지 않는다.
- 반드시 넣을 것: 판정(1줄), 종합 점수와 큰 감점·통과 근거(1~2줄), 실행 결과(행 수 등, 1줄), 필요 시 확인 필요한 사항(1줄).
- 컬럼명은 `물리명(한글명)` 형식으로 쓴다.
- 1~7절에 이미 있는 내용을 그대로 다시 나열하지 말고, 읽는 사람이 결론을 바로 grasp할 수 있게 **풀어서** 요약한다.

## 6. 실행 결과 기록

시나리오 SQL 실행 기록이다. JSON 에는 실제 행 수만 `verdicts[].row_count` 로 담고, 나머지 실행 요지는 `## 3. SQL 실행 결과` 절에 쓴다.

| 기록 | 위치 | 규칙 |
|---|---|---|
| 실행 상태 | `## 3` 의 `- 실행:` | `success`(1행 이상) / `empty`(0행) / `error`(쿼리 오류) / `미실행(<사유>)` |
| 실제 행 수 | `## 3` 의 `- 행 수:` 과 `verdicts[].row_count` | **도구가 자르기 전의 실제 행 수**(X6 행 수 적절성 판정 기준). 돌아온 행이 10행보다 적으면 그 값, 10행이면 `COUNT(*)` 로 감싸 센 값. 미실행·오류면 null / 확인 불가 |
| 표본 | `## 3` 표 | 핵심 컬럼 값을 담은 표본 몇 행. PII 컬럼 값은 `"***"` |
| 오류 원문 | `## 3` 의 `- 오류:` | 오류가 없으면 "없음" |
