# 출력 명세

출력은 **Markdown 1개**다. 맨 끝 `## verdict JSON` 절의 ```json 코드블록 1개를 파싱한 결과가 입출력 명세서의 출력 변수다. 그 앞에는 사람이 읽는 **판정(표)** 과 **검증 요약** 절이 있다.

## 1. 파싱 규칙

- 출력 안의 ```json 코드블록은 **정확히 1개**이며 `## verdict JSON` 절에 둔다. 표본 행, 확인 질의, 판정(표), 검증 요약 등은 json 블록으로 쓰지 않는다 (표 또는 일반 텍스트로).
- JSON 은 UTF-8, 키 순서는 아래 「verdict JSON 스키마」 순서를 지킨다. 주석·후행 쉼표를 쓰지 않는다.
- 최상위 `verdicts` 배열은 항상 쓴다. 검증 대상이 1건이므로 배열에 객체 1개를 담는다.

## 2. verdict JSON 스키마

최상위는 `verdicts` 배열이고, 각 요소는 검증 대상 시나리오 1건을 담은 객체다. 값이 null 이어도 키는 항상 모두 쓴다.

```json
{"verdicts":[{"scenario_name":"...","verdict":"PASS","row_count":1250,"remaining_rows":312,"explained_conditions":[{"condition":"같은 달에 취소 행이 있어 합치면 0","rows":905},{"condition":"관계사 간 거래","rows":33}],"reason":"..."}]}
```

| 키 | 타입 | 규칙 | 후속 사용 |
|---|---|---|---|
| `verdicts` | object[] | 검증 대상 1건이면 객체 1개. 항상 배열로 쓴다 | |
| `verdicts[].scenario_name` | string | 입력 받은 이름 그대로. 입력이 없으면 `""` | |
| `verdicts[].verdict` | string | `PASS` / `EXPLAINED` / `INVALID` / `DUPLICATE` / `DB_UNAVAILABLE` (SKILL.md 판정표) | 드릴다운 판단 `base_validation.verdict` |
| `verdicts[].row_count` | integer \| null | 시나리오 SQL 실행의 실제(도구가 자르기 전) 행 수(「실행 결과 기록」). 실행하지 않거나 행 수 확인 불가면 null | 드릴다운 판단 `base_validation.row_count` |
| `verdicts[].remaining_rows` | integer \| null | 모든 소명 조건을 뺀 남은 행 수. 모두 소명되면 0. 소명 확인을 하지 않았으면 null | 드릴다운 판단 `base_validation.remaining_rows` |
| `verdicts[].explained_conditions` | object[] | 소명 조건마다 `condition`(업무 말 한 줄, 물리명·SQL·코드값 없이)과 `rows`(소명된 행 수). 없으면 `[]` | 드릴다운 판단 `base_validation.explained_conditions` |
| `verdicts[].reason` | string | 판정 근거 1~2문장. 「reason」 형식 | 드릴다운 판단 `base_validation.reason` |

> 데이터 사전 대조(`bundle_check`), 소명 경로별 확인 내용, 중복 판별 대상(`duplicate_of`)은 JSON 에 담지 않는다. 이 내용은 각각 Markdown 의 「데이터 사전 대조」, 「소명 확인」, 「중복 판별」 절에 표·문장으로 둔다.

## 3. reason / evidence 작성 형식

### 문장 쓰는 법

`reason`, evidence, 「감사인이 확인할 소명 자료」, 「확인 필요」, 검증 요약은 처음 보는 사람이 한 번에 읽고 이해하도록 풀어서 쓴다.

- 줄임말, 내부 이름, 다른 곳을 가리키는 말(「위 경로와 같음」, 「케이스A 같이」, 「~컬럼에서」)을 쓰지 않는다. 무엇을 확인했고 무엇을 알 수 없었는지 문장으로 쓴다.
  - 예: `시나리오 결과에 입찰을 다시 찾을 번호가 없어서, 연결된 승인 기록이 있는지 확인하지 못했다.`
- 테이블·컬럼 이름은 어느 테이블의 어느 컬럼에 어떤 조건을 걸었는지 설명할 때만 쓴다.
  - 예: `입찰 테이블 DEMO.DEMO_BID 의 BID_TYPE(입찰유형)이 단가계약('F')인 행은 고정 단가라 견적가가 같은 것이 정상이다.`
- 소명 경로 이름은 그대로 써도 된다.

### 컬럼명 표기

- `reason` 을 뺀 출력의 모든 문장에서 물리 컬럼명을 쓸 때는 **`물리명(한글명)`** 형식으로 쓴다 (예: `REQ_NO(견적입찰번호)`).
- 한글명은 데이터 사전 문서 `# Schema` 표의 컬럼명·코멘트에서 확인한다. 데이터 사전 문서가 없어 확인하지 못하면 물리명 단독으로 쓴다.
- 한글명 단독으로 쓰지 않는다.
- `explained_conditions[].condition` 에는 물리명을 쓰지 않는다.

### reason

| verdict | 형식 | 예 |
|---|---|---|
| `PASS` | `<탐지 요지> <N>건 중 <K>건 소명, <M>건 소명 안 됨(소명 경로 모두 확인 \| 소명 경로 <J>개는 확인하지 못함). 기존 시나리오와 2축 이상 일치 없음.` | `요청가와 1% 이내로 일치한 낙찰 1,250건 중 938건 소명, 312건 소명 안 됨(소명 경로 모두 확인). 기존 시나리오와 2축 이상 일치 없음.` |
| `EXPLAINED` | `<N>건 모두 소명: <주된 소명 조건>.` | `410,564건 모두 소명: 배치 계정 하나가 같은 시각에 일괄 등록한 적재 행.` |
| `DUPLICATE` | `<M>건 소명 안 됨. 기존 <ID>(<이름>)와 <축> 일치로 중복.` | `312건 소명 안 됨. 기존 SSA2405003(들러리 견적 업체 반복 참여)와 위험 상황·대상 일치로 중복.` |
| `INVALID` (입력) | `입력 누락: <항목>.` 또는 `형식 오류: <내용>.` | |
| `INVALID` (번들·실행) | `<위반 또는 오류 요지>로 미실행.` 또는 `실행 오류: <오류 요지>.` | `데이터 사전에 없는 객체 DEMO.DEMO_BID 로 미실행.` |
| `INVALID` (0행) | `결과 0건으로 소명할 대상 없음.` | |
| `DB_UNAVAILABLE` | `DB 실행 불가로 소명 확인·중복 검토 미수행.` | |

### evidence

- 실측 수치를 먼저 쓴다: 행 수, 소명된 행 수, 남은 행 수. 실측이 없으면 "미실행(사유)"이라고 쓴다.
- 판정에 영향을 준 데이터 사전·SQL 문제를 덧붙인다 (예: "데이터 사전에 없는 객체 DEMO.DEMO_BID").
- `DB_UNAVAILABLE` 이면 오류 원문을 그대로 쓴다.
- PII 값은 쓰지 않는다.

## 4. 숫자·문자 형식

- JSON 문자열 안의 큰따옴표·역슬래시는 이스케이프한다.
- 건수는 Markdown 본문에서는 천 단위 쉼표(`1,061건`), JSON 의 정수 필드에서는 쉼표 없이(`1061`).

절 제목과 순서를 고정한다. 해당 사항이 없는 절도 지우지 않고 "없음" 또는 "미수행(사유)"을 쓴다.

### 판정(표)

- `## 판정` 절은 verdict JSON (`verdicts` 배열의 1개 객체)을 **표**로 보여준다 (json 블록은 1개만 허용되므로 사람이 읽는 판정 결과는 표로 쓴다).
- 표는 2열(`키` / `값`)이며 키 순서는 verdicts 요소 필드 순서(`scenario_name`, `verdict`, `row_count`, `remaining_rows`, `explained_conditions`, `reason`)와 같다.
- `값` 열의 규칙:
  - `scenario_name`, `verdict`, `reason` 은 값을 그대로 쓴다.
  - `row_count`, `remaining_rows` 는 정수로, null 이면 `확인 불가`.
  - `explained_conditions` 는 `<condition> <rows>행` 을 ` · ` 로 이어 한 줄로 쓴다. 없으면 `없음`.
- verdicts 6개 필드 이후에 다음 **상세 3행**을 추가해, JSON 에 담지 않는 결과를 사람도 표에서 바로 본다:
  - `evidence`: 실측 수치와 핵심 발견 1~3문장 (「evidence」 규칙).
  - `duplicate_of`: `DUPLICATE` 가 아니면 `없음`, 아니면 `<scenario_id>(<scenario_nm>, 일치 축: <matched_axes>)`.
  - `bundle_check`: 5개 키 요약 (예: `객체 위반: DEMO.DEMO_BID / 컬럼 누락 없음 / 조인 위험 없음 / PII 없음 / SELECT 전용 통과`). 대조하지 못했으면 `미대조`.

### 검증 요약

- verdict JSON 보다 앞에 두고, **3~6줄로 간략**하게 쓴다. 길게 쓰지 않는다.
- 반드시 넣을 것: 판정(1줄), 소명된 것과 남은 것(1~2줄), 실행 결과(행 수 등, 1줄), 필요 시 감사인이 확인할 소명 자료나 확인 필요한 사항(1줄).
- 컬럼명은 `물리명(한글명)` 형식으로 쓴다.
- 앞 절에 이미 있는 내용을 그대로 다시 나열하지 말고, 읽는 사람이 결론을 바로 알 수 있게 **풀어서** 요약한다.

## 6. 실행 결과 기록

시나리오 SQL 실행 기록이다. JSON 에는 실제 행 수만 `verdicts[].row_count` 로 담고, 나머지 실행 요지는 `## 3. SQL 실행 결과` 절에 쓴다.

| 기록 | 위치 | 규칙 |
|---|---|---|
| 실행 상태 | `## 3` 의 `- 실행:` | `success`(1행 이상) / `empty`(0행) / `error`(쿼리 오류) / `미실행(<사유>)` |
| 실제 행 수 | `## 3` 의 `- 행 수:` 과 `verdicts[].row_count` | **도구가 자르기 전의 실제 행 수**. 돌아온 행이 10행보다 적으면 그 값, 10행이면 `COUNT(*)` 로 감싸 센 값. 미실행·오류면 null / 확인 불가 |
| 표본 | `## 3` 표 | 핵심 컬럼 값을 담은 표본 몇 행. PII 컬럼 값은 `"***"` |
| 오류 원문 | `## 3` 의 `- 오류:` | 오류가 없으면 "없음" |
