# audit-report

생성 skill 이 확정한 시나리오를 감사팀이 읽을 보고서로 쓴다. 읽는 사람이 「무슨 나쁜 일을 잡으려고, 어떤 순서로 찾았고, 무엇이 나왔는지」를 위에서부터 차례로 이해할 수 있게 쓴다. 맨 위 「점검 조건」과 「조회된 결과」만 봐도 무엇을 걸렀고 무엇이 나왔는지 알 수 있어야 한다. 보고서는 결과와 근거만 담는다. 마지막 「시나리오 JSON」은 다음 단계 프로그램이 읽으므로 형식을 바꾸지 않는다.

## 하는 순서

1. **재료 모으기**: 앞 단계에서 확정한 것(시나리오 이름, 시나리오 SQL, 건수 확인 결과 `HIT_CNT`·`KEY_CNT`·`HIT_AMT`·`HIT_ACTOR_CNT`, 대상별·월별 집계, 테이블·조인, 패턴·가설·이상치, 기준 시나리오와 바꾼 조건, 조건값을 정한 근거, 읽은 문서, 가정)을 그대로 가져온다. 다시 정하거나 다시 조회하지 않는다.
2. **결과 수**: 결과 수는 시나리오 탐색에서 확인한 `HIT_CNT` 다. 0이거나 확인하지 못했으면 「유효한 시나리오가 없을 때」 형식으로 쓴다.
3. **쓰기**: 아래 「보고서 틀」에 「모드별 값」을 넣어 쓰고 「쓰는 말」을 지킨다.
4. **점검**: 「내보내기 전 점검」을 하나씩 확인하고, 어긋나면 고친 뒤 낸다.

````markdown
## 1. 점검 시나리오

- <이 시나리오가 무엇을 찾는지 한 문장>
- <어떤 조건으로 좁혀 무엇을 확인 대상으로 추리는지 한 문장. 모드: 1절>

## 2. 점검 목적

- <잡으려는 나쁜 행위: 누가 무엇을 어떻게 해서, 겉으로는 어떻게 보이게 만드는지>
- <그렇게 해서 무엇을 얻거나 회사에 어떤 손실을 주는지>
- <그런 행위가 왜 지금 절차에서 걸러지지 않기 쉬운지>
- 따라서 <그 행위>를 잡기 위해, **<무엇이 무엇과 맞는지>** 확인함.

## 3. 이상 거래를 찾아낸 과정

1. <무엇을 모았는지 한 줄. 제외한 것은 괄호에 짧게>
2. <그중 무엇을 골라냈는지 한 줄>
3. <어떻게 더 좁혔는지 한 줄>
4. <무엇 기준으로 모아 정리했는지 한 줄>

## 4. 발견 이상 데이터 및 사례

**전체 규모**

- <모집단 가운데 몇 곳·몇 개·얼마가 걸렸는지. 금액은 굵게>
- <몇 개 법인·대상에 걸쳐 있고, 어디에 몰려 있는지>
- <건수·반복 정도의 분포를 한 줄로>

**두드러진 사례**

- **<법인코드(법인명)> · <대상 이름> (<대상 코드>)**
  - <수와 **금액**, 그리고 왜 두드러지는지(가장 큼, 반복, 다른 정도가 뚜렷함 등)>
  - <담당자·기간 등 확인에 필요한 사실>
  - <확인할 점 한 줄>
<2~4개>

## 시나리오 JSON

```json
{"scenario_name":"<시나리오 이름>","scenario_sql":"<시나리오 SQL>"}
```
````

- 5절 표에는 시나리오 SQL 이 쓰는 테이블을 빠짐없이 적는다.
- 점검 조건은 시나리오 SQL 의 조건(기간, 걸러 낸 것, 경계값, 묶어서 넘긴 기준)과 하나씩 맞춘다. SQL 에 없는 조건을 쓰지 않고, SQL 의 조건을 빠뜨리지 않는다. 순서는 넓은 조건에서 좁은 조건으로 쓴다.
- 조회된 결과는 결과 전체를 요약한 통계 표 하나다. 머리 1행과 값 1행의 2행 표로 쓰고, 대상별 목록이나 순위를 쓰지 않는다.
- 열은 「분석 기간」을 맨 앞에 두고, 결과 수(`HIT_CNT`)와 금액(`HIT_AMT`, 금액이 없는 시나리오면 뺀다), 그리고 걸린 대상의 수(사람·업체·법인·제품 등, `HIT_ACTOR_CNT` 와 시나리오 탐색에서 센 값)를 이어 쓴다. 어떤 대상 수를 넣을지는 시나리오에 맞게 고르고, 조회하지 않은 값은 넣지 않는다.
- 열 이름은 업무 말로 쓴다(예: 「셀아웃 실적」, 「할인 차액 합계」, 「법인 수」).
- 시나리오 JSON 은 한 줄 JSON 객체 하나다. 키는 `scenario_name`, `scenario_sql` 두 개뿐이고 `{`, `}`, `:`, `,` 앞뒤에 공백이 없다.
- `scenario_name` 은 제목의 이름과 같고, `scenario_sql` 은 확정한 시나리오 SQL 을 글자 그대로 넣는다. SQL 안의 큰따옴표는 `\"`, 역슬래시는 `\\`.

**유효한 시나리오가 없을 때**: 보고서와 JSON 없이 아래만 쓴다.

```markdown
# <범위> 시나리오 설계 결과: 유효한 시나리오 없음

- 범위: <범위> / 기간: <시작일> ~ <마지막 포함일> / 작성일: <오늘 날짜>
- <2~3문장: 무엇을 살펴봤고(가설, 이상치, 변형) 왜 시나리오가 되지 못했는지>
```

## 쓰는 말

**문장**

- 개조식으로 쓰되 칸 안의 문장이 이어지게 쓴다. 2절은 「이런 행위가 있고 → 이렇게 보이게 해서 → 이래서 놓치기 쉬움 → 따라서 이것을 확인함」 순서다.
- 2절은 통제의 빈틈보다 **잡으려는 나쁜 행위와 그 의도**가 먼저 읽히게 쓴다.
- 3절은 읽는 사람이 「이런 순서로 걸러서 찾아냈구나」를 알 수 있게, 단계마다 한 줄로 쓴다. 기간, 코드값, 조인 키, 경계값의 근거 같은 세부는 쓰지 않는다.
- 한 줄에 사실 하나만, 짧게 쓴다. 용어를 쪼개 나열하지 않는다.
- 문장 끝은 「~함」, 「~임」, 「~됨」, 「~필요」로 맞춘다.
- 단정하지 않는다. 「부정이다」가 아니라 「의심 신호」, 「확인 대상」, 「~했을 가능성」으로 쓴다.
- 한국어로 쓰고 영어 문장이나 한자어를 섞지 않는다(물리명, SQL, 고유 기술 용어만 예외).

**점검 조건과 참고**

- 점검 조건은 「~인 실적」, 「~한 제품」처럼 명사로 끝나는 짧고 자연스러운 문장으로 쓴다. 기간·비율·금액 같은 기준값은 문장 안에 넣는다(예: 「2025년 11월부터 2026년 10월까지 들어온 셀아웃 실적」, 「원가보다 40% 이상 싸게 판 프로모션 제품」).
- 참고는 「모드별 값」의 참고 가운데 결과를 읽는 데 꼭 필요한 것만 1~3줄로 쓴다. 「틀릴 수 있음」, 「부정으로 확정하지 않음」처럼 미리 방어하는 문장은 쓰지 않는다.

**물리명은 정해진 곳에만**

- 점검 조건, 조회된 결과, 1~4절, 참고는 업무 말로만 쓴다. 테이블·컬럼 물리명, 코드값, SQL 조건식을 쓰지 않는다. 법인·업체 같은 대상의 코드는 「대상 표기」대로 쓴다.
- 물리명은 5절 표와 부록에만 쓴다.
- 시스템·도구 말을 업무 말로 바꾼다: 플레이스홀더 → 임시값, I/F 적재 중복 → 시스템 중복 저장, modified z·MAD·`TARGET_VAL` → 평소 범위.

**대상 표기**

- 법인·업체·거래선·담당자는 조회 결과의 코드와 이름을 그대로 쓴다(「C550(SIEL)」, 「업체 GMRAS.A. (FA5D1S)」). 가리거나 ■■ 로 바꾸지 않는다.

**단위**

- 「행」, 「건」을 습관적으로 붙이지 않는다. 세는 대상에 맞는 단위를 쓴다: 기기 ~대, 청구 ~회, 업체 ~곳, 법인 ~개, EO ~개, 기록 ~개.
- 「건」은 사고 하나, 문서 하나처럼 정말 한 건인 대상에만 쓴다.

**숫자와 기간**

- 숫자는 조회 결과에 있는 값만 쓴다. 같은 대상의 숫자는 모든 절에서 같은 값이다.
- 본문의 금액은 「약 14.8억 원」, 「약 1,314만 달러」처럼 읽기 쉽게 줄여 쓰고, 정확한 값은 「조회된 결과」 표에만 쓴다. 금액은 천 단위 쉼표를 붙인다.
- 통화는 테이블 문서나 컬럼 이름으로 확인한 것만 붙인다. 확인하지 못했으면 단위 없이 쓰고 참고에 「금액 통화 확인 필요」를 적는다.
- 기간은 실제로 포함되는 마지막 날로 쓴다. SQL 이 「다음 날 미만」(`< '20261201'`)으로 썼으면 「~ 2026-11-30」이다. 「조회된 결과」의 분석 기간과 시나리오 SQL 의 기간이 같은 날짜 범위를 가리켜야 한다. 데이터가 그 날짜보다 먼저 끝나면 기간은 그대로 두고 참고에 「데이터는 <날짜>까지 있음」을 한 줄 적는다.

**쓰지 않는 것**

- DB 접속 정보.
- sub-agent 이름, 도구 이름과 호출 횟수, skill 문서 경로, 테이블을 고른 과정(참고만 한 테이블과 그 이유는 A-1 에 쓴다), 건수 확인 질의와 그 열 이름(`HIT_CNT` 등), 「확인해 보니」식 묘사.
- 시나리오 JSON 밖의 SQL·JSON. 읽은 문서 경로는 A-1 에만 쓴다.

## 내보내기 전 점검

형식만 본다. 조건·기간·이름은 다시 검토하지 않는다.

1. 답변이 보고서 `#` 제목으로 시작하고 「시나리오 JSON」으로 끝난다(유효한 시나리오가 없으면 그 형식대로 끝난다). 앞뒤에 다른 문장이 없다.
2. 제목(모드 표시 2개와 업무 영역), 머리말 2줄(작성일, 상태), 「점검 조건」, 「조회된 결과」, `## 1.` ~ `## 5.`, 「※ 참고」, `## 부록`(A-1), `## 시나리오 JSON` 이 이 순서로 있다. 머리말에 분석 기간이 없고 상태 줄에 결과 수·금액이 없다. 「조회된 결과」는 2행 표다.
3. 1절은 2줄, 3절은 단계마다 한 줄이다. 점검 조건이 시나리오 SQL 의 조건과 하나씩 맞다.
4. 2절이 잡으려는 나쁜 행위로 시작하고 「따라서 ~확인함」으로 끝난다.
5. 점검 조건, 1~4절, 참고에 테이블·컬럼 물리명, 코드값, SQL 조건식, 작업 과정 서술이 없다.
6. 「조회된 결과」 표와 4절 전체 규모의 결과 수가 `HIT_CNT` 와 같고, 같은 대상의 숫자·금액이 조회된 결과, 4절에서 같다.
7. 「조회된 결과」의 분석 기간과 시나리오 SQL 의 기간이 같은 날짜 범위를 가리킨다.
8. 「행」, 「건」이 세는 대상과 맞지 않게 쓰인 곳이 없다.
9. 5절 표에 시나리오 SQL 이 쓰는 테이블이 모두 있다. A-1 의 출발점이 1·2절과 맞다.
10. SQL 은 시나리오 JSON 의 `scenario_sql` 에만 있고 확정한 시나리오 SQL 과 글자 하나까지 같다. 시나리오 이름이 제목과 같고, 숫자 기준 없이 풀어 쓴 문장이다. 시나리오 JSON 이 맨 마지막에 한 번만 있다.
