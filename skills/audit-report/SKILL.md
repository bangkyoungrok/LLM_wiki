# audit-report

생성 skill 이 확정한 시나리오를 감사팀이 읽을 보고서로 쓴다. 보고서는 결과와 근거만 담는다. 마지막 「부록: 시나리오 JSON」은 다음 단계 프로그램이 읽으므로 형식을 바꾸지 않는다.

## 하는 순서

1. **재료 모으기**: 앞 단계에서 확정한 것(시나리오 이름, 시나리오 SQL, 건수·금액, 대상 집계, 테이블·조인, 패턴·가설·이상치, 기준 시나리오와 바꾼 조건, 조건값을 정한 근거, 읽은 문서, 가정)을 그대로 가져온다. 다시 정하거나 다시 조회하지 않는다.
2. **건수**: 결과 건수는 시나리오 탐색에서 확인한 `HIT_CNT` 다. 0건이거나 확인하지 못했으면 「유효한 시나리오가 없을 때」 형식으로 쓴다.
3. **쓰기**: 아래 「보고서 틀」에 「모드별 값」을 넣어 쓰고 「쓰는 말」을 지킨다. 형식이 헷갈리면 `skills/audit-report/references/example.md` 를 본다.
4. **점검**: 「내보내기 전 점검」을 하나씩 확인하고, 어긋나면 고친 뒤 낸다.

보고서 뒤에 아래를 차례로 붙인다.

- `## 만들지 못한 시나리오`: 「시나리오 | 사유」 표. 없으면 「없음」. 사유는 업무 말로 한 줄.
- `## 부수 발견`(Bottom-up 만): 「ID | 내용 | 심각도」 표. 없으면 「없음」. 심각도 상은 감사 질문에 답할 수 없게 만드는 것(연결 키 없음, 적재 중단), 중은 분석을 잘못 읽게 만드는 것(임시값, 중복 적재), 하는 영향이 작은 것.
- `## 부록: 시나리오 JSON`(확정된 시나리오가 있을 때만, 항상 마지막):

````markdown
## 부록: 시나리오 JSON

```json
{"scenario_name":"<시나리오 이름>","scenario_sql":"<시나리오 SQL>"}
```
````

  - 한 줄 JSON 객체 하나. 키는 `scenario_name`, `scenario_sql` 두 개뿐이고 `{`, `}`, `:`, `,` 앞뒤에 공백이 없다.
  - `scenario_name` 은 제목의 이름과, `scenario_sql` 은 A-2 의 SQL 과 글자 하나까지 같다. SQL 안의 큰따옴표는 `\"`, 역슬래시는 `\\`.

**유효한 시나리오가 없을 때**: 보고서와 JSON 없이 아래만 쓴다. Bottom-up 은 뒤에 「부수 발견」도 쓴다.

```markdown
# <범위> 시나리오 설계 결과: 유효한 시나리오 없음

- 범위: <범위> / 기간: <시작일> ~ <종료일> / 작성일: <오늘 날짜>
- <2~3문장: 무엇을 살펴봤고 왜 시나리오가 되지 못했는지>

## 만들지 못한 시나리오
| 시나리오 | 사유 |
|---|---|
```

## 쓰는 말

- 각 절의 첫 문장이 그 절의 결론이다. 한 문장에 한 가지만, 짧게 쓴다.
- 업무 말로 쓴다. 1.1, 5, 7.1, 8, 9, 11절에는 테이블·컬럼 물리명을 쓰지 않는다. 물리명은 틀이 자리를 둔 곳(참고한 근거, 1.2, 2절, 3.1·4절 조건식, 6절, 7.2, 10.1, 부록)에만 쓴다. 컬럼은 「거래선코드(`SOLD_TO`)」처럼 쓴다.
- 컬럼의 이름·타입·한글명은 그 컬럼이 속한 테이블 문서 `# Schema` 에서 그대로 옮긴다.
- 통계·도구 용어(modified z, MAD, `TARGET_VAL` 같은 내부 열 이름)를 쓰지 않는다. 「평소 범위」처럼 풀어 쓴다.
- 숫자는 조회 결과에 있는 값만 쓰고 새로 계산하지 않는다. 숫자에는 단위와 비교 대상을 붙인다(「64건」, 「21%(전체 3%)」). 같은 대상의 숫자는 어느 절에서나 같은 값으로 쓴다. 금액은 원 단위에 천 단위 쉼표만 붙인다.
- 단정하지 않는다. 「부정이다」가 아니라 「~했을 가능성을 본다」, 「부정 의심」, 「확인 필요」로 쓴다.
- 사람 이름과 계정은 가린다(`Y***.P***`). 한국어로 쓰고 영어 문장이나 한자어를 섞지 않는다(물리명, SQL, 고유 기술 용어만 예외).
- 쓰지 않는 것: sub-agent 이름, 도구 이름과 호출 횟수, skill 문서 경로, 테이블을 고른 과정(참고만 한 테이블과 그 이유는 「참고한 근거」에 쓴다), 건수 확인 질의와 그 열 이름(`HIT_CNT` 등), 「확인해 보니」식 묘사, 1~11절의 SQL·JSON, 표본 행의 값, DB 접속 정보. 읽은 문서 경로는 「참고한 근거」에만 쓴다.

## 내보내기 전 점검

형식만 본다. 조건·기간·이름은 다시 검토하지 않는다.

1. 답변이 보고서 `#` 제목으로 시작하고 마지막 절(시나리오 JSON, 없으면 「만들지 못한 시나리오」나 「부수 발견」)로 끝난다. 앞뒤에 다른 문장이 없다.
2. 제목(표시 2개), 메타 4줄, 참고한 근거, `## 1.` ~ `## 11.`, 부록(A-1, A-2)이 이 순서로 있다. 참고한 근거의 패턴·테이블이 3.1·A-1 과 맞다.
3. 메타의 결과 건수와 3.1 제목의 건수가 `HIT_CNT` 와 같다.
4. 1.1, 5, 7.1, 8, 9, 11절에 물리명이 없고, 작업 과정 서술이 없다.
5. SQL 블록은 A-2 에만 있고, 확정한 시나리오 SQL 과 글자 하나까지 같다.
6. 3.1 의 L1~L3 와 4절 조건식이 A-2 SQL 의 WHERE 조건과 같다(경계값, 비교 방향, 기간). 「맥락 조건」으로 적은 L3 는 예외.
7. 시나리오 이름이 제목과 시나리오 JSON 에서 같다.
8. 같은 대상의 건수·금액이 3.1, 5, 8, 11절과 「만들지 못한 시나리오」에서 같다.
9. 「만들지 못한 시나리오」가 보고서 뒤에 한 번 있고, Bottom-up 은 그 다음에 「부수 발견」이 있다.
10. 「부록: 시나리오 JSON」이 마지막에 한 번만 있다. 확정된 시나리오가 없으면 이 절이 없다.
