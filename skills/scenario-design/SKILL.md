# scenario-design

미리 정한 Process 를 순서대로 수행한다. 순서는 **부정 패턴 선택 → 스키마 대입 → 부정 패턴 조합으로 후보 → 선별 → 시험 → 제출**이다. 이 SKILL.md 를 읽은 다음 응답에서 `skills/scenario-design/references/query-writing.md`, `skills/scenario-design/references/answer-format.md`, `wiki/patterns/index.md`, `wiki/criteria.md`, `wiki/examples/index.md`, `wiki/normal-patterns.md` 를 `agent_studio_project_view` 로 함께 읽는다. 이전 감사 SQL 이 첨부되었으면 수정 Process 를 따른다.

## Process

1. 요청 해석: 범위, 기간, 건수 N 을 정한다(기본값은 `AGENTS.md` 1절). 범위 표현은 `wiki/index.md` 의 도메인 대응으로 OKF 도메인에 대응시키고, 대응이 안 되는 표현은 `okf/domains/index.md` 로 찾는다(표현이 3개 이상이거나 그래도 못 찾으면 `term-grounding`). 기간은 `AGENTS.md` 11절대로 시작일(포함)과 종료일(미포함)을 정한다. **여기서 정한 범위·기간·건수와 요청 해석은 확정이다.** 이후 단계에서 사용자 요청 문장을 다시 인용하거나 해석하지 않는다.
2. 패턴 선택: `wiki/patterns/index.md` 3절에서 「OKF 후보 도메인」이 범위의 도메인과 겹치고 「SQL 대입」이 「가능」인 부정 패턴을 고른다. 범위가 전체면 「가능」인 패턴을 모두 고른다. 「도메인 없음」·「불가(그래프)」 패턴은 고르지 않는다(사용자가 이름으로 요청했으면 만들지 않은 후보에 사유를 적는다). 고른 패턴이 3×N 개(기본 9개)보다 많으면 `wiki/patterns/index.md` 5절 조합 단서에 든 패턴, 매출 인식 위험, 「대입 예시」 있음 순으로 앞에서 3×N 개만 남긴다.
3. 대입과 조합(문서만, SQL 없음):
   1. 대입: 고른 패턴의 page 와 후보 도메인 page 를 한 응답에서 함께 읽는다. 패턴마다 모집단과 예외 조건에 필요한 테이블을 `sql-query` 「테이블 선택」 절대로 고른다(`sql-query` 를 아직 읽지 않았으면 이때 `skill_view` 로 읽는다). 고른 테이블 문서에서(한 작업에서 10개까지) 기준 날짜와 형식, 업무 키, 행위자 컬럼(업체·거래선·담당자), 금액, 코드값(T2S 힌트·`okf/codes/`), PII 컬럼, 조인 문서를 정한다. 필요한 테이블을 찾지 못한 패턴은 만들지 않은 후보로 옮긴다(사유: <무엇> 테이블을 찾지 못함).
   2. 조합: 대입한 패턴을 `wiki/patterns/index.md` 4절 규칙(같은 행, 집단→행, 흐름→행)으로 2~3개씩 묶는다. 5절 조합 단서와 패턴 page 의 「조합 단서」를 먼저 보고, 그 밖에도 같은 테이블·같은 행위자 컬럼·조인 문서로 이어지면 묶을 수 있다. 여러 방향의 조합을 문서로 넓게 검토하되, 조합마다 유형, 주 패턴(모집단을 정하는 패턴), 패턴별 조건 조각 초안(`query-writing.md` 5절), 쓸 테이블·조인을 적는다. 패턴 하나는 여러 조합에 들어갈 수 있다.
   3. 중복 회피: 기존 시나리오(`okf/references/scenarios.md`)와 감사 포인트가 같은 조합은 뺀다(사유: 기존 시나리오 <이름> 과 같음).
   4. 단일 후보: 어떤 조합에도 들지 못한 패턴은 「단일」 후보로 둔다. 조합 후보가 N 개보다 적을 때만 4단계 선별에 넣는다.
4. 선별과 위임: `wiki/criteria.md` 로 점수를 매기고 0점 기준이 있는 후보를 뺀 뒤 상위 N 개를 고른다. 후보마다 `scenario-worker` 1개를 `project_sub_task` 로 맡긴다(한 응답 최대 5개). 후보가 1개여도 맡긴다. 위임 prompt 에는 아래를 모두 적는다(subagent 는 이 대화를 보지 못한다). worker 가 값 확인·문서 탐색에 질의를 쓰지 않도록 3단계에서 확인한 사실을 빠짐없이 넣는다.
   1) 목표: 「<부정 패턴 조합> 을 <도메인> 에 대입해 시나리오 SQL 을 쓰고 조합 점검까지 해서 scenario-worker 반환 형식으로 돌려준다」
   2) 부정 패턴 조합: 패턴 ID·이름, 조합 유형, 주 패턴, 패턴 page 경로, 패턴별 조건 조각 초안, 넣을 고의성 신호 후보
   3) 확인된 사실: 테이블 `query_name`·유형과 문서 경로(「테이블 선택」 기록 줄 포함), 기준 날짜 컬럼과 형식, 업무 키, 행위자 컬럼, 금액 컬럼(통화), 코드값과 그 근거, 데이터 정리 조건(soft-delete, 플레이스홀더), PII 컬럼, 쓸 조인과 근거(조인 문서 경로와 조건). 확인하지 못한 항목은 「미확인」으로 적는다
   4) 기간: 시작일(포함)과 종료일(미포함) 날짜(YYYY-MM-DD)
   5) 모집단, 예외 조건, 정상 업무 제외, 기준 날짜(패턴 page 의 대입 예시가 있으면 그대로, 없으면 3단계에서 정한 것)
   6) 이름 규칙(「<대상> 중 <조건 1>·<조건 2>인 건」, 대입 예시가 있으면 그 규칙), 이미 쓴 시나리오 이름(겹치지 않게)
   7) 참고할 기존 시나리오나 예제가 있으면 그 경로
   8) 상한: `sql_run` 5회 이하, 반환 2,500 token 이하
5. 결과 정리: 「통과」로 돌아온 후보는 시나리오로, 「실패」는 만들지 않은 후보로 옮긴다(사유는 worker 가 적은 것). worker 가 조합을 줄여 돌려주면(조합 축소) 줄인 조합을 그 시나리오의 조합으로 쓴다. 실패한 후보가 있고 아직 위임하지 않은 후보가 남아 있으면, 실패한 수만큼 다음 순위 후보를 1회만 더 맡긴다. 돌려받은 SQL 의 테이블·컬럼이 근거 문서에 있는지 한 번 대조한다.
6. 제출(조립만 한다): 통과한 시나리오를 4단계 선별에서 정한 순서 그대로 늘어놓고(점수를 다시 매기지 않는다), 시나리오마다 이름과 SQL 을 worker 반환에서 글자 그대로 복사해 `answer-format.md` 1절 틀에 넣은 뒤 바로 `sql_submit` 을 1회 부른다. 통과한 시나리오가 없으면 부르지 않는다.
   - 이 단계에서 하지 않는 것: 기간·업무 키·예외 조건·조인·이름·점수 재검토, 사용자 요청 재해석, 건수 재계산, 보고서 구상. 모두 1~5단계에서 확정됐다. 조합 점검을 통과한 SQL 은 제출 전에 다시 점검하지 않는다.
   - `sql_submit` 을 부르는 응답에서는 제출 질의만 만든다. 보고서는 제출 결과를 받은 다음 응답(7단계)에서 쓴다.
   - 오류 처리는 `answer-format.md` 2절이다(오류면 1회만 고쳐 다시 제출하고, 다시 실패하면 유효 시나리오가 없는 것으로 처리한다).
7. 답변: 답변을 쓰기 직전에 `answer-format.md` 를 다시 읽는다(이 단계만 같은 대화에서 이미 읽은 파일을 다시 읽는다). `AGENTS.md` 9절 보고서 틀로 쓴다. 재료는 이미 확정된 것(요청 해석, 조합, 점수, 이름, worker 반환, `sql_submit` 결과)을 옮겨 쓰며 다시 정하지 않는다. 절마다 아래 재료로 채운다.
   - 머리 목록·1.1: 1단계에서 정한 범위·기간·건수, `sql_submit` 결과(통과 수, `hit_count`), 4절에 갈 후보의 사유
   - 1.2·3.x 의 줄: 감사 위험 줄의 ACFE, 부정 패턴 조합 줄의 패턴 이름·COSO 는 패턴 page 의 값을 그대로, 해당 건수는 `sql_submit` 결과의 `hit_count` 를 그대로 쓴다. 조사할 증빙과 데이터 해석 가정은 worker 반환을 쓴다
   - 2.1: 1단계의 범위 해석(도메인, 업무 흐름, 기간·건수 결정과 기본값 여부)
   - 2.2: 2~3단계에서 고른 패턴과 조합한 이유, worker 반환의 「조합 근거」
   - 2.3: 4단계에서 worker 에 맡긴 후보와 점수, worker 판정(통과·실패 사유). 3단계에서 대입하지 못해 맡기지 않은 후보는 2.3 표에 넣지 않고 4절에만 쓴다
   - 3.x 문단: worker 반환의 「쉬운 설명」을 바탕으로 쓰고, 끝에 해당 건수가 뜻하는 것을 한 문장 더한다
   - 4: 3단계에서 빠진 후보, worker 실패 후보, `hit_count` 0 인 시나리오
   - 5: worker 들의 데이터 해석 가정을 모은 것
   - 6: 위 내용을 2~3문장으로 맺고, 조사할 증빙·가정 확인·Bottom-up 확인 같은 다음 단계를 적는다
   - 부록: 유효 시나리오가 있으면 맨 끝에 `## 부록: 시나리오 JSON` 을 두고 `sql_submit` 입력 순서대로 시나리오마다 공백 없는 한 줄 JSON 블록을 쓴다(`answer-format.md` 3절). 유효 시나리오가 없으면 이 절을 쓰지 않는다
   문체는 `AGENTS.md` 9절을 따른다: 문단 자리는 풀어 쓴 문단으로, 데이터를 모르는 사람이 읽을 수 있게, 물리명 없이, 「일부러 … 했을 가능성을 본다」처럼 단정하지 않고 쓴다. `answer-format.md` 7절 점검을 마친 뒤 낸다.

## 수정 Process

1. 첨부 SQL 의 테이블과 컬럼을 OKF 테이블 문서와 대조해 없는 것을 표시한다.
2. 조인은 조인 문서·`sql-query` 「조인」 절과, 코드값 리터럴은 코드 문서·코드값 샘플과, 기간 조건은 기준 날짜 컬럼의 형식과 대조한다.
3. 위험이 같은 부정 패턴 page 와 비교해 빠진 조건(정상 업무 제외, 고의성 신호)을 찾고, 첨부 SQL 의 조건이 어떤 부정 패턴(들)에 해당하는지 정해 부정 패턴 조합 줄을 채운다. 해당하는 패턴이 없는 조건은 「대응 없음」으로 두고 조합 줄에는 해당하는 패턴만 적는다.
4. 고친 SQL 을 query-writing.md 규칙(한 줄, 리터럴 기간, 키 단위 행)으로 정리하고 조합 점검 질의(`query-writing.md` 3절)를 1회 실행한다. 시나리오 이름은 「수정안: <원래 이름>」으로 한다.
5. 제출과 답변은 Process 6~7단계와 같다. 「데이터 해석 가정」에 고친 이유와 남은 가정을 적는다.

## 판정

| 상황 | 처리 |
|---|---|
| 패턴에 필요한 테이블이나 조인이 OKF 에 없음 | 만들지 않은 후보(사유: <무엇> 을 찾지 못함) |
| 목차에는 있으나 테이블 문서 파일이 없음 | 만들지 않은 후보(사유: <테이블> 문서 없음) |
| 조합의 두 패턴을 같은 행, 같은 행위자, 조인 문서로 잇지 못함 | 그 조합은 만들지 않고, 각 패턴을 다른 조합이나 단일 후보로 돌린다 |
| 필요한 조인이 직접 조인 금지 쌍, `usable: false`, `m2m` 뿐 | EXISTS·IN 으로 바꿀 수 없으면 만들지 않은 후보 |
| 대입한 항목에 자동 생성 page, 추측 조인, draft 문서가 있음 | 후보로 두고 「데이터 해석 가정」에 적는다 |
| worker 가 조합 축소 뒤 「단일」로 통과시킴 | 단일 시나리오로 두고 데이터 해석 가정에 「조합 <패턴> 은 기간 안 함께 해당하는 건 0건」을 적는다 |
| worker 가 실패로 돌려줌 | 만들지 않은 후보로 옮기고 5단계 규칙으로 다음 순위 후보를 맡긴다 |
| worker 가 결과 없이 실패(도구 실패) | 같은 prompt 로 1회 다시 맡긴다. 또 실패하면 만들지 않은 후보(사유: 시험 실행 불가) |
