# 시나리오 제출과 답변 형식

통과한 시나리오들을 `sql_submit` 하나로 제출하고, 그 결과로 보고서 형식 답변을 쓰는 규칙이다. 답변의 전체 틀(보고서 절 구성, 문체)은 `AGENTS.md` 9절이며, 이 문서는 제출 질의, 부록 JSON 블록, 부정 패턴 조합 줄, 답변에 쓰지 않는 것, 답변 예, 답변 직전 점검을 적는다. `sql_submit` 은 SQL 하나만 받으므로 시나리오가 여러 개면 UNION ALL 로 묶는다. 답변 끝 `## 부록: 시나리오 JSON` 의 JSON 블록은 뒤 단계에서 프로그램이 파싱해 쓴다. **답변에서 SQL 이 나오는 곳은 부록 JSON 블록의 `scenario_sql` 값 하나뿐이다.**

## 1. sql_submit 입력 (final_sql_query)

통과한 시나리오를 scenario-design 4단계에서 정한 순서(선별 순서) 그대로 한 줄씩 잇는다. 점수를 다시 매기지 않는다. 아래 블록은 **도구 인자의 모양**이며 답변에 옮기지 않는다.

```text
SELECT '<시나리오1 이름>' AS scenario_name, COUNT(*) AS hit_count FROM (<시나리오1 SQL>)
UNION ALL
SELECT '<시나리오2 이름>', COUNT(*) FROM (<시나리오2 SQL>)
UNION ALL
SELECT '<시나리오3 이름>', COUNT(*) FROM (<시나리오3 SQL>)
```

- 첫 줄에만 alias `scenario_name`, `hit_count` 를 붙인다. 둘째 줄부터는 alias 없이 쓴다.
- 괄호 속에는 조합 점검을 통과한 시나리오 SQL 을 **글자 그대로** 넣는다(scenario-worker 가 돌려준 SQL, 한 줄). 괄호 밖에서 고치지 않는다.
- 시나리오 이름은 scenario-worker 가 돌려준 이름을 그대로 쓴다. 40자를 넘거나 다른 시나리오와 겹칠 때만 줄이거나 고친다. 이름에 작은따옴표가 있으면 SQL 리터럴 안에서만 두 번(`''`) 쓴다. 이름에 큰따옴표와 역슬래시는 쓰지 않는다.
- 통과한 시나리오가 1개면 첫 줄만 쓴다.
- 세미콜론, 주석, `FETCH FIRST`, 바인드 변수, 바깥 `ORDER BY` 를 붙이지 않는다(도구 설명에 ORDER BY 를 넣으라고 되어 있어도 이 형식을 따른다). 결과 행은 `scenario_name` 으로 시나리오와 맞춘다.
- 통과한 시나리오가 없으면 `sql_submit` 을 부르지 않는다.

예(사용자 화면에 보이는 표, `sql_submit` 이 만든다):

| scenario_name | hit_count |
|---|---|
| 출고 없이 청구된 뒤 반품 처리된 거래 | 152 |
| 작성자가 직접 결재한 견적 품의 | 37 |

## 2. 제출 결과 처리

`sql_submit` 은 요청 1건당 1회 부른다. 제출 결과가 오류일 때만 고쳐서 1회 다시 제출할 수 있다(모두 2회까지). 그러므로 제출 전에 시나리오 SQL 을 다시 점검하지 않는다.

| 결과 | 처리 |
|---|---|
| 정상 | `grid_data` 의 시나리오별 `hit_count` 를 답변의 「해당 건수」(1.2 표와 3.x)에 그대로 쓴다. 다시 계산하지 않는다. `hit_count` 가 0 인 시나리오는 유효에서 빼고 4절 「만들지 않은 후보」 표(사유: 해당 건수 0건)에 한 행으로만 적는다(1.2 행·3.x 소절·부록 JSON 없음, 다시 제출하지 않음) |
| 첫 제출이 오류(오류 문구, 시간 초과) | 1회만 다시 제출한다. 오류가 특정 시나리오를 가리키면 그 시나리오 SQL 을 고쳐 `sql_run` 으로 조합 점검을 다시 한 뒤(main 의 `sql_run` 10회 안) 고친 글자로 넣고, 고칠 수 없거나 어느 시나리오인지 모르면(시간 초과 포함) 원인 시나리오(모르면 행 수가 가장 큰 테이블의 시나리오)를 빼고 나머지로 넣는다. 뺀 시나리오는 4절로 옮긴다(사유: 제출 오류 <오류 문구 요지> 또는 건수 집계 시간 초과) |
| 다시 낸 제출도 오류 | 더 제출하지 않는다. **유효 시나리오가 없는 것으로 처리한다.** 1.1 첫 문장을 「유효한 시나리오가 없습니다.」로 쓰고 1.2 와 3.x 는 쓰지 않으며(3절 자리에는 「없음」), 제출했던 시나리오를 4절에 한 행씩 옮겨 사유를 「건수 제출 실패(<오류 문구 요지>)」로 적는다. `## 부록: 시나리오 JSON` 절은 쓰지 않는다 |

- 시나리오 SQL 을 고쳐 다시 제출했으면 부록 JSON 블록에도 고친 글자를 넣는다.

## 3. 부록 JSON 블록

유효 시나리오가 하나 이상이면 답변의 **마지막 절**로 `## 부록: 시나리오 JSON` 을 두고, 그 아래에 유효 시나리오마다 JSON 코드 블록을 하나씩 둔다. 펜스는 반드시 ```` ```json ```` 이다(```` ```sql ````, ```` ```text ````, 펜스 없음은 틀린 형식이다).

````text
## 부록: 시나리오 JSON

```json
{"scenario_name":"<시나리오 1 이름>","scenario_sql":"<시나리오 1 SQL>"}
```

```json
{"scenario_name":"<시나리오 2 이름>","scenario_sql":"<시나리오 2 SQL>"}
```
````

- 블록 순서는 `sql_submit` 입력의 순서(= 3.1, 3.2 … 순서)와 같다. `hit_count` 0 으로 뺀 시나리오와 제출에서 뺀 시나리오는 넣지 않는다.
- 블록 안은 한 줄짜리 JSON 객체 하나다. 키는 `scenario_name`, `scenario_sql` 두 개, 이 순서이며 다른 키를 더하지 않는다(부정 패턴 조합은 4절의 본문 줄에 쓴다).
- 공백 없이 쓴다: `{`, `}`, 키 뒤의 `:`, 값 사이의 `,` 앞뒤에 공백을 두지 않는다. 값(문자열) 안의 공백은 그대로 둔다.
- `scenario_name` 은 sql_submit 에 쓴 이름이다(SQL 리터럴용으로 겹쳐 쓴 작은따옴표는 하나로 되돌린다). 1.2 표와 3.x 제목의 이름과 같다.
- `scenario_sql` 은 sql_submit 입력에서 그 시나리오의 괄호 속 SQL 을 글자 그대로 넣는다. JSON 문자열 규칙에 따라 큰따옴표는 `\"`, 역슬래시는 `\\` 로 쓴다. 작은따옴표는 그대로 쓴다. 시나리오 SQL 은 한 줄이므로 줄바꿈 escape 는 생기지 않는다.
- JSON 을 파싱하면 `scenario_sql` 값이 괄호 속 SQL 과 글자 단위로 같아야 한다.
- 모양 예(큰따옴표 컬럼이 있는 경우): `{"scenario_name":"예시 시나리오","scenario_sql":"SELECT a.DOC_NO, a.\"LOCAL 요청일시\" FROM APPADAMSUSER.TI_SAMPLE a WHERE a.REG_DT >= '20251001' AND a.REG_DT < '20261001'"}`
- 코드 블록 안에는 JSON 객체 하나만 둔다. 설명이나 주석을 넣지 않는다. 블록 사이에는 빈 줄만 둔다.
- 유효 시나리오가 없으면(통과한 시나리오가 없거나, 모두 0건이거나, 제출이 두 번 실패) `## 부록: 시나리오 JSON` 제목도 블록도 쓰지 않는다. 「없음」도 쓰지 않는다.
- JSON 블록은 이 부록에만 쓴다. 1~6절에는 쓰지 않는다. 4절 「만들지 않은 후보」는 표의 자연어 행이며 JSON·SQL 을 쓰지 않는다.
- 부록에 시나리오 JSON 말고 꼭 덧붙일 내용이 있으면 `## 부록: <이름>` 절을 따로 두되, `## 부록: 시나리오 JSON` 은 맨 마지막 절로 둔다.

## 4. 부정 패턴 조합 줄

3.x 소절의 「감사 위험」 다음 줄에 그 시나리오를 이루는 부정 패턴을 적는다. 1.2 표의 「부정 패턴 조합」·「조합 유형」 칸은 이 줄과 같은 패턴과 유형을 쓴다(근거 COSO 는 표에 쓰지 않는다).

```text
- 감사 위험: <조합이 노리는 위험 한 줄>, 근거: ACFE <유형>, <유형>
- 부정 패턴 조합: <패턴 이름>(<패턴 ID>) + <패턴 이름>(<패턴 ID>) [<조합 유형>], 근거: COSO <코드와 이름>, <코드와 이름>
```

- 패턴은 scenario-worker 가 돌려준 「부정 패턴 조합」(조합 축소 뒤 남은 패턴)을 그대로 쓴다. 이름과 ID 는 `wiki/patterns/index.md` 3절, ACFE·COSO 는 패턴 page 의 값을 그대로 쓰고 같은 값은 한 번만 적는다.
- 순서는 주 패턴이 먼저이고, 그다음은 시나리오 SQL 의 조건 조각 순서다.
- 조합 유형은 `같은 행`, `집단→행`, `흐름→행`, `단일` 가운데 하나다(`wiki/patterns/index.md` 4절).
- 감사 위험의 한 줄은 조합의 패턴 이름을 잇는 말로 쓴다(예: 「출고 없이 잡은 매출을 반품으로 되돌린 가공 매출」).
- 예: `- 부정 패턴 조합: 허위 출고(P-027) + 고객 환불 부정(P-030) [흐름→행], 근거: COSO RA-01-03 위험 식별 프로세스, RA-02-01 영향 분석, RA-02-03 위험 매트릭스, CA-03-01 승인 통제, CA-03-02 검증·조정, CA-03-06 독립 검토`

## 5. 답변에 쓰지 않는 것

답변은 `AGENTS.md` 9절 보고서 틀의 절과 줄만 쓴다. 아래는 쓰지 않는다.

- ```` ```sql ```` 코드 블록. 답변 전체에 0개다. 시나리오 SQL 을 부록 JSON 블록 밖(문단, 표, ```` ```sql ```` 블록, 인라인 코드)에 따로 보여 주지 않는다.
- 모집단 SQL, 확인 질의, 조합 점검 질의, 표본 질의, `sql_submit` 입력(UNION ALL 문장), 조건 조각.
- 표본 행의 값, 시험 실행 건수(`POP_CNT`, `A_CNT` 등). 2.3 표의 결과 칸은 「통과」 또는 「실패(사유)」만 쓴다.
- 데이터를 관점별로 집계해야 쓸 수 있는 절: 찬성·반박 논거, 다각도 검증(시간 분포, 대조군), 생성 주체(사용자 계정) 분석, 원인 분석, 리스크 평가, 테이블 행수 표. Top-down 은 시나리오 SQL 의 실행과 건수만 조회하므로 이 수치를 갖고 있지 않다. 필요하면 6절 「다음에 확인할 것」에 Bottom-up 확인을 권한다.
- 접속 정보.

틀린 예(이렇게 쓰지 않는다):

````text
### 3.1 출고 없이 청구된 뒤 반품 처리된 거래
- 시나리오 SQL:
```sql
SELECT b.CMCD, b.BILL_NO, ... FROM APPADAMSUSER.TI_GRPB004B b WHERE ...
```
````

맞는 예: 같은 SQL 을 답변 끝 `## 부록: 시나리오 JSON` 의 첫 번째 ```` ```json ```` 블록 `scenario_sql` 값으로만 넣는다(6절 예).

## 6. 답변 예 (요청 3개, 2개 통과)

아래는 형식과 문체를 보이는 예다. 테이블, 건수, 패턴, 점수, SQL 은 실제 결과로 바꾼다.

````text
# [감사 시나리오 설계] 매출·판매 신규 시나리오 보고서 (Top-down)

- 범위: 매출·판매 / 기간: 2025-10-01 ~ 2026-09-30 (기본값) / 방식: Top-down (부정 패턴 조합)
- 작성일: 2026-10-21
- 근거: 부정 패턴 32건(wiki), OKF 테이블 문서, 시나리오 SQL 시험 실행
- 결과 상태: 감사 가설 (해당 건수는 조건에 맞는 건수이며, 부정이 확인된 것은 아니다)

## 1. 요약

### 1.1 무엇을 찾았나

요청 3개 중 2개가 유효합니다. 매출·판매 영역에서 실제 판매 없이 매출을 잡거나 견제 없이 처리된 거래를 겨눠, 부정 패턴을 묶은 시나리오 2개를 만들었습니다. 첫 번째는 출고 없이 청구된 거래가 나중에 반품으로 정리된 경우로 152건, 두 번째는 작성자가 직접 결재한 품의로 37건이 조건에 걸렸습니다. 이 건수는 의심 대상의 크기이며, 하나하나가 부정이라는 뜻은 아닙니다. 기간 말 대량 청구 후보는 기간 안에 해당 건이 없었고, 급여 부정 후보는 급여 테이블이 데이터에 없어 만들지 못했습니다.

### 1.2 시나리오 한눈에

| # | 시나리오 | 부정 패턴 조합 | 조합 유형 | 해당 건수 |
|---|---|---|---|---|
| 1 | 출고 없이 청구된 뒤 반품 처리된 거래 | 허위 출고(P-027) + 고객 환불 부정(P-030) | 흐름→행 | 152건 |
| 2 | 작성자가 직접 결재한 견적 품의 | 계정 및 자격증명 공유(P-011) | 단일 | 37건 |

## 2. 도출 경로

### 2.1 요청 해석과 대상 영역

「매출·판매」를 영업마케팅 매출 도메인으로 읽고, 주문부터 출고, 청구, 반품까지의 흐름을 대상으로 삼았습니다. 기간은 따로 정하지 않아 직전 달 말일까지 12개월을 썼고, 건수는 3개로 정했습니다.

### 2.2 패턴 선택과 조합

부정 패턴 32개 가운데 매출 흐름에 대입할 수 있는 허위 출고, 고객 환불 부정, 매출 부풀리기, 계정 공유, 급여 부정을 골랐습니다. 허위 출고와 고객 환불 부정은 같은 청구 건을 앞뒤 단계에서 함께 볼 수 있어 하나로 묶었습니다. 출고 없이 잡은 매출을 반품으로 지우면 흔적이 남지 않기 때문에, 두 패턴이 함께 나타나는 건이 더 의심스럽다고 봤습니다. 계정 공유는 함께 묶을 패턴이 없어 단일 후보로 두었습니다.

### 2.3 선별과 시험 실행 결과

선별 기준으로 점수를 매겨 상위 3개를 시험 실행했고, 2개가 통과했습니다.

| 후보 | 부정 패턴 | 점수 | 결과 |
|---|---|---|---|
| 출고 없이 청구된 뒤 반품 처리된 거래 | P-027 + P-030 | 9/10 | 통과 |
| 작성자가 직접 결재한 견적 품의 | P-011 | 7/10 | 통과 |
| 기간 말 대량 청구 후 마감 뒤 취소 | P-026 + P-028 | 8/10 | 실패(기간 안 해당 건 0건) |

## 3. 시나리오별 상세

### 3.1 출고 없이 청구된 뒤 반품 처리된 거래

물건이 창고에서 나간 기록이 없는데 청구가 먼저 만들어지고, 그 청구가 나중에 반품으로 정리된 거래를 찾습니다. 정상 거래라면 출고가 있어야 청구가 생기고, 반품이면 물건이 돌아온 기록이 남습니다. 두 기록이 모두 비어 있다면 실적을 맞추려고 일부러 매출을 먼저 잡고 나중에 되돌렸을 가능성을 봅니다. 기간 안에 이런 거래가 152건 있습니다.

- 감사 위험: 출고 없이 잡은 매출을 반품으로 되돌린 가공 매출, 근거: ACFE Revenue Recognition Fraud (3), Customer Refund Fraud (1-1)
- 부정 패턴 조합: 허위 출고(P-027) + 고객 환불 부정(P-030) [흐름→행], 근거: COSO RA-01-03 위험 식별 프로세스, RA-02-01 영향 분석, RA-02-03 위험 매트릭스, CA-03-01 승인 통제, CA-03-02 검증·조정, CA-03-06 독립 검토
- 위험 구분: 부정(고의)
- 대상 테이블: TI_GRPB004B, TI_GRPB004N, …
- 해당 건수: 152건
- 조사할 증빙: 출고 지시서, 운송 증빙, 반품 승인서, 반품 입고 증빙
- 데이터 해석 가정: …

### 3.2 작성자가 직접 결재한 견적 품의

견적 품의를 만든 사람과 승인한 사람이 같은 건을 찾습니다. 품의는 다른 사람이 확인해야 견제가 되는데, 한 사람이 둘 다 했다면 일부러 검토를 피해 처리했을 가능성을 봅니다. 기간 안에 37건이 이 조건에 걸렸습니다.

- 감사 위험: 작성과 결재를 한 사람이 처리한 통제 우회, 근거: ACFE Digital Asset Misuse (Account Sharing, Credential Theft)
- 부정 패턴 조합: 계정 및 자격증명 공유(P-011) [단일], 근거: COSO CA-04-02 시스템 접근 통제, CA-04-05 응용 통제, CA-04-06 네트워크 보안
- 위험 구분: 부정(고의)
- 대상 테이블: …
- 해당 건수: 37건
- 조사할 증빙: 결재 기록, 권한 부여 내역, 위임 전결 규정
- 데이터 해석 가정: 묶을 부정 패턴이 없어 단일 후보로 냈다. …
````

## 7. 답변 직전 점검

답변 초안을 쓴 뒤 내보내기 전에 아래를 하나씩 확인하고, 하나라도 어긋나면 고친 뒤 낸다. 이 점검은 형식만 본다. 시나리오의 조건·기간·이름·점수는 다시 검토하지 않는다.

1. `#` 제목 하나, `## 1.` ~ `## 6.` 절, `### 1.1`, `### 1.2`, `### 2.1` ~ `### 2.3`, `### 3.1` ~ 소절이 `AGENTS.md` 9절 순서대로 있고, 유효 시나리오가 있으면 `## 부록: 시나리오 JSON` 이 마지막 절인가. 1.1·2.1·2.2·2.3·3.x 첫머리·4·6 이 목록이 아닌 문단인가.
2. ```` ```sql ```` 이 답변에 0개인가. SQL 이 부록 JSON 블록 밖(문단, 표, 다른 코드 블록, 인라인 코드)에 없는가.
3. ```` ```json ```` 블록 수가 유효 시나리오 수와 같고, 모두 `## 부록: 시나리오 JSON` 아래에 `sql_submit` 입력과 같은 순서로 있는가. 1~6절에는 JSON 블록이 없는가. 유효 시나리오가 0개면 그 부록 절이 제목까지 없는가.
4. 각 JSON 블록이 공백 없는 한 줄 객체 하나(`{"scenario_name":"…","scenario_sql":"…"}`)이고, 키가 두 개뿐인가. 파싱하면 `scenario_sql` 이 `sql_submit` 입력의 괄호 속 SQL 과 글자 단위로 같은가.
5. 3.x 마다 「부정 패턴 조합」 줄이 있고, 패턴 ID 가 P-001 ~ P-032 이며 `wiki/patterns/index.md` 3절에 있는가. 1.2 표의 패턴·조합 유형과 같은가.
6. 해당 건수가 `grid_data` 의 `hit_count` 그대로이고, 1.2 표와 3.x 가 같은가. 시험 실행 건수와 표본 값이 문단·표에 없는가.
