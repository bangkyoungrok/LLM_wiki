# 시나리오 제출과 답변 형식

통과한 시나리오들을 `sql_submit` 하나로 제출하고, 그 결과로 **유효 시나리오 1건마다 11절 분석 보고서 1개**를 쓰는 규칙이다. 이 문서가 보고서 형식의 기준이며(`AGENTS.md` 9절은 이 문서를 가리킨다), 제출 질의, 제출 결과 처리, 부정 패턴 조합 줄, 보고서 틀, 쓰는 말, 쓰지 않는 것, 부록 JSON, 보고서 예, 직전 점검을 적는다. `sql_submit` 은 SQL 하나만 받으므로 시나리오가 여러 개면 UNION ALL 로 묶는다. **답변에서 SQL 이 나오는 곳은 보고서마다 부록 A-2 한 곳과, 답변 맨 끝 `## 부록: 시나리오 JSON`(뒤 단계 프로그램이 파싱) 두 곳뿐이다.** 보고서는 감사팀 사용자가 읽는 문서이므로 agent 의 작업 과정은 쓰지 않는다.

## 1. sql_submit 입력 (final_sql_query)

통과한 시나리오를 scenario-design 4단계에서 정한 순서(선별 순서) 그대로 한 줄씩 잇는다. 점수를 다시 매기지 않는다. 아래 블록은 **도구 인자의 모양**이며 답변에 옮기지 않는다.

```text
SELECT '<시나리오1 이름>' AS scenario_name, COUNT(*) AS hit_count FROM (<시나리오1 SQL>)
UNION ALL
SELECT '<시나리오2 이름>', COUNT(*) FROM (<시나리오2 SQL>)
UNION ALL
SELECT '<시나리오3 이름>', COUNT(*) FROM (<시나리오3 SQL>)
```

- 첫 줄에만 alias `scenario_name`, `hit_count` 를 붙인다. 둘째 줄부터는 alias 없이 쓴다.
- 괄호 속에는 조합 점검을 통과한 시나리오 SQL 을 **글자 그대로** 넣는다(scenario-worker 가 돌려준 SQL, 한 줄). 괄호 밖에서 고치지 않는다.
- 시나리오 이름은 scenario-worker 가 돌려준 이름을 그대로 쓴다. 40자를 넘거나 다른 시나리오와 겹칠 때만 줄이거나 고친다. 이름에 작은따옴표가 있으면 SQL 리터럴 안에서만 두 번(`''`) 쓴다. 이름에 큰따옴표와 역슬래시는 쓰지 않는다.
- 통과한 시나리오가 1개면 첫 줄만 쓴다.
- 세미콜론, 주석, `FETCH FIRST`, 바인드 변수, 바깥 `ORDER BY` 를 붙이지 않는다(도구 설명에 ORDER BY 를 넣으라고 되어 있어도 이 형식을 따른다). 결과 행은 `scenario_name` 으로 시나리오와 맞춘다.
- 통과한 시나리오가 없으면 `sql_submit` 을 부르지 않는다.

예(사용자 화면에 보이는 표, `sql_submit` 이 만든다):

| scenario_name | hit_count |
|---|---|
| 출고 없이 청구된 뒤 반품 처리된 거래 | 152 |
| 작성자가 직접 결재한 견적 품의 | 37 |

## 2. 제출 결과 처리

`sql_submit` 은 요청 1건당 1회 부른다. 제출 결과가 오류일 때만 고쳐서 1회 다시 제출할 수 있다(모두 2회까지). 그러므로 제출 전에 시나리오 SQL 을 다시 점검하지 않는다.

| 결과 | 처리 |
|---|---|
| 정상 | `grid_data` 의 시나리오별 `hit_count` 를 보고서 상태 줄과 3.1 제목의 건수에 그대로 쓴다. 다시 계산하지 않는다. `hit_count` 가 0 인 시나리오는 유효에서 빼고 보고서를 쓰지 않으며 「만들지 못한 시나리오」 표(사유: 해당 건수 0건)에 한 행으로만 적는다(부록 JSON 없음, 다시 제출하지 않음) |
| 첫 제출이 오류(오류 문구, 시간 초과) | 1회만 다시 제출한다. 오류가 특정 시나리오를 가리키면 그 시나리오 SQL 을 고쳐 `sql_run` 으로 조합 점검을 다시 한 뒤(main 의 `sql_run` 10회 안) 고친 글자로 넣고, 고칠 수 없거나 어느 시나리오인지 모르면(시간 초과 포함) 원인 시나리오(모르면 행 수가 가장 큰 테이블의 시나리오)를 빼고 나머지로 넣는다. 뺀 시나리오는 「만들지 못한 시나리오」로 옮긴다(사유: 제출 오류 <오류 문구 요지> 또는 건수 집계 시간 초과) |
| 다시 낸 제출도 오류 | 더 제출하지 않는다. **유효 시나리오가 없는 것으로 처리한다.** 4절의 「유효 시나리오가 없을 때」 안내를 쓰고, 제출했던 시나리오를 「만들지 못한 시나리오」에 한 행씩 옮겨 사유를 「건수 제출 실패(<오류 문구 요지>)」로 적는다. `## 부록: 시나리오 JSON` 절은 쓰지 않는다 |

- 시나리오 SQL 을 고쳐 다시 제출했으면 부록 A-2 와 부록 JSON 블록에도 고친 글자를 넣는다.

## 3. 부정 패턴 조합 줄

보고서 3.1 의 L1~L3 다음에 그 시나리오를 이루는 부정 패턴을 아래 두 줄로 적는다(4절 틀의 3.1 참조).

```text
- 감사 위험: <조합이 노리는 위험 한 줄>, 근거: ACFE <유형>, <유형>
- 부정 패턴 조합: <패턴 이름>(<패턴 ID>) + <패턴 이름>(<패턴 ID>) [<조합 유형>], 근거: COSO <코드와 이름>, <코드와 이름>
```

- 패턴은 scenario-worker 가 돌려준 「부정 패턴 조합」(조합 축소 뒤 남은 패턴)을 그대로 쓴다. 이름과 ID 는 `wiki/patterns/index.md` 3절, ACFE·COSO 는 패턴 page 의 값을 그대로 쓰고 같은 값은 한 번만 적는다.
- 순서는 주 패턴이 먼저이고, 그다음은 시나리오 SQL 의 조건 조각 순서다.
- 조합 유형은 `같은 행`, `집단→행`, `흐름→행`, `단일` 가운데 하나다(`wiki/patterns/index.md` 4절).
- 감사 위험의 한 줄은 조합의 패턴 이름을 잇는 말로 쓴다(예: 「출고 없이 잡은 매출을 반품으로 되돌린 가공 매출」).
- 예: `- 부정 패턴 조합: 허위 출고(P-027) + 고객 환불 부정(P-030) [흐름→행], 근거: COSO RA-01-03 위험 식별 프로세스, RA-02-01 영향 분석, RA-02-03 위험 매트릭스, CA-03-01 승인 통제, CA-03-02 검증·조정, CA-03-06 독립 검토`

## 4. 보고서 틀 (시나리오 1건 = 보고서 1개)

답변은 **유효 시나리오 1건마다 아래 11절 보고서 1개**를 쓰고, 유효 시나리오가 여럿이면 `sql_submit` 입력 순서대로 보고서를 이어 쓴다(보고서 사이에 `---` 한 줄). 보고서 뒤에 「만들지 못한 시나리오」 절을 한 번 두고, 답변 맨 끝에 `## 부록: 시나리오 JSON` 을 둔다(7절). 이 보고서는 감사팀 사용자가 읽는 문서다. 아래 {{…}} 자리를 채우고, 자리 밖의 절·소절 이름과 순서는 바꾸지 않는다. 해당 내용이 없는 소절은 「없음」 한 줄로 둔다.

- **시나리오 ID**: `SSA<YYMM><NNN>` — YYMM 은 작성일의 연·월 두 자리씩(예: 2026-10 → 2610), NNN 은 이 답변 안의 보고서 순번(001부터). 임시 번호이며 사람이 등록할 때 다시 매긴다.
- **제목 태그**: 첫 태그는 `부정 위험`, 둘째 태그는 OKF 도메인의 업무 이름(영업, 입찰·견적, 마케팅비, 구매, 재무, 인사, MRO 등).
- **상태 줄**: 이 agent 는 시나리오 SQL 을 DB 에서 실행했으므로 늘 「분석 완료 — DB 실행 검증 완료 (실행일 <작성일>, 결과 <hit_count>건)」이다. 「결과 N건」은 `sql_submit` 의 `hit_count` 다.
- **3·5·7 절의 꼬리표**: Top-down 은 시나리오 SQL 의 실행과 건수만 조회하므로 5절 제목은 「핵심 발견 (예상)」, 7.1 은 「메커니즘 (추정)」으로 쓴다. 3절 제목은 「발견 상세」다.

## 5. 쓰는 말

보고서는 감사팀 사용자가 한 번 읽고 이해할 수 있게 쓴다.

- 각 절의 첫 문장은 그 절의 결론이다. 한 문장에는 한 가지만 쓰고 짧게 끊는다.
- **업무 말로 쓴다**: 1.1, 5, 7.1, 8, 9, 11 은 테이블·컬럼 물리명 없이 업무 말로만 쓴다. 물리명(`TI_GRPB004B`, `SOLD_TO`)은 템플릿이 자리를 둔 곳(1.2, 2.x 제목과 조인 키, 3.1·4.x 조건식, 6.x, 7.2, 10.1, 부록)에만 쓴다. 컬럼은 한글명 뒤에 괄호로 물리명을 붙인다(예: 거래선코드(`SOLD_TO`)).
- 통계·도구 용어를 쓰지 않는다: modified z, MAD, IQR, 기법 코드, 점검 열 이름, `TARGET_VAL` 같은 내부 열 이름. 「평소 범위(같은 대상의 지난 값으로 정한 범위)」처럼 풀어 쓴다.
- 수치에는 단위와 비교 대상을 붙인다(예: 「64건」, 「21%(전체 3%)」). 도구·SQL 결과에 있는 값만 쓰고 새로 계산하지 않는다.
- 단정하지 않는다. 「부정이다」가 아니라 「~했을 가능성을 본다」, 「부정 의심」, 「확인 필요」로 쓴다.
- 사람 이름·계정은 가린다(예: `Y***.P***`).
- 1.1, 5.x, 7.1 은 「일부러 … 했을 가능성을 본다」처럼 부정 의심으로 쓰고 단정하지 않는다.

## 6. 쓰지 않는 것

보고서는 **결과와 근거**만 담는다. agent 가 어떻게 일했는지는 쓰지 않는다.

- **내부 작업 서술**: subagent·worker 이름, 위임, `sql_run`·`sql_submit`·도구 이름과 호출 횟수, 호출 상한, skill·wiki·OKF 문서 경로, 패턴 page 를 읽었다는 말, 「테이블 선택」 후보·순서·건너뛴 이유, 선별 점수, 조합 점검·건수 점검·표본 질의와 그 수치(`POP_CNT`, `A_CNT`, `HIT_CNT`, `KEY_CNT`, `COMBO_CNT`, `NORMAL_CNT` 등), 질의 ①·② 같은 단계 이름, alias, 「확인해 보니」식 과정 묘사. 「A 와 B 를 조인해서 … 를 확인했더니」 같은 문장은 2.x 의 조인 키 한 줄로 바꿔 쓴다.
- **본문의 SQL·JSON**: 1~11절에는 ```` ```sql ````·```` ```json ```` 블록, 인라인 SQL, 모집단 질의, 확인·점검·표본 질의, `sql_submit` 입력(UNION ALL 문장), 통계 도구 호출 인자와 조회문 원문을 쓰지 않는다. SQL 은 부록 A-2와 `## 부록: 시나리오 JSON` 에만 있다.
- 표본 행의 값, 통계 표 원문, 접속 정보.
- Top-down 은 데이터를 관점별로 집계하지 않으므로 5·7·8 절에 실측 수치(분포, 집중도, 금액 합)를 지어내지 않는다. 보고서의 수치는 `hit_count` 하나다.

## 7. 부록: 시나리오 JSON (답변 맨 끝)

유효 시나리오가 하나 이상이면 답변의 **마지막 절**로 `## 부록: 시나리오 JSON` 을 한 번만 두고(보고서마다 두지 않는다), 유효 시나리오마다 JSON 코드 블록을 하나씩 `sql_submit` 입력 순서대로 둔다. 뒤 단계 프로그램이 이 블록을 파싱하므로 형식을 지킨다. 펜스는 반드시 ```` ```json ```` 이다.

````text
## 부록: 시나리오 JSON

```json
{"scenario_name":"<시나리오 1 이름>","scenario_sql":"<시나리오 1 SQL>"}
```

```json
{"scenario_name":"<시나리오 2 이름>","scenario_sql":"<시나리오 2 SQL>"}
```
````

- 블록 안은 한 줄짜리 JSON 객체 하나, 키는 `scenario_name`, `scenario_sql` 두 개뿐이며 공백 없이 쓴다(`{`, `}`, `:`, `,` 앞뒤 공백 없음).
- `scenario_name` 은 보고서 제목의 시나리오 이름과 `sql_submit` 의 `scenario_name` 과 같은 글자다(SQL 리터럴용으로 겹쳐 쓴 작은따옴표는 하나로 되돌린다).
- `scenario_sql` 은 `sql_submit` 입력에서 그 시나리오의 괄호 속 SQL 과 글자 단위로 같고, 부록 A-2 의 SQL 과도 같다. 큰따옴표는 `\"`, 역슬래시는 `\\` 로 쓴다. 작은따옴표는 그대로 쓴다.
- `hit_count` 0 으로 뺀 시나리오와 제출에서 뺀 시나리오는 넣지 않는다. 시나리오 SQL 을 고쳐 다시 제출했으면 고친 글자를 넣는다.
- 유효 시나리오가 없으면 이 절은 제목도 블록도 쓰지 않는다(「없음」도 쓰지 않는다).

## 1. 요약

### 1.1 무엇이 문제인가
빌링(청구)은 **항상 등록된 거래선**에 대해 이뤄져야 한다. 거래선 코드가 비어 있거나, 코드는 있으나 거래선 마스터에 없는 청구 건은 **거래선 검증을 거치지 않고 청구가 만들어졌을 가능성**을 본다. 기존 영업 시나리오는 거래선별 금액·할인 이상에 집중했으나, 이 시나리오는 청구와 거래선 마스터의 연결 자체를 본다.

### 1.2 문제가 발견된 포인트
- 판매주문내역 빌링(`TI_GRPB004B`): 빌링번호(`BILL_NO`), 거래선코드(`SOLD_TO`), 금액(`LAMT`), 빌링일자(`BILL_DT`), 법인코드(`CMCD`)
- 거래선정보(`TI_GRPB810`): 법인코드(`CMCD`) + 거래선코드(`ENTP_CD`)
- 청구 행의 거래선 코드가 비어 있거나 거래선 마스터에 없으면 의심 건으로 추출

## 2. 발견 경로: 빌링 → 거래선 마스터 조인 분석

## 9. 보고서 직전 점검

보고서 초안을 쓴 뒤 내보내기 전에 아래를 하나씩 확인하고, 하나라도 어긋나면 고친 뒤 낸다. 이 점검은 형식만 본다. 시나리오의 조건·기간·이름·점수는 다시 검토하지 않는다.

1. 유효 시나리오마다 보고서가 하나씩 있고, 순서가 `sql_submit` 입력과 같은가. 보고서마다 `#` 제목(태그 2개), 메타 4줄, `## 1.` ~ `## 11.`, `## 부록: 분석에 사용된 주요 테이블`(A-1, A-2)이 이 순서대로 있는가.
2. 상태 줄의 「결과 N건」과 3.1 제목의 건수가 `sql_submit` `grid_data` 의 `hit_count` 와 같은가.
3. 1.1, 5, 7.1, 8, 9, 11 에 테이블·컬럼 물리명이 없는가. 본문 어디에도 6절의 내부 작업 서술(worker, sql_run, 점수, 점검 수치, 문서 경로)이 없는가.
4. ```` ```sql ```` 블록이 보고서마다 부록 A-2에만 있는가. 1~11절에 SQL·JSON 블록이 없는가.
5. A-2 의 SQL 이 `sql_submit` 입력의 괄호 속 SQL 과 글자 단위로 같은가(`FETCH FIRST`, 바인드 변수, 세미콜론을 덧붙이지 않았는가).
6. 11절 「영향 요약」 마지막 줄이 고정 문구 그대로인가.
7. `## 만들지 못한 시나리오` 가 보고서 뒤에 한 번 있는가(없으면 「없음」).
8. `## 부록: 시나리오 JSON` 이 답변의 마지막 절이고 한 번만 있으며, ```` ```json ```` 블록 수가 유효 시나리오 수와 같고, 순서와 `scenario_sql` 이 `sql_submit` 입력·A-2 와 같은가. 유효 시나리오가 없으면 이 절이 아예 없는가.
