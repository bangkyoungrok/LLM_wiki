# data-investigation

실제 데이터 값의 이상에서 시나리오를 만든다. 순서는 **데이터 조회 → 데이터 이상징후 패턴 대응 → 패턴 조합으로 가설 → 가설 조사 → 표본 점검 → 제출 → 보고서**다. 기간은 분석 기간 하나만 쓴다. 이 SKILL.md 를 읽은 다음 응답에서 아래 파일을 `agent_studio_project_view` 로 함께 읽는다.

- `skills/data-investigation/references/stat-views.md`, `skills/data-investigation/references/result-reading.md` (통계 도구 인자, 탐색 관점, 결과 읽기)
- `skills/data-investigation/references/query-writing.md`, `skills/data-investigation/references/answer-format.md` (점검 질의, 조합 질의, 시나리오 SQL, 건수 점검, 제출, 보고서)
- `wiki/patterns/index.md` (데이터 이상징후 패턴 대응표와 조합 규칙)
- `wiki/risk-interpretation.md`, `wiki/normal-patterns.md`, `wiki/criteria.md`

패턴 분류 파일(`wiki/patterns/anomaly/*.md`)은 4단계에서 가설에 쓰는 패턴이 든 파일만 읽는다. Top-down 시나리오가 첨부되었으면 `AGENTS.md` 12절대로 5~8단계만 수행한다.

## 절차

1. 계획: 요청에서 범위, 건수, 기간을 정한다(기본값은 `AGENTS.md` 1절). 사용자가 기간을 날짜로 말했으면 그 기간이 분석 기간이다. 기간을 말하지 않았으면 최근 1년, 「최근 6개월」처럼 길이만 말했으면 그 길이로 하고, 날짜는 2단계에서 최근 데이터 날짜를 확인해 정한다. **여기서 정한 범위·건수·기간 해석은 확정이다.** 이후 단계에서 사용자 요청 문장을 다시 인용하거나 해석하지 않는다.
2. 대상: 범위 표현을 `wiki/index.md` 의 대응으로 OKF 도메인에 맞추고(범위가 없으면 거래 테이블이 많은 도메인 2개), 도메인 page 의 「## 테이블 목록」에서 `sql-query` 「테이블 선택」 절대로 분석할 테이블을 2개(많아도 3개) 고른다(`sql-query` 를 아직 읽지 않았으면 이때 `skill_view` 로 읽는다). 분석할 테이블은 거래 행(기준 날짜와 업무 키가 있는 행)을 담아야 한다. 테이블 문서를 한 응답에서 함께 읽고 테이블마다 정한다.
   - 기준 날짜 컬럼과 형식(`VARCHAR2(8)` 등), 차원(업체·거래선·담당자·사이트 코드 가운데 통계 도구 group_column 과 점검 질의에 함께 쓸 하나), 지표 후보(`has:amount` 금액, 수량, 두 날짜 사이 일수, 두 금액의 비율), 업무 키(`primary_key`, 그레인 블록), 번호 컬럼(결번 점검), 짝이 있어야 하는 상대 테이블(조인 문서), 데이터 정리 조건(soft-delete, 플레이스홀더), PII 컬럼
   - **점검할 데이터 이상징후 패턴**: `wiki/patterns/index.md` 2절 목록에서 탐지 수단이 「점검 질의」인 패턴 가운데 이 테이블 컬럼으로 조건을 쓸 수 있는 것(최대 6개)과 그 조건(분류 파일의 「점검 질의 열 조건」)
   - 분석 기간 정하기(사용자가 날짜로 기간을 말하지 않았을 때): 대상 테이블의 최근 데이터 날짜와 분석 기간을 아래 질의 한 문장으로 `sql_run` 1회 확인한다(테이블이 여럿이면 테이블마다 한 줄씩 `UNION ALL`). `FROM_DT`(포함) ~ `TO_DT`(미포함)가 분석 기간이고 `LAST_DT` 가 최근 데이터 날짜다. 테이블이 여럿이면 `LAST_DT` 가 가장 이른 테이블의 기간을 모든 테이블에 쓴다. `LAST_DT` 가 NULL(최근 2년 안에 데이터 없음)인 테이블은 대상에서 빼고 다른 거래 테이블을 고른다. 날짜는 결과 값을 그대로 쓰고 직접 계산하지 않는다.

     ```sql
     SELECT '<테이블>' AS TBL, m.LAST_DT, TO_CHAR(ADD_MONTHS(TO_DATE(m.LAST_DT, 'YYYYMMDD') + 1, -<개월 수>), 'YYYYMMDD') AS FROM_DT, TO_CHAR(TO_DATE(m.LAST_DT, 'YYYYMMDD') + 1, 'YYYYMMDD') AS TO_DT FROM (SELECT MAX(<기준 날짜>) AS LAST_DT FROM <query_name> WHERE <기준 날짜> <= TO_CHAR(SYSDATE, 'YYYYMMDD') AND <기준 날짜> >= TO_CHAR(ADD_MONTHS(SYSDATE, -24), 'YYYYMMDD') AND REGEXP_LIKE(<기준 날짜>, '^[0-9]{8}$')) m
     ```

     - `<개월 수>` 는 기본 12, 사용자가 길이를 말했으면 그 개월 수다.
     - 기준 날짜가 `VARCHAR2(8)`(YYYYMMDD)이면 위 그대로 쓴다. `VARCHAR2(14)`(YYYYMMDDHH24MISS)이면 `<기준 날짜>` 자리를 모두 `SUBSTR(<기준 날짜>, 1, 8)` 로, `DATE` 형식이면 `TO_CHAR(<기준 날짜>, 'YYYYMMDD')` 로 바꿔 쓴다.
     - 오늘 이후 날짜와 형식이 틀린 값(플레이스홀더 `'99991231'` 등)은 최근 데이터 날짜로 보지 않는다(위 WHERE 조건).
   - 표본이나 테이블 구조를 더 봐야 하면 통계 도구의 `describe_table` 을 쓴다(통계 도구 스키마의 테이블만).
3. 탐색(데이터 조회): 분석 기간만 집계한다.
   - 통계 도구: `stat-views.md` 6절의 관점표로 관점마다 도구를 정하고, 1~5절의 인자와 호출 단위를 따른다. 이 DB 의 날짜가 문자열이면 `stat-views.md` 4·5절의 조회문 방식으로 부른다. 기준 테이블 1개·호출 3회 이하면 직접 부르고(서로 의존하지 않는 호출은 한 응답에서 함께), 그 밖에는 기준 테이블마다 `stat-screener` 를 맡긴다(아래 「stat-screener 위임」).
   - 이상징후 점검 질의: 2단계에서 고른 점검 패턴을 `query-writing.md` 7절 질의 하나로 테이블당 `sql_run` 1회 실행한다. 빈 값 비율(P-123), 월말 3일 비중(P-129)도 이 질의의 열로 넣는다. 서로 다른 테이블의 점검 질의는 한 응답에서 함께 부른다.
   - 결과는 `result-reading.md` 기준으로 읽어 **이상 목록**(대상, 관점 또는 점검 열, 방향, 대상 값, 하한·상한 또는 평소·전체 값, 건수, 금액, 근거 호출)을 만든다. 수치는 결과 값 그대로 옮긴다.
   - 보고서 부록 A-1·7.2 재료: 테이블마다 분석 기간 행 수(점검 질의의 합계 행 CNT 또는 통계 도구 `scope.rows_in_period`)와 최근 데이터 날짜를 적어 둔다.
   - 부수 발견 재료: 통계 도구의 해석 주의·판정하지 않은 항목, 점검 질의에서 드러난 형식 오류·빈 값·플레이스홀더, 테이블 사이 최근 데이터 날짜 차이처럼 **감사 위험이 아니라 데이터 적재·품질 문제**로 보이는 것을 따로 적어 둔다(`answer-format.md` 3절 심각도).
4. 데이터 이상징후 패턴 대응과 가설 세우기: 문서만으로 한다(SQL 없음).
   1. 대응: 이상마다 `wiki/patterns/index.md` 1절 표로 패턴 ID 를 붙인다. 대응하는 패턴이 없는 이상은 가설로 세우지 않는다(이유: 대응하는 패턴 없음).
   2. 조합: 같은 점검 대상에서 함께 신호가 나온 패턴을 `wiki/patterns/index.md` 3절 규칙으로 2~3개씩 묶는다. 단서는 ① 통계 도구 후보의 target 과 점검 질의 결과의 DIM 이 같은 차원 값 ② 점검 질의 한 행에서 전체 비율보다 큰 열이 둘 이상인 차원 값 ③ 같은 테이블에서 함께 나온 행 수준 신호 ④ match_tables 결과의 기준 테이블과 같은 테이블의 행 수준 신호다. 조합마다 유형(같은 행, 집단→행, 흐름→행), 패턴별 조건 조각 초안(`query-writing.md` 6절), 근거 이상 수치를 적는다. 쓰는 패턴이 든 분류 파일을 이때 한 응답에서 함께 읽는다.
   3. 해석: 조합마다 `wiki/risk-interpretation.md` 3절로 감사 위험, 경영진 주장, 위험 구분을 찾는다. 연결되는 행이 없는 조합과 `wiki/normal-patterns.md` 로 이미 설명되는 조합은 가설로 세우지 않고 기록만 해 둔다(보고서에는 적지 않는다).
   4. 가설 세우기: 남은 조합을 패턴 수가 많은 순, 같으면 근거 이상의 차이가 큰 순으로 늘어놓고 H1 부터 번호를 붙인다(최대 5개). 조합 가설이 요청 건수보다 적을 때만 단일 패턴 가설을 뒤에 더한다. 가설마다 `answer-format.md` 3절 규칙으로 제목(데이터 현상 이름)을 짓는다.
5. 가설 조사: H1 부터 최대 5개를 `hypothesis-worker` 에 한 응답에서 함께 맡긴다(아래 「hypothesis-worker 위임」). worker 가 조합을 줄여 돌려주면(조합 축소) 줄인 조합을 그 가설의 조합으로 쓰고, 제목도 남은 현상에 맞게 고친다.
6. 표본 점검: worker 가 「충분」으로 돌려준 가설마다 worker 의 예외 질의로 `query-writing.md` 4절의 표본 질의(5행, PII 제외)를 `sql_run` 1회 실행한다. 건수 점검은 worker 가 분석 기간으로 이미 했으므로 다시 실행하지 않는다. 아래 판정 표로 가설마다 판정을 정한다.
7. 시나리오 SQL 확정: 「확인」 가설마다 worker 의 예외 질의(분석 기간)를 글자 그대로 시나리오 SQL 로 확정한다(다시 실행하지 않는다. worker 건수 점검의 HIT_AMT 는 선별 기준의 영향 규모 순위에 쓴다). 가설 제목이 시나리오 이름이다.
8. 선별·제출·보고서:
   1. `wiki/criteria.md` 로 「확인」 가설의 점수를 매겨 상위 요청 건수를 고른다. 나머지 「확인」 가설은 「확인(순위 밖)」이다.
   2. 제출(조립만 한다): 1에서 정한 순서 그대로, 시나리오마다 이름(가설 제목)과 SQL(7단계에서 확정한 예외 질의)을 글자 그대로 `answer-format.md` 1절 틀에 넣어 `sql_submit` 을 1회 부른다. 확인된 시나리오가 없으면 부르지 않는다. 이 단계에서는 기간·업무 키·조건·제목·점수를 다시 검토하지 않고, 사용자 요청을 다시 해석하지 않으며, 보고서를 구상하지 않는다. 표본 점검까지 통과한 SQL 은 제출 전에 다시 점검하지 않는다. `sql_submit` 을 부르는 응답에서는 제출 질의만 만들고, 보고서는 결과를 받은 다음 응답에서 쓴다. 오류면 `answer-format.md` 2절대로 1회만 다시 제출하고, 다시 실패하면 확인된 시나리오가 없는 것으로 처리한다.
   3. 보고서를 쓰기 직전에 `answer-format.md` 를 다시 읽는다(이 단계만 같은 대화에서 이미 읽은 파일을 다시 읽는다). `answer-format.md` 4절 틀로 **확인된 시나리오 1건마다 11절 분석 보고서 1개**를 `sql_submit` 입력 순서대로 쓴다. 재료는 이미 확정된 것(판정, worker 반환의 수치·설명 재료, 확인된 사실, 테이블 문서, `sql_submit` 결과)을 `answer-format.md` 4절 「재료 대응」 표대로 옮겨 쓰며 다시 정하지 않는다. 보고서 뒤에 `## 만들지 못한 시나리오`(판정이 반박·재분류·보류인 가설, 확인(순위 밖), `hit_count` 0)와 `## 부수 발견`, 맨 끝에 `## 부록: 시나리오 JSON` 을 둔다. 문체와 금지는 `answer-format.md` 5·6절을 따른다: 감사팀 사용자가 읽는 문서이므로 업무 말로, 물리명은 템플릿 자리에만, 통계·도구 용어와 agent 의 작업 과정(worker, 도구, 점수, 질의 ①·②, 점검 수치, 문서 경로)은 쓰지 않는다. `answer-format.md` 9절 점검을 마친 뒤 낸다.

예외 질의와 시나리오 SQL 은 특정 거래처나 사원을 지목하지 않고 데이터 이상징후 패턴 조합의 조건으로 쓴다. 지목된 대상은 근거 수치로 적는다.

## sql_run 상한 (main agent)

- main agent 의 `sql_run` 은 요청 1건당 **10회**다. 단계별로 나누어 두지 않고 합쳐서 센다. 쓰는 곳은 2단계 최근 날짜 확인(테이블이 여럿이면 `UNION ALL` 한 문장으로 1회, 사용자가 날짜로 기간을 말했으면 0회), 3단계 이상징후 점검 질의(대상 테이블당 1회)와 추가 템플릿(선택), 6단계 표본 점검(「충분」 가설당 1회), 수정과 제출 오류 뒤 재점검이다.
- 6단계 표본 점검에 쓸 횟수를 남겨 둔다. 남은 횟수가 모자라면 번호가 앞선 가설부터 표본 점검하고, 점검하지 못한 가설은 「보류」(이유: 호출 상한)로 적는다.
- 같은 SQL 은 다시 실행하지 않는다. 수정은 질의 1건당 3회까지이되 10회 안에서만 한다.
- 직접 읽는 테이블 문서는 10개까지, `sql_submit` 은 1회(오류 시 1회 재제출)다.

## stat-screener 위임

subagent 는 이 대화를 보지 못하므로 아래 항목을 prompt 에 모두 적는다. 물리명은 OKF 테이블 문서(또는 describe_table 결과)에서 복사한다.

1) 목표: 「<테이블> 의 아래 항목을 통계 도구로 계산해 stat-screener 반환 형식의 JSON 하나로 돌려준다」
2) 대상: `query_name` 과 기준 날짜 컬럼(형식 포함). 조회문 방식이면 조회문 원문(대조 대상 쪽은 match_select 원문)과 인자로 넘길 alias
3) 기간: 분석 기간의 시작일과 종료일(종료일 미포함, YYYY-MM-DD)
4) 지표: 지표 컬럼과 지표 종류. 간격은 시작 날짜와 끝 날짜, 비율은 분자와 분모
5) 비교 단위: 집단 컬럼(이상징후 점검 질의와 같은 차원). 없으면 「없음」
6) 조건: 같은 조건끼리 비교할 컬럼(최대 2개). 없으면 「없음」
7) 규칙 점검: 중복의 key 컬럼과 금액 컬럼, 결번의 번호 컬럼과 번호 체계 컬럼, 대조의 대상 테이블과 연결 키 쌍과 금액 컬럼 쌍. 없으면 「없음」
8) 출력 형식: 반환 형식의 JSON 하나, 후보 20건 이하, 공백을 뺀 4,300자 이하

- 돌려받은 결과가 JSON 이 아니거나 candidates, header.checks, not_evaluated 가 모두 비어 있으면 같은 prompt 로 1회 다시 맡기고, 다시 실패하면 그 테이블은 직접 호출로 계산한다.
- not_evaluated 에 「물리명 미확인」이 있으면 OKF 테이블 문서로 물리명을 다시 정해 1회 다시 맡긴다.

## hypothesis-worker 위임

subagent 는 이 대화를 보지 못한다. worker 가 값 확인·문서 탐색으로 질의를 낭비하지 않도록 **main agent 가 이미 확인한 사실을 모두 넘긴다.** 아래 항목을 prompt 에 모두 적는다.

1) 목표: 「아래 가설(데이터 이상징후 패턴 조합)이 분석 기간 데이터에서 조건 단위로 재현되는지, 정상으로 설명되지 않는지 조사해 hypothesis-worker 반환 형식으로 돌려준다」
2) 가설: 번호(H1 …)와 제목
3) 데이터 이상징후 패턴 조합: 패턴 ID·이름, 조합 유형, 분류 파일 경로, 패턴별 조건 조각 초안(테이블 컬럼으로 채운 SQL 조건, 집단 조각의 경계 값 포함)
4) 근거 이상: 패턴마다 이상 수치(대상 값, 평소·전체 값, 건수, 금액)와 근거 호출 요지(도구 이름과 주요 인자, 또는 점검 질의의 열 이름)
5) 감사 위험·경영진 주장·위험 구분(`wiki/risk-interpretation.md` 의 행)
6) 분석 기간: 시작일 포함·종료일 미포함 날짜와 기준 날짜 컬럼 형식에 맞춘 리터럴
7) 확인된 사실: `query_name`·유형(「테이블 선택」 기록 줄 포함), 기준 날짜 컬럼과 형식, 업무 키, 금액 컬럼(통화), 차원, 데이터 정리 조건, PII 컬럼, 쓸 조인과 근거(조인 문서 경로와 조건, 실측했으면 고아율), 정상 조건(`wiki/normal-patterns.md` 에서 대상 테이블에 해당하는 것과 그 절 번호)
8) 대상 테이블 문서 경로
9) 상한과 출력: `sql_run` 5회·통계 도구 2회 이하, 반환 형식(2,000 token 이하)

- 돌려받은 결과가 반환 형식이 아니면 같은 prompt 로 1회만 다시 맡기고, 다시 실패하면 그 가설은 「보류」(이유: 가설 조사 실패)로 적는다.

## 판정

가설마다 아래 표에서 위부터 맞는 첫 행으로 판정한다. 판정 이름의 뜻은 `answer-format.md` 3절이다.

| 상황 | 판정 |
|---|---|
| worker 가 「충분」이고, 표본 5행이 `wiki/normal-patterns.md` 의 정상 조건에 해당하지 않음 | 확인 |
| worker 가 「충분」이지만 표본 행이 `normal-patterns.md` 2절(업무 패턴)에 해당함 | 반박 (이유: 표본이 정상 업무 <패턴>) |
| worker 가 「충분」이지만 표본 행이 `normal-patterns.md` 1절(데이터 특성)에 해당함 | 재분류 (이유: 데이터 적재·표기 특성 <패턴>). 「부수 발견」에도 적는다 |
| worker 가 「반박」 또는 「재분류」 | worker 판정 그대로. 재분류는 「부수 발견」에도 적는다 |
| worker 가 「보류」, 표본 질의 오류가 `sql-query` 의 수정 뒤에도 남음, 호출 상한 | 보류 (이유: 확인하지 못한 까닭) |
