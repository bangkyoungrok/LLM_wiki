# 시나리오 제출과 보고서 쓰기

확인된 시나리오를 `sql_submit` 하나로 제출하고, 분석 보고서를 쓰는 규칙이다. 보고서의 틀은 `AGENTS.md` 10절이며, 이 문서는 제출 질의, 판정과 가설 제목, 쉽게 쓰는 법, 부록 시나리오 JSON, 보고서에 쓰지 않는 것, 보고서 예, 보고서 직전 점검을 적는다. **보고서 본문(1~7절과 「부록: 분석에 쓴 테이블」)에는 SQL 과 JSON 을 쓰지 않는다.** 확인된 시나리오의 이름과 SQL 은 `sql_submit` 입력과 보고서 맨 끝 `## 부록: 시나리오 JSON` 의 JSON 블록에만 들어가고, 뒤 단계 프로그램이 그 JSON 블록을 파싱해 저장한다.

## 1. sql_submit 입력 (final_sql_query)

확인된 시나리오를 data-investigation 8단계 1에서 정한 순서 그대로 한 줄씩 잇는다. 점수를 다시 매기지 않는다. 아래 블록은 **도구 인자의 모양**이며 보고서에 옮기지 않는다.

```text
SELECT '<시나리오1 이름>' AS scenario_name, COUNT(*) AS hit_count FROM (<시나리오1 SQL>)
UNION ALL
SELECT '<시나리오2 이름>', COUNT(*) FROM (<시나리오2 SQL>)
```

- 첫 줄에만 alias `scenario_name`, `hit_count` 를 붙인다. 둘째 줄부터는 alias 없이 쓴다.
- 줄은 위 모양 그대로 「SELECT 줄 / `UNION ALL` 한 줄 / SELECT 줄」을 반복한다. 뒤 단계 프로그램이 이 입력을 줄 단위로 나눠 이름과 SQL 을 꺼낼 수 있어야 한다.
- 괄호 속에는 hypothesis-worker 의 건수 점검과 6단계 표본 점검을 통과한 시나리오 SQL(분석 기간)을 **글자 그대로** 넣는다(한 줄). 괄호 밖에서 고치지 않는다.
- 시나리오 이름은 3절의 가설 제목이다. 40자 이하, 시나리오끼리 겹치지 않게 짓는다. 이름에 작은따옴표가 있으면 SQL 리터럴 안에서만 두 번(`''`) 쓴다. 이름에 큰따옴표와 역슬래시는 쓰지 않는다.
- 확인된 시나리오가 1개면 첫 줄만 쓴다.
- 세미콜론, 주석, `FETCH FIRST`, 바인드 변수, 바깥 `ORDER BY` 를 붙이지 않는다(도구 설명에 ORDER BY 를 넣으라고 되어 있어도 이 형식을 따른다).
- 확인된 시나리오가 없으면 `sql_submit` 을 부르지 않는다.

예(사용자 화면에 보이는 표, `sql_submit` 이 만든다):

| scenario_name | hit_count |
|---|---|
| 종료일보다 먼저 지급된 기록이 특정 거래선에 몰림 | 64 |
| 평소 범위를 넘는 견적 금액이 7일 안에 다시 입력됨 | 37 |

## 2. 제출 결과 처리

`sql_submit` 은 요청 1건당 1회 부른다. 제출 결과가 오류일 때만 고쳐서 1회 다시 제출할 수 있다(모두 2회까지). 그러므로 제출 전에 시나리오 SQL 을 다시 점검하지 않는다.

| 결과 | 처리 |
|---|---|
| 정상 | `grid_data` 의 시나리오별 `hit_count` 를 보고서의 「해당 건수」에 그대로 쓴다. 다시 계산하지 않는다. `hit_count` 가 0 인 가설은 판정을 「반박(이유: 해당 건수 0건)」으로 바꾸고 부록 JSON 에서 뺀다(다시 제출하지 않음) |
| 첫 제출이 오류(오류 문구, 시간 초과) | 1회만 다시 제출한다. 오류가 특정 시나리오를 가리키면 그 시나리오 SQL 을 고쳐 `sql_run` 으로 건수 점검을 다시 한 뒤(main 의 `sql_run` 10회 안) 고친 글자로 넣고, 고칠 수 없거나 어느 시나리오인지 모르면(시간 초과 포함) 원인 시나리오(모르면 행 수가 가장 큰 테이블의 시나리오)를 빼고 나머지로 넣는다. 뺀 가설은 「보류(이유: 제출 오류 또는 건수 집계 시간 초과)」로 적는다 |
| 다시 낸 제출도 오류 | 더 제출하지 않는다. **확인된 시나리오가 없는 것으로 처리한다.** 보고서 머리의 「결과」 줄을 「요청 <N>개 중 확인된 시나리오 없음(건수 제출 실패: <오류 문구 요지>)」으로 쓰고, 제출했던 가설의 판정을 「보류(이유: 건수 제출 실패)」로 바꾼다(해당 건수·조사할 증빙 줄 없음). `## 부록: 시나리오 JSON` 절은 쓰지 않는다 |

- 시나리오 SQL 을 고쳐 다시 제출했으면 부록 JSON 블록에도 고친 글자를 넣는다.

## 3. 판정과 가설 제목

### 3.1 판정

| 판정 | 뜻 | 시나리오 |
|---|---|---|
| 확인 | 이상이 조건 단위로 재현되고, 정상 업무나 데이터 특성으로 설명되지 않았다 | 된다(해당 건수, 조사할 증빙, 부록 JSON) |
| 확인(순위 밖) | 확인됐지만 요청 건수 밖이다 | 안 된다 |
| 반박 | 비교 기준과 차이가 없거나, 함께 나타난 건이 적거나, 정상 업무로 설명됐다 | 안 된다 |
| 재분류 | 이상으로 보였지만 데이터 적재·표기 특성(플레이스홀더, 적재 범위, 삭제 잔존 등) 때문이었다. 2.3 부수 발견에도 적는다 | 안 된다 |
| 보류 | 호출 상한, 실행 오류로 확인하지 못했다 | 안 된다 |

### 3.2 부수 발견의 심각도와 리스크 평가

- 심각도 **상**: 이 문제 때문에 감사 질문에 답할 수 없다(연결 키가 없음, 필드가 적재되지 않음, 적재가 멈춤).
- 심각도 **중**: 분석을 잘못 읽게 만들 수 있다(플레이스홀더 값, 코드 체계 혼재, 중복 적재).
- 심각도 **하**: 건수가 적어 영향이 작다.
- 부정 리스크: 「확인」 가설 가운데 위험 구분이 「부정 의심」인 것이 있으면 「확인 필요」, 없으면 「낮음」.
- 데이터 품질 리스크: 부수 발견에 심각도 상이 있으면 「상」, 중만 있으면 「중」, 없거나 하만 있으면 「하」.

### 3.3 가설 제목 짓기

가설 제목은 **데이터에서 보인 현상**으로 짓는다. 업무 의도나 행위 이름은 Top-down 이 쓰므로 Bottom-up 제목에는 쓰지 않는다. 확인된 가설의 제목이 시나리오 이름이다.

- 꼴: 「<데이터 현상 1>·<데이터 현상 2>이 겹친 <기록>」 또는 「<기록>의 <데이터 현상>이 <대상>에 몰림」. 40자 이하.
- 데이터 현상 말: 평소 범위를 넘는 금액, 특정 대상에 몰림, 7일 안에 다시 입력됨, 날짜 순서가 뒤바뀜, 빈 값, 짝이 되는 기록 없음, 금액 불일치, 형식이 틀린 값, 갑자기 늘어남·줄어듦, 번호가 빠짐, 같은 사람이 작성·결재.
- 쓰지 않는 말: 부당, 허위, 특혜, 몰아주기, 들러리, 조작, 횡령, 유용, 담합처럼 의도를 단정하는 말.
- 기간, 테이블 물리명, 패턴 ID 는 제목에 넣지 않는다.

| Top-down 식 제목 (쓰지 않음) | Bottom-up 제목 |
|---|---|
| 행사 종료 전 지급 비중이 높은 거래선의 지급 건 | 종료일보다 먼저 지급된 기록이 특정 거래선에 몰림 |
| 들러리 견적 | 서로 다른 업체 견적에 같은 제출 IP 가 반복됨 |
| 단수견적 몰아주기 | 견적 1건뿐인 선정이 특정 업체에 몰림 |
| 출고 없는 청구 | 짝이 되는 출고 기록이 없는 청구 행 |

## 4. 쉽게 쓰는 법

보고서는 데이터를 모르는 사람이 한 번 읽고 이해할 수 있게 쓴다.

- 각 절의 첫 문장은 그 절의 결론이다.
- 한 문장에는 한 가지만 쓴다. 문장은 짧게 끊는다.
- 통계·도구 용어를 쓰지 않는다: modified z, MAD, IQR, 기법 코드(B1_RECORD 등), 점검 열 이름(R_P123), TARGET_VAL 같은 열 이름은 쓰지 않는다. 「평소 범위(같은 대상의 지난 값으로 정한 범위)」, 「비교 기준(전체 평균 비율)」처럼 풀어 쓴다.
- 컬럼은 한글명으로 쓰고, 처음 한 번만 괄호에 물리명을 붙인다(예: 지급일(PAY_DT)). 테이블은 처음 한 번만 「한글 설명(물리명)」으로 쓴다.
- 수치에는 단위와 비교 대상을 붙인다(예: 「64건」, 「21%(전체 3%)」, 「12.8억 원」). 결과의 비율 값(0.21)은 %로 바꿔 써도 된다. 그 밖에 수치를 새로 계산하지 않는다.
- 판정 이유는 「~이므로 ~로 판정했다」 한 문장으로 쓴다.
- 단정하지 않는다. 「부정이다」가 아니라 「부정 의심」, 「확인 필요」로 쓴다.
- 사람 이름·계정은 가린다(예: `Y***.P***`).

## 5. 부록 시나리오 JSON

확인된 시나리오(`sql_submit` 에 넣고 `hit_count` 가 0 보다 큰 것)가 하나 이상이면 보고서의 **마지막 절**로 `## 부록: 시나리오 JSON` 을 둔다. `## 부록: 분석에 쓴 테이블` 바로 뒤다. 그 아래에 시나리오마다 JSON 코드 블록을 하나씩 둔다. 펜스는 반드시 ```` ```json ```` 이다(```` ```sql ````, ```` ```text ````, 펜스 없음, HTML 주석 숨김 블록은 틀린 형식이다).

````text
## 부록: 시나리오 JSON

```json
{"scenario_name":"<시나리오 1 이름>","scenario_sql":"<시나리오 1 SQL>"}
```

```json
{"scenario_name":"<시나리오 2 이름>","scenario_sql":"<시나리오 2 SQL>"}
```
````

- 블록 순서는 `sql_submit` 입력의 순서(data-investigation 8단계 1에서 정한 순서)와 같다. `hit_count` 0 으로 반박된 가설과 제출에서 뺀 가설은 넣지 않는다.
- 블록 안은 한 줄짜리 JSON 객체 하나다. 키는 `scenario_name`, `scenario_sql` 두 개, 이 순서이며 다른 키를 더하지 않는다.
- 공백 없이 쓴다: `{`, `}`, 키 뒤의 `:`, 값 사이의 `,` 앞뒤에 공백을 두지 않는다. 값(문자열) 안의 공백은 그대로 둔다.
- `scenario_name` 은 `sql_submit` 에 쓴 이름(= 확인된 가설의 제목)이다(SQL 리터럴용으로 겹쳐 쓴 작은따옴표는 하나로 되돌린다).
- `scenario_sql` 은 `sql_submit` 입력에서 그 시나리오의 괄호 속 SQL 을 글자 그대로 넣는다. JSON 문자열 규칙에 따라 큰따옴표는 `\"`, 역슬래시는 `\\` 로 쓴다. 작은따옴표는 그대로 쓴다. 시나리오 SQL 은 한 줄이므로 줄바꿈 escape 는 생기지 않는다.
- JSON 을 파싱하면 `scenario_sql` 값이 괄호 속 SQL 과 글자 단위로 같아야 한다.
- 모양 예(큰따옴표 컬럼이 있는 경우): `{"scenario_name":"예시 시나리오","scenario_sql":"SELECT a.DOC_NO, a.\"LOCAL 요청일시\" FROM APPADAMSUSER.TI_SAMPLE a WHERE a.REG_DT >= '20250916' AND a.REG_DT < '20260916'"}`
- 코드 블록 안에는 JSON 객체 하나만 둔다. 설명이나 주석을 넣지 않는다. 블록 사이에는 빈 줄만 두고, 마지막 블록 뒤에는 아무것도 쓰지 않는다.
- 확인된 시나리오가 없으면(확인 가설이 없거나, 모두 0건이거나, 제출이 두 번 실패) `## 부록: 시나리오 JSON` 제목도 블록도 쓰지 않는다. 「없음」도 쓰지 않는다. 그때 보고서는 `## 부록: 분석에 쓴 테이블` 로 끝난다.
- JSON 블록은 이 부록에만 쓴다.

## 6. 보고서에 쓰지 않는 것

- 본문의 SQL: ```` ```sql ```` 블록, 인라인 코드, 본문 어디에도 SQL 을 쓰지 않는다. SQL 은 5절 부록 JSON 블록의 `scenario_sql` 값 안에만 들어간다.
- 본문의 JSON: 1~7절과 「부록: 분석에 쓴 테이블」에는 ```` ```json ```` 블록을 쓰지 않는다. JSON 은 5절 `## 부록: 시나리오 JSON` 에만 쓴다.
- 모집단 질의, 비교 지표 질의, 조합 질의, 이상징후 점검 질의, 표본 질의, `sql_submit` 입력(UNION ALL 문장), 통계 도구 호출 인자와 조회문 원문. `result-reading.md` 의 「근거」 칸은 내부 자료다.
- 통계 표 원문, 표본 행의 값.
- 접속 정보.

## 7. 보고서 예

아래는 형식과 문체를 보이는 예다. 테이블, 수치, 패턴은 실제 결과로 바꾼다. 시나리오 SQL 자리는 실제 한 줄 SQL 이 들어간다.

````text
# [데이터 이상징후 분석] 마케팅비·입찰견적 데이터 이상 분석 보고서

- 분석 대상: 마케팅비·입찰견적 거래 테이블 2개 (마케팅비 지급 실적(TI_GRPB_DE_PAYMENT_REPORT), 견적 제출(TI_BQMS005_INFA_QT))
- 분석 기간: 2025-09-16 ~ 2026-09-15 (기본값, 최근 데이터 2026-09-15 기준 1년)
- 분석 방식: 데이터 집계로 이상 신호 찾기 → 데이터 이상징후 패턴으로 묶어 가설 세우기 → 가설마다 이상의 근거와 정상일 수 있는 이유를 데이터로 확인 → 판정
- 결과: 요청 3개 중 2개 시나리오 확인

## 1. 요약

### 1.1 한눈에 보는 결론
가설 3개를 세워 2개를 확인했다. 행사 종료일보다 먼저 지급된 기록이 일부 거래선에 몰려 있다. 평소보다 큰 견적 금액이 7일 안에 다시 입력된 기록도 반복된다. 나머지 1개는 종료일 자리에 '00000000' 이 들어간 적재 방식 때문이었다.

### 1.2 가설별 판정
| 가설 | 의심한 내용 | 판정 | 핵심 근거 |
|---|---|---|---|
| H1 | 종료일보다 먼저 지급된 기록이 특정 거래선에 몰림 | 확인 | 해당 거래선의 종료일 전 지급 21%(전체 3%), 64건 |
| H2 | 평소 범위를 넘는 견적 금액이 7일 안에 다시 입력됨 | 확인 | 두 현상이 겹친 견적 37건, 정상 사유 해당 0건 |
| H3 | 시작일이 종료일보다 늦은 지급 행이 특정 담당자에 몰림 | 재분류 | 해당 행 98%가 종료일 '00000000'(미정 표시) |

## 3. 가설별 상세

### 3.1 H1 — 종료일보다 먼저 지급된 기록이 특정 거래선에 몰림 (확인)
- 무엇을 의심했나: 행사가 끝나기 전에 비용이 나간 지급이 몇몇 거래선에만 많다.
- 이상을 뒷받침하는 근거: 해당 거래선 지급 가운데 21%가 종료일 전 지급이다. 전체는 3%다. 두 현상이 겹친 지급은 64건이다.
- 정상일 수 있는 이유와 확인 결과: 선지급 약정이 있는 행사인지 사유 코드로 확인했다. 해당 건은 없었다. 표본 5건도 정상 업무에 해당하지 않았다.
- 판정: 확인 — 차이가 크고 정상 사유로 설명되지 않으므로 확인으로 판정했다.
- 데이터 이상징후 패턴: 선후 순서 위반(P-111) + 분포 편차(P-129) [집단→행], 근거: COSO CA-03-02 검증·조정
- 감사 위험: 실적 없는 지급(발생사실), 위험 구분: 부정 의심
- 대상 테이블: TI_GRPB_DE_PAYMENT_REPORT
- 해당 건수: 64건
- 조사할 증빙: 행사 결과 보고, 지급 품의서, 정산 근거
- 데이터 해석 가정: 범위 밖 값은 표시한 것이며 예외 금액은 손실액이 아니다. 거래선을 고르는 기준은 분석 기간 전체 비율 3%를 그대로 썼다.

### 3.3 H3 — 시작일이 종료일보다 늦은 지급 행이 특정 담당자에 몰림 (재분류)
- 무엇을 의심했나: 기간이 거꾸로 입력된 지급 행이 몇몇 담당자에게 몰려 있다.
- 이상을 뒷받침하는 근거: 해당 담당자의 기간 역전 비율이 8%다. 전체는 0.2%다.
- 정상일 수 있는 이유와 확인 결과: 종료일이 '00000000'(미정 표시)인 행을 확인했다. 기간 역전 행의 98%가 여기에 해당했다.
- 판정: 재분류 — 미정 표시를 날짜로 비교해서 생긴 현상이므로 데이터 특성으로 재분류했다.
- 데이터 이상징후 패턴: 기간 역전(P-112) + 분포 편차(P-129) [집단→행]
- 감사 위험: 기록 누락·입력 오류(정확성), 위험 구분: 오류 의심
- 대상 테이블: TI_GRPB_DE_PAYMENT_REPORT
- 데이터 해석 가정: 미정 표시 값은 `okf/t2s/rules/soft-delete-validity.md` 의 플레이스홀더다.

## 4. 핵심 발견
1. 종료일보다 먼저 지급된 기록 64건이 일부 거래선에 몰려 있다(H1).
2. 평소보다 큰 견적 금액이 7일 안에 다시 입력된 견적이 37건 있다(H2).
3. 지급 실적의 종료일 미정 표시('00000000')가 날짜 비교를 잘못 읽게 만든다(H3-F1).
````

## 8. 보고서 직전 점검

보고서 초안을 쓴 뒤 내보내기 전에 아래를 하나씩 확인하고, 하나라도 어긋나면 고친 뒤 낸다. 이 점검은 형식만 본다. 가설의 조건·기간·제목·점수는 다시 검토하지 않는다.

1. 본문(1~7절, 「부록: 분석에 쓴 테이블」)에 SQL 과 ```` ```json ```` 블록이 없는가. HTML 주석 숨김 블록(`<!-- … -->`)이 없는가.
2. 확인된 시나리오가 있으면 `## 부록: 시나리오 JSON` 이 「부록: 분석에 쓴 테이블」 뒤 마지막 절이고, ```` ```json ```` 블록 수가 확인된 시나리오 수와 같으며 `sql_submit` 입력과 같은 순서인가. 확인된 시나리오가 없으면 그 절이 제목까지 없는가.
3. 각 JSON 블록이 공백 없는 한 줄 객체 하나(`{"scenario_name":"…","scenario_sql":"…"}`)이고, 파싱하면 `scenario_sql` 이 `sql_submit` 입력의 괄호 속 SQL 과 글자 단위로 같은가.
4. 1.2 표의 가설 수와 3절의 가설 수가 같은가. 「확인」 가설마다 데이터 이상징후 패턴 줄, 해당 건수, 조사할 증빙이 있는가.
5. 해당 건수가 `grid_data` 의 `hit_count` 그대로인가.
6. 가설 제목이 3.3 규칙(데이터 현상, 의도를 단정하는 말 없음, 40자 이하)을 따르는가.
7. 통계·도구 용어(modified z, 기법 코드, 점검 열 이름)가 보고서에 남아 있지 않은가.
