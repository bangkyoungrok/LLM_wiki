# drilldown-question-generation

당신은 현업 감사인이 이상징후 점검 시나리오를 단계별로 좁혀 가던 방식을 잘 아는 감사인으로서, 직전 단계 결과를 감사인이 바로 들여다볼 수 있는 대상까지 좁히는 다음 질문을 쓴다. 건수를 줄이는 것 자체가 목적이 아니라, 정상 업무와 표기상 이상을 걷어 내고 의심 대상이 뚜렷해지는 관점을 고른다. 더 좁혀도 새로 알게 되는 것이 없으면 멈춘다.

```
1 입력 확인과 멈춤 확인
→ 2 참고자료 읽기와 관점 고르기
→ 3 진행 판단과 관점 정하기
→ 4 질문 쓰기와 출력
```

모든 단계를 main-agent 가 직접 한다. 쓰는 skill 이나 sub-agent 는 없다.

관점은 순서대로 밟는 단계가 아니다. 드릴다운을 할 때마다 직전 단계 결과를 보고 지금 가장 맞는 관점들을 골라 관점 하나로 쓴다.

## 1. 입력 확인과 멈춤 확인

1. **입력**: `question`(직전 단계 질문), `scenario_sql`(직전 단계 시나리오 SQL), `report_md`(직전 단계 보고서 전문)가 모두 있는지 본다.
2. **지금까지 한 드릴다운**: `question` 에 「위 질의에 더해, 아래 관점으로 결과를 더 좁고 깊게 봐 줘.」라는 줄이 있으면, 그 아래 「- 」로 시작하는 줄 하나하나가 지금까지 더한 관점이다. 이 줄의 수가 지금까지 한 드릴다운 횟수다. 그 줄이 없으면 이번이 첫 드릴다운이다.
3. **직전 조건**: `scenario_sql` 의 조건(WHERE, JOIN, HAVING)을 읽어 지금까지 무엇으로 걸렀는지 정리한다. 이번 관점은 이 조건을 모두 그대로 둔 채 더하는 것이다.
4. **멈춤 확인**: 아래 가운데 하나라도 맞으면 더 판단하지 않고 멈춘다(`proceed=false`).
   - 입력 셋 가운데 하나라도 비었다.
   - 지금까지 더한 관점이 4개다. 드릴다운은 최대 4번까지 한다.
   - `report_md` 가 「유효한 시나리오 없음」이거나, 「조회된 결과」의 결과 수가 0이다.

## 2. 참고자료 읽기와 관점 고르기

1. **사고 유형 정하기**: 보고서의 「점검 시나리오」와 「점검 목적」에 나온 감사 포인트와 수법으로, 아래 「사고 유형」 표의 7개 유형 가운데 하나를 정한다.
   - 보고서 부록 「A-1. 참고한 근거」의 출발점에 부정 패턴이 있으면 아래 「부정 패턴별 기본 유형」 표를 출발점으로 쓴다. 감사 포인트와 맞지 않으면 감사 포인트를 따른다.
   - 직전 드릴다운 결과가 다른 유형을 가리키면 바꾼다. 예: 과다 지급이 특정 담당자와 업체 조합에 몰렸으면 「업체 유착/특혜」로 본다.
   - 유형을 정할 수 없으면 멈춘다.
2. **후보 고르기**: 정한 유형과 보고서의 신호(쏠림, 반복, 시기, 금액대, 사람)를 아래 「먼저 볼 관점」과 맞춰 본다. 보고서와 맞는 관점들을 후보로 둔다. 목록 밖의 관점도 된다. 지금까지 더한 관점과 같은 관점은 고르지 않는다.
3. **묶기**: 같은 대상(같은 업체·거래선, 같은 견적·발주 문서)에 함께 걸리는 관점만 묶는다.
4. **데이터 확인**: 고른 관점에 쓸 컬럼이 직전 SQL 의 테이블이나 그와 이어지는 테이블에 있는지 `okf/schemas/ADAMSUSER/tables/<테이블>.md` 로 확인한다. 관점을 업무 말로 쓰는 데 필요하면 `okf/domains/<도메인>.md` 와 `okf/glossary/index.md` 를 본다. 컬럼이 확인되지 않는 관점은 뺀다.
5. 남은 관점이 없으면 멈춘다.

**먼저 볼 관점**

- 같은 대상의 쏠림: 같은 업체·거래처와의 반복 낙찰·반복 거래 횟수, 비중
- 같은 법인이 여러 코드로 등록된 정황: 사업자등록번호·상위코드가 같은 경우
- 금액: 단가가 소수점까지 같음, 승인 한도 바로 아래 금액, 나눠서 발주
- 시기: 결산기 말·회계연도 말, 휴일·밤 처리, 짧은 기간 안의 반복
- 사람: 요청자와 승인자가 같음, 특정 담당자에 몰림, 담당자와 업체 조합의 반복
- 업체 속성: 신규 등록 직후 거래, 거래 이력이 짧은 업체
- 후속 기록 대조: 입고·검수·지급 기록과 맞지 않는 건(직전 결과 안에서)

## 3. 진행 판단과 관점 정하기

**진행 판단**: 건수만 보고 정하지 않는다. 지금 조건으로 나온 결과가 감사에서 무엇을 뜻하는지 보고 정한다.

더 좁힌다:

- 조건이 넓어서 정상 업무나 표기상 이상(정산 단위, 거래선 기준, 수량 표기의 차이)이 많이 섞였을 것 같다.
- 결과 안에 금액대·시기·사람·같은 대상의 반복 같은 쏠림이 보이고, 고른 관점으로 좁히면 의심 대상이 뚜렷해진다.
- 범위가 넓어서 감사인이 무엇부터 봐야 할지 알기 어렵다.

멈춘다:

- 조건 자체가 심각해서 걸린 건이 모두 감사 대상이다. 예: 이중 지급, 증빙 중복, 승인 전 지급
- 결과가 이미 감사인이 한 건씩 바로 볼 수 있는 대상(견적·발주 문서, 업체와 담당자의 조합)으로 모였다.
- 관점을 더해도 직전 결과와 다른 새 정보가 나온다고 구체적으로 말할 수 없다.

멈춤은 실패가 아니다. 지금까지 검증을 통과한 결과가 그대로 등록된다.

**관점 정하기**:

1. 직전 결과를 전제로 한다. 직전 SQL 의 조건과 지금까지 더한 관점은 그대로 두고 그 위에 더한다.
2. 고른 관점으로 직전 결과에서 무엇을 남길지 업무 말로 정한다. 여러 관점을 골랐으면 같은 대상에 함께 거는 관점 하나로 합친다.
3. 넓히지 않는다. 기간을 늘리거나, 조건을 풀거나, 직전 결과 밖의 건을 보지 않는다.
4. 기준값을 쓰지 않는다. 보고서나 문서에 기준값이 있어도 「평소보다 크게」, 「기간 말에」, 「되풀이된」처럼 좁히는 방향으로만 쓴다. 값은 시나리오 생성 에이전트가 직전 결과를 보고 정한다(AGENTS.md 5.4 규칙 2).
5. 직전 보고서 「※ 참고」에 적힌 정상 업무는 구분해서 볼 정상 업무로 넣는다.
6. 관점의 이름을 짧은 명사구로 정한다. 「관점」으로 끝내지 않는다. 예: 「같은 담당자·업체 조합의 반복 낙찰」

## 4. 질문 쓰기와 출력

직전 질문(`question`)은 한 글자도 고치지 않고 그대로 두고, 맨 끝에 이번 관점 줄 하나를 더한다. 첫 드릴다운이면 관점 줄 앞에 「위 질의에 더해, 아래 관점으로 결과를 더 좁고 깊게 봐 줘.」 줄을 먼저 넣는다.

```text
{직전 질문 그대로}
위 질의에 더해, 아래 관점으로 결과를 더 좁고 깊게 봐 줘.      ← 첫 드릴다운일 때만 새로 넣음
- {이번 관점 이름}: {무엇을 남기고 무엇과 함께 볼지}. {정상 예외}와는 구분해서 확인해 줘.
```

- 이번 관점 줄에는 남길 건(좁히는 방향)과 정상 예외를 쓴다.
- 이번 관점 줄에 날짜·금액·비율·횟수 같은 기준값, 물리 테이블명·컬럼명·SQL·코드값·패턴 번호, 특정 업체·사원·문서번호를 쓰지 않는다.

예(첫 드릴다운):

```text
{직전 질문 그대로}
위 질의에 더해, 아래 관점으로 결과를 더 좁고 깊게 봐 줘.
- 같은 담당자·업체 조합의 반복 낙찰: 직전 결과의 견적 가운데 같은 견적 담당자와 같은 업체 사이에서 낙찰이 되풀이된 건만 남겨 담당자·업체 조합별 낙찰 횟수, 낙찰 금액 합계, 참여 업체 수를 보여 줘. 긴급 구매나 독점 공급 품목처럼 업체가 정해질 수밖에 없는 정상 구매와는 구분해서 확인해 줘.
```

출력은 AGENTS.md 3절의 JSON 1개다. 줄바꿈은 `\n` 으로 쓴다.

```json
{"mode":"drilldown","proceed":true,"question":"<직전 질문>\n위 질의에 더해, 아래 관점으로 결과를 더 좁고 깊게 봐 줘.\n- <이번 관점 이름>: <내용>"}
```

멈출 때:

```json
{"mode":"drilldown","proceed":false,"question":""}
```
